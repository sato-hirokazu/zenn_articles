## はじめに

AIツールの普及で、開発速度は上がりました。
一方で「速く作れたが、品質が不安定」「レビューが追いつかない」「設計意図が失われる」といった問題も増えています。

AI時代に必要なのは、個人のスキルだけではなく、**プロセスそのものの再設計**です。
この章では、まず全体像と設計原則を整理します。

## 1. AI時代に起きた3つの変化

### 1.1 実装コストの急低下

以前は、コードを書く作業そのものがボトルネックでした。
今はAIが下書きを高速に生成するため、ボトルネックは次の3点へ移動しています。

- 問題設定の質
- 受け入れ条件の明確さ
- 検証の網羅性

つまり、開発の価値は「どれだけ書いたか」ではなく「何を正しく作ったか」で決まるようになりました。

### 1.2 設計と実装の距離が縮まった

AIは設計意図を与えると、複数の実装案を短時間で提示できます。
これにより、設計段階で「実装可能性の検証」をすぐ回せるようになりました。

結果として、次の流れが重要になります。

1. 設計仮説を立てる
2. AIで実装案を作る
3. 計測して比較する
4. 設計へ戻して更新する

このループを短く回せるチームほど、意思決定の質が上がります。

### 1.3 レビュー対象がコードから成果物全体へ広がった

AI活用時のレビューは、コードの見た目だけでは不十分です。
最低でも次を確認する必要があります。

- 要件との整合性
- セキュリティと法令順守
- テスト観点の不足
- 運用時の監視可能性

AI時代のレビューは、**成果物レビュー + プロセスレビュー**の両輪になります。

## 2. AI時代の開発プロセス設計原則

### 2.1 原則1: 仕様を先に機械可読化する

人間向けの仕様書だけでは、AIへの指示が曖昧になりがちです。
受け入れ条件を次のように構造化しておくと、生成品質が安定します。

- 入力条件
- 正常系出力
- 異常系出力
- 性能要件
- セキュリティ要件

この形式は、そのままテストケースの雛形にもなります。

### 2.2 原則2: 生成を前提に責務を分割する

AIが扱いやすい単位に分割すると、再生成や修正が容易になります。
目安として、1タスクは次の条件を満たすように設計します。

- 目的が1文で説明できる
- 入出力が明確
- 依存範囲が狭い

責務分割が不十分だと、AIが出した変更の影響範囲が読みにくくなります。

### 2.3 原則3: 生成物は必ず計測可能にする

「なんとなく良さそう」は禁止です。
判断は計測値で行います。

代表的な計測対象は次の通りです。

- テスト成功率
- 静的解析警告数
- パフォーマンス指標
- 変更失敗率
- 復旧時間

AIは高速に案を出せるので、計測基盤があるほど組織学習が加速します。

## 3. 役割分担の再定義

AI時代のチームでは、役割が次のように変わります。

### 3.1 エンジニア

- 実装者から「検証設計者」へ
- 重要タスク: 仕様の構造化、テスト観点設計、例外処理の定義

### 3.2 テックリード

- コード判断者から「プロセス設計者」へ
- 重要タスク: AI利用ポリシー、レビュー基準、品質ゲート設計

### 3.3 プロダクトマネージャー

- 要望収集者から「価値仮説の運用者」へ
- 重要タスク: 要件の優先順位付け、受け入れ条件の明確化、効果測定

## 4. 最小プロセスのテンプレート

小さく始めるために、次の6ステップをテンプレートとして使えます。

1. 課題とゴールを1ページで定義する
2. 受け入れ条件をチェックリスト化する
3. AIに実装案を複数生成させる
4. 自動テストと静的解析で機械判定する
5. 人間が設計意図と運用観点をレビューする
6. 学びをプロンプトとガイドラインへ反映する

重要なのは、6で終わらせずに次サイクルへ接続することです。

## 5. この章のまとめ

AI時代の開発プロセスは、次の考え方で設計します。

- ボトルネックは実装から検証へ移動した
- 仕様の構造化が品質と速度を同時に高める
- 役割は「書く人」から「正しさを設計する人」へ変わる

次章では、実際にチームへ導入するための具体的な運用フローを解説します。
