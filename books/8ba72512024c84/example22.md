## 1. コードレビューの目的と意義

### 1.1 コードレビューの目的

コードレビューをするのは、ひとことで言うと「良いコードにするため」です。

では「良いコードとはどんなコードなのか？」というと、以下の6つの観点が重要です。

**長期的な観点**:
1. **可読性**: 他の人が読んで理解しやすい
2. **保守性**: 後から変更しやすい
3. **堅牢性**: 予期せぬ入力や状態でも壊れない

**短期的な観点**:
4. **正しさ**: 仕様通りに動作する
5. **セキュリティ**: 脆弱性がない
6. **パフォーマンス**: 十分に速い

### 1.2 AI時代におけるコードレビューの重要性

近年では「コードレビューはAIにやらせているよ」という現場も増えてきていると思います。もちろん、それ自体は問題ありません。

ただし、ITエンジニアがコードレビューのやり方をよく理解しないままでよいのか、という疑問は残ります。少なくとも、AIが出してきたレビューコメントを読んで、

> 「うん、適切だね」

というように、その妥当性を評価できるスキルは身につけておくべきではないでしょうか。

そのためにも若手エンジニアはまず、自分でコードレビューする経験をある程度積んでおく必要があります。

## 2. Claude Codeプラクティス集

### 2.1 基本的なスタイル

著者の基本的なスタイルは以下の通りです。

- **Planモードから始める**: 気力があれば、Planはなるべくじっくり眺める。違和感があればClaudeにフィードバックする
- **直感にしたがってプロンプトを打つ**: Claudeが走り出したあとは、あまり考え込まず
- **yやplsだけ打つ**: Claudeの意見に異論がないときは `y` とだけ入力する（Yesの意味）
- **音声入力は使わない**: Linux環境のため
- **2〜4PJを並列で稼働**: いくつ動かすかは気分（気力）次第
- **hooksやskillsを作り込まない**: だいたい都度指示を出している

### 2.2 CLAUDE.mdの内容

CLAUDE.mdと rules/* には以下の内容を記載しています。

1. **テストに関する指示**: TDDで進めるよう明記
2. **ghコマンドでPRを作成**: 実装の区切りではghコマンドでPRを作成させる
3. **Issueによる作業引き継ぎ**: PR作成などのタイミングで、引き継ぎ資料をGitHub Issueとして記述するよう指示
4. **Codexによるレビュー**: `codex exec` コマンドでCodexによるレビューを受けるよう指示

### 2.3 TDDの徹底

CLAUDE.mdにはTDDで進めるよう明記しています。

```markdown
## Implementation Policy

Follow TDD; Test Driven Development.

**CRITICAL**: TDDの本質は「仕様をテストコードとして記述すること」である。
詳細なガイドラインは `~/.claude/rules/tdd-comprehensive.md` を参照。

### TDDサイクル

1. **RED**: 失敗するテストを書く
   - 仕様の詳細（サイズ、色、フォント等）を具体的な値で検証
   - エッジケース・異常系を最初から計画
2. **GREEN**: 最小限のコードでテストをパス
3. **REFACTOR**: コードを改善（定数化、命名、責務の分離）
4. **FEEDBACK**: 設計への気づきを反映

### テスト作成の必須要件

**正常系**:
- [ ] 具体的な値を検証（例: `expect(style.width).toBe(48)`）
- [ ] サイズ、色、フォントなど仕様の詳細をテスト

**エッジケース**:
- [ ] 空の値（空文字列、undefined、null）
- [ ] 非常に長い値（1000文字など）
- [ ] 矛盾する状態の組み合わせ（loading + disabled など）
- [ ] デフォルト値の確認
- [ ] 連続操作の挙動

**重要**: 「動作する」だけでなく、「どのように動作するか」を検証する。
```

単にプロンプトで「TDDで実装してください」と指示したとき、RED -> GREEN までしか行わず、Refactorしないことが何度かありました。そのため、CLAUDE.mdではRefactorを行うよう明示するとともに、実装したあとの気づきをフィードバックするように記載しています。

### 2.4 Issueによる作業引き継ぎ

Anthropic社のJason Kim氏いわく「GitHub IssueでもSlackでもEメールでも、自分の好きなやり方で構わないが、Claude Codeの作業が見えるようにしておく」とのことで、これに倣いGitHub Issueに作業記録を残すよう指示しています。

これをやっておくと、ヒトがAIの作業内容をトラッキングできるだけでなく、AI自身がセッションをまたいでコンテキストを引き継ぐことができます。

## 3. コードレビューはCLAUDE.md/skillsに書け

### 3.1 同じ指摘を繰り返すな

「一歩踏み込む Claude Code 活用LT会 〜新機能を使い倒す、現場の開発最前線〜」での登壇資料によると、コードレビューで同じ指摘を繰り返さないために、CLAUDE.mdやskillsにレビュー観点を記載することが重要です。

### 3.2 コードレビューの進め方

1. **プルリクエストを開く**: コードレビューのトリガーはPR
2. **diffの大きさを確認する**: PRの規模を確認
3. **descriptionなどからどんな変更が入ったのかを予想する**
4. **実際に変更されたファイルの一覧を確認する**
5. **実際にコードをレビューしていく**: 基本的に上から下へ順番に
6. **気になった部分にコメントを入れていく**: 可読性、保守性、堅牢性、正しさ、セキュリティ、パフォーマンスの6つの観点で
7. **CIのテストがパスしているかどうかを確認する**
8. **レビューが終わったことを連絡する**

### 3.3 PRの作成者が配慮すべき点

コードレビューは、する側の努力だけでなく、される側の協力も必要不可欠です。PRの作成者はレビュアーの負担を減らすために、以下のような点に配慮しましょう。

- **大きすぎるPRは小口化する**

## 4. Docs as Codeの運用

### 4.1 コンテキスト・エンジニアリング

AIにいい感じに動いてもらうには、プロンプトを工夫するだけでは足りないことが多いです。

チームでDocs as Codeを採用しているのも、このコンテキスト・エンジニアリングの観点が大きいです。

### 4.2 AI Readyなコードベースにするためのドキュメント管理

AI Agentが効果的にコードを生成できるよう、次のような情報をコードベース内に整備しています。

具体的には次のドキュメントを実際にGitHubのリポジトリに入れて管理しています。

- プロダクト画面仕様書
- ADR（Architectural Decision Record）
- Design Doc
- API定義（Protocol Buffers）

これらをコードと同じリポジトリで管理することで、AIがリポジトリ内のファイルとしてドキュメントに直接アクセスでき、コンテキストとして活用できるようになります。

### 4.3 実際の開発フロー

実際の開発フローとしては、何かを作るときに

1. 必要なドキュメントを参照
2. AI Agentに指示
3. 成果物をレビュー
4. 必要に応じてドキュメントを更新

というサイクルで回しています。

### 4.4 各ドキュメントの詳細

**プロダクト画面仕様書**:
- 画面単位やコンポーネント単位で、仕様書をMarkdownで管理
- 当初はデザイン要素も仕様書に書いていたのですが、プロジェクトの性質上デザイン変更が頻繁に発生し、仕様書の更新が追いつかなくなった

**ADR（Architectural Decision Record）**:
- プロジェクトの重要な設計決定を記録するドキュメント
- 場面に応じてセクションを追加・削除

**Design Doc**:
- API設計やデータベース設計、ロジックの設計など、技術的な詳細を書くドキュメント
- Design Docの運用には悩ましさもある
- ADRのような軽量なドキュメントだけの運用にシフトしていく可能性もある

**API定義（Protocol Buffers）**:
- Protocol BuffersによるAPI定義も、重要なドキュメントの1つ

## 5. まとめ

AI時代におけるコードレビューとドキュメント管理のポイントをまとめます。

### 5.1 コードレビューのポイント

1. **目的の理解**: 可読性、保守性、堅牢性、正しさ、セキュリティ、パフォーマンスの6つの観点を意識
2. **AIの評価能力**: AIのレビューコメントの妥当性を評価できるスキルを身につける
3. **CLAUDE.md/skillsの活用**: 同じ指摘を繰り返さないために、レビュー観点を明文化
4. **TDDの徹底**: テスト駆動開発をCLAUDE.mdで明記し、Refactorまで含めたサイクルを回す
5. **Issueによる引き継ぎ**: 作業記録をGitHub Issueに残し、人間とAIの両方がコンテキストを共有

### 5.2 Docs as Codeのポイント

1. **コンテキスト・エンジニアリング**: AIが効果的に動けるよう、ドキュメントをコードと同じリポジトリで管理
2. **AI Readyなドキュメント**: プロダクト画面仕様書、ADR、Design Doc、API定義などを整備
3. **開発フローの確立**: ドキュメント参照 → AI指示 → レビュー → ドキュメント更新のサイクル

これらのプラクティスを組み合わせることで、AI時代においても高品質なコードを効率的に開発・維持できる体制を構築できます。
