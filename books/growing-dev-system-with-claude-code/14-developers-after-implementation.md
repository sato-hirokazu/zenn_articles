第13章で、仕組みの総体をハーネスとして束ねました。
束ねたことで、投資判断も計測も1つの対象に対して行えるようになります。
最後に残った引用が、その章の締めにありました。
エージェントのログを読み、失敗を分析し、仕組みに還元すること自体が重要なエンジニアリングスキルである、というものです。

読む人がいなければ成立しません。

その人の側で何が起きているかは、ここまで一度も見ていません。

エンジニア3名による座談会記事に、手がかりになる数字が出ています。
業務時間のうちAIと対話したり作業を任せたりしている割合を問われて、3人はそれぞれ50〜60%、70〜80%、60%と答えています。
一日の半分以上が対話に置き換わったということです。

仕組みを育てるのは、この時間を過ごしている開発者です。
仕組みが劣化するかどうかは、この時間の質で決まります。

## 一日の半分以上が対話になる

3人の割合には差がありますが、上限が100%にならない理由は共通しています。
ミーティングが多い人は50〜60%にとどまり、少ない人は70〜80%まで上がる。
そして中間の1人は、100%にならない理由をこう説明しています。
作るものの方向性についてメンバーとディスカッションする部分は人間がやらないといけない。

第3章で扱った「作らない判断」が、時間配分の側から同じ場所を指しています。
何を作るかの合意は他人との間にあるので、対話の相手をAIに替えられません。
残りは替えられます。

置き換わった時間の中身が問題です。
実装していた時間が対話に変わったのだから、手を動かす回数は減ります。
減らないのは判断の回数です。

指示を書き、出力を読み、採否を決める。
この3つが1サイクルで、実装していた頃の1サイクルよりずっと短い。
サイクルが短くなった分、単位時間あたりの判断回数は増えます。
第1章で「書く速度と読む速度の非対称」を扱いましたが、読む側に回ってきた負荷は、レビュー工程だけでなく実装工程の内部にも来ています。

時間の使い方も変わります。
座談会では、ミーティングの前に依頼しておいてミーティング後に確認する、という使い方が挙げられています。
自分が手を動かしていないので、作業を待たせておける。
待たせておけるということは、複数を並行できるということです。

### 対話時間の内訳を1週間記録する

割合そのものは、あまり役に立ちません。
50%か70%かを知っても、次に何を直すかは決まりません。
役に立つのは内訳です。

1週間、次の4つに分けて記録します。
所要時間は日に2〜3分程度で、正確な計測は必要ありません。

```markdown
## 対話時間の内訳（YYYY-MM-DD 週）

| 分類 | 体感の割合 | 具体例 |
| --- | --- | --- |
| 指示を書く | 15% | 仕様の説明、参照先の指定、制約の追記 |
| 出力を読んで判断する | 45% | 差分の確認、方針の採否、やり直しの指示 |
| 手で直す | 25% | 命名、テストの期待値、境界条件 |
| 待つ | 15% | 実行完了を待っている時間 |
```

内訳が出たら、多い項目に対応する章へ戻ります。

| 多い項目 | 疑うべき場所 | 対応する章 |
| --- | --- | --- |
| 待つ | 1変更の粒度が大きい | 第5章 |
| 出力を読んで判断する | 人間が見る範囲の線引きが粗い | 第6章 |
| 手で直す | 規範が明文化されていない | 第4章 |
| 指示を書く | 毎回同じ前提を書き直している | 第4章 |

「手で直す」が4分の1を超えているなら、直した内容のうち2回以上現れたものが規範の候補です。
第4章の「同じ説明を2回したら、3回目の前に書く」を、レビューではなく自分の手直しに適用する形になります。

## のめり込めなくなる

座談会には、AIの効用を並べた記事にはあまり載らない証言が入っています。
フロントエンドを専門とするエンジニアの発言です。

> AIに実装をやらせているとき自体はそんなにワクワクしなくなってきました。自分が書いていないからのめり込めなくて、複数のことを並行して浅く広く動かす形になってしまっている。コードを書いているときの楽しさは、正直なくなってきましたね。

読み流すと、個人の感想に見えます。
実際には、この一文に第1章で導入した**認知負債**（コードは動いているが、理解している人間がいない状態）の発生機構が書かれています。

認知負債は結果の状態です。
理解している人間がいない、という完成した状態を指します。
その手前に、理解しようとする動機が下がる過程があります。
自分が書いていないのでのめり込めない、というのがその過程です。

順に並べると、こうなります。

1. 自分が書いていないので、コードへの没入が起きない
2. 没入していないので、複数を並行して浅く見る
3. 浅く見ているので、違和感が立たない
4. 違和感が立たないので、通す

3が要点です。
コードを読んで「ここは何かおかしい」と感じるのは、細部まで頭に入っている状態で起きます。
第6章で人間が見る範囲を線引きしましたが、線引きの内側に置いた変更でも、浅く見ていれば見ていないのと同じ結果になります。
線引きは対象を決める仕組みであって、注意の深さを保証しません。

同じ座談会には、逆向きの証言もあります。
モバイル開発を専門とするエンジニアは、楽しさはむしろ大きくなったと述べています。
ネット上の記事を探し回る時間をAIが肩代わりするので、プロダクトの仕様をどう改善すれば売上に貢献できるかという、本来考えるべきことに頭を使える時間が増えた、という説明です。
そして、職人的な充実感よりも事業を前に進めている手応えに重きが移ったと続けます。

2つの証言は矛盾しません。
没入の対象が、コードから事業側へ移ったと述べているだけです。

品質保証の側から見ると、移動には代償があります。
事業側に没入している人は、事業の判断で違和感を持てます。
コードの細部で違和感を持つ人が、その分減ります。
第2章でコードレビューの4つの役割を分解しましたが、そのうち「変更容易性の維持」と「実装の妥当性の確認」は、細部の違和感に依存する部分が大きい役割です。

### 並行本数に上限を置く

浅く広く並行することが問題なら、並行を減らすのが直接の対策です。
ただし「集中しましょう」では運用になりません。
数で決めます。

```markdown
## 並行作業のルール

- 同時に走らせる作業は2本まで
- そのうち1本は、差分を全部自分で読む
- 3本目を始めたくなったときは、次のどちらかを選ぶ
  - 走っている1本を終わらせてから始める
  - 走っている1本の粒度を割り直して短くする
- 不可逆な変更（第6章の分類）を含む作業は、必ず「全部読む」側に置く
```

2本という数字に根拠はありません。
1本では待ち時間が無駄になり、4本では全部が浅くなる、という体感の間を取っただけです。
自分のチームで調整する前提の初期値として置きます。

大事なのは2本目の条件です。
上限だけを決めると、上限まで並行して全部を浅く見る状態が正常化します。
「1本は全部読む」を条件に入れると、上限が読む余力で決まる形になります。

### 読んだかどうかを記録する

ルールは記録しないと守られません。
PRにラベルを2種類だけ用意します。

| ラベル | 意味 |
| --- | --- |
| `read-through` | 差分を全部自分で読んだ |
| `skimmed` | 主要部分だけ見た |

週次で比率を出します。
第9章で作った週次ワークフローに1行足すだけです。

```bash
# 先週マージされたPRのうち、read-through の比率を出す
SINCE=$(date -v-7d +%Y-%m-%d 2>/dev/null || date -d '7 days ago' +%Y-%m-%d)

TOTAL=$(gh pr list --state merged --search "merged:>=$SINCE" \
  --limit 200 --json number | jq 'length')

READ=$(gh pr list --state merged --search "merged:>=$SINCE label:read-through" \
  --limit 200 --json number | jq 'length')

echo "read-through: ${READ}/${TOTAL}"
```

比率そのものを目標にすると、ラベルだけが付きます。
第12章で「PR数やAI利用率を目標にすると作らない判断と衝突する」と書いたのと同じ罠です。

使い道は別に決めます。
`read-through` が3割を下回った週は、その週にマージした不可逆な変更を1件選び、翌週の朝会で担当者が口頭で説明します。
説明できれば、ラベルが `skimmed` でも実質は読んでいたということです。
説明できなければ、その週は並行しすぎていたということです。

ラベルは判定の材料であって、判定そのものではありません。

## 説明できるかを出荷条件にする

浅く見たまま通した変更を、どこで止められるでしょうか。
テストは止めません。
第10章で扱ったとおり、テストが通ることは実装と期待値が一致していることしか意味しないので、期待値が浅い理解のまま書かれていれば一緒に通ります。
静的解析も止めません。

止まるのは、説明を求められたときだけです。

第12章では、AIに変更の意図を説明させて、その説明に違和感を持てるかを認知負債のテストにしました。
あれは仕組み側のテストです。
ここで置くのは当事者側のテストで、自分が説明できるかを出荷の条件にします。

### PRテンプレートに1問足す

```markdown
## この変更でやりたいこと
<コードを見ずに、3行以内で書く>

## 自分で読んだ範囲
- [ ] 差分を全部読んだ
- [ ] 主要部分だけ読んだ
- [ ] 読んでいない（理由: ）

## 判断の出所
| 判断した内容 | 出所 |
| --- | --- |
| 一覧の並び順は更新日時の降順 | 仕様書（インタビューに基づく） |
| リトライは最大1回 | 推測。既存の実装に合わせた |

## 戻し方
<不可逆な要素があれば書く。なければ「なし」と書く>
```

「コードを見ずに」が効きます。
差分を見ながら書くと、差分の要約になります。
要約はAIが書けるので、書けたことが理解の証拠になりません。
コードを見ずに3行書けるかどうかは、頭に入っているかどうかの代理指標になります。

「判断の出所」欄は、第5章の仕様テンプレートに置いた根拠表を、PRの粒度に縮めたものです。
仕様書に根拠を書いていても、実装中に決めた判断は仕様書に載りません。
載らない判断がいちばん失われやすいので、PRで拾います。

### 空欄をCIで弾く

テンプレートは、埋めなくてもマージできる状態だと埋まりません。
第4章で扱ったとおり、守られるかどうかが推論に依存してよいものと、100%実行されなければならないものは分けます。
これは後者です。

```yaml
# .github/workflows/pr-description-check.yml
name: PR description check

on:
  pull_request:
    types: [opened, edited, synchronize, reopened]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - name: Check required sections
        env:
          BODY: ${{ github.event.pull_request.body }}
        run: |
          set -euo pipefail

          fail=0

          # 「やりたいこと」が3行以内で埋まっているか
          intent=$(printf '%s' "$BODY" \
            | awk '/^## この変更でやりたいこと/{f=1;next} /^## /{f=0} f' \
            | sed '/^\s*$/d' | sed '/^<.*>$/d')

          if [ -z "$intent" ]; then
            echo "::error::「この変更でやりたいこと」が空です"
            fail=1
          elif [ "$(printf '%s\n' "$intent" | wc -l)" -gt 3 ]; then
            echo "::error::「この変更でやりたいこと」が3行を超えています"
            fail=1
          fi

          # 読んだ範囲のチェックボックスが1つ選ばれているか
          checked=$(printf '%s' "$BODY" \
            | awk '/^## 自分で読んだ範囲/{f=1;next} /^## /{f=0} f' \
            | grep -c '^- \[x\]' || true)

          if [ "$checked" -ne 1 ]; then
            echo "::error::「自分で読んだ範囲」を1つだけ選んでください（現在 ${checked} 個）"
            fail=1
          fi

          # 戻し方が空でないか
          revert=$(printf '%s' "$BODY" \
            | awk '/^## 戻し方/{f=1;next} /^## /{f=0} f' \
            | sed '/^\s*$/d' | sed '/^<.*>$/d')

          if [ -z "$revert" ]; then
            echo "::error::「戻し方」が空です。不可逆な要素がなければ「なし」と書いてください"
            fail=1
          fi

          exit "$fail"
```

このチェックが判定できるのは、埋まっているかどうかだけです。
書かれた3行が本当に理解を表しているかは判定できません。
決定論で捕まえられるのは形式までで、中身は人間が見る側に残ります。
第6章で引いた線の、内側に置くべき項目がここに1つ増えます。

### AIにPR説明を書かせる場合

書かせてはいけない、とは言えません。
実際に書かせている現場は多く、書かせたほうが読みやすい説明になることもあります。

問題は、書かせた説明では「説明できない」が見えなくなることです。
テンプレートの欄を分けて対処します。

| 欄 | 書く人 |
| --- | --- |
| この変更でやりたいこと | 人間。コードを見ずに書く |
| 変更点の一覧 | AIでよい |
| 判断の出所 | 人間。AIが埋めた前提はAIに列挙させてよい |
| 戻し方 | 人間 |

「変更点の一覧」は差分から機械的に導けるので、AIに書かせても情報は失われません。
「やりたいこと」は差分から導けないので、AIに書かせると差分の要約に化けます。
差分から導けるかどうかが、分担の境界になります。

## 言語化の精度が責任の単位になる

座談会のエンジニアリングマネージャーは、変わったことをこう整理しています。
人との解釈合わせにかかるコミュニケーションコストが減った。
そして、AIへの指示は自分の責任で完結するから、より言語化の精度を上げないといけないという意識が強まった。

前半と後半が逆を向いているように見えて、同じ現象の裏表です。

人に頼むときは、曖昧な指示は聞き返されます。
「適切にエラーハンドリングしておいて」と言えば、どこまでを適切とするのかを尋ねられる。
尋ねられた時点で曖昧さが発覚し、その場で埋まります。
解釈合わせのコストは、曖昧さの検出装置としても働いていました。

AIは聞き返しません。
曖昧なところは、それらしい値で埋めて先に進みます。
埋めた事実がログにも残らないので、曖昧さは発覚せずに実装へ入ります。

コストが減ったのではなく、検出のタイミングが後ろへ移りました。
移った先が、レビューか、本番です。

### 埋めた前提を先に吐き出させる

座談会では、まず一度考えさせることを意識しているという工夫が挙げられています。
「プランニングしてください」と明示的に書いてから進める、という運用です。

プランを出させるだけでも効きますが、プランは「何をするか」の宣言なので、「何を勝手に決めたか」は出てきません。
決めた前提を分類して出させる形にします。

```markdown
---
name: clarify-instruction
description: 実装や調査の依頼を受けたとき、手を動かす前に、指示から読み取れなかった前提と自分で埋めた前提を列挙する。「実装して」「直して」「作って」と言われたが、対象・範囲・期待結果のいずれかが書かれていないときに使う。要求仕様書やチケットが添付されていて、正常系と異常系が表になっている場合は使わない。
---

## 手順

1. 依頼文から、実装に必要な決定事項を列挙する
2. 各項目を次の3つに分類する
   - 依頼文に書かれている
   - 書かれていないので、リポジトリの既存実装から推定した
   - 書かれておらず、推定もできないので仮に決めた
3. 3つ目が1件以上あれば、実装に入らず、下記フォーマットで出力して停止する
4. 3つ目が0件のときだけ、実装計画を提示してから作業に入る

## 制約

- 2つ目に分類した項目には、推定の根拠にしたファイルのパスを必ず添える。パスを示せないものは3つ目に分類する
- 「たぶん問題ない」で3つ目を2つ目に格上げしない
- 項目が0件になるまで依頼者に質問を返し続けない。1往復で答えられる形にまとめる

## 出力フォーマット

### 依頼文に書かれている
- <項目>

### 既存実装から推定した
| 項目 | 決めた内容 | 根拠にしたファイル |
| --- | --- | --- |

### 仮に決めた（確認が必要）
| 項目 | 仮の内容 | 確認したい相手 |
| --- | --- | --- |
```

制約の1つ目が肝心です。
根拠のパスを求めないと、推定と仮決めの区別が曖昧になり、ほとんどが「推定した」に寄ります。
パスを示せることを条件にすると、区別が機械的になります。

第5章の根拠表と同じ発想を、仕様ではなく指示に当てています。
仕様書の記述に「インタビューに基づく」「推測」「根拠なし」のラベルを付けたのと同じで、指示の解釈にも出所のラベルを付けます。

### 指示文に混ざる曖昧語

自分の指示文を検査する材料として、埋められやすい語を挙げます。

| 語 | AIが埋める内容 |
| --- | --- |
| 適切に | 一般的な作法。プロダクトの事情は入らない |
| いい感じに | 学習データ上の多数派 |
| 必要なら | 必要かどうかの判断ごと委ねている |
| 既存に合わせて | どの既存か。複数の流派があれば片方 |
| 基本的に | 例外の扱いが未定のまま進む |
| よくある形で | 汎用実装。ドメイン固有の制約は落ちる |

この一覧を、指示を書く前のチェックリストではなく、`clarify-instruction` を発火させる条件として使うほうが続きます。
人間が毎回チェックリストを見る運用は続きません。
語の一覧を description に書いておけば、該当する語を含む依頼で自動的に前提の列挙が入ります。

## コードの外に出た生成物

座談会で挙げられている使い道は、コードだけではありません。
顧客向けの案内文、顧客との調整の頭出し、社内チャットのステータス変更の自動化とスケジューリング、企画段階のアイデアのデータ化と画像化、ブラウザ操作を含むワークフローの実行。

第12章までの仕組みは、すべてリポジトリの中で完結しています。
テストゲートも、レビュー観点も、フィーチャーフラグも、コードにしか掛かりません。
コードの外に出た生成物には、何も掛かっていません。

しかも危険の性質が違います。
コードは第11章で扱ったとおり戻せます。
顧客に届いた文章は戻せません。

### 線引きをコードの外へ広げる

第6章でリスクによる線引きを作りました。
同じ3つの軸（クリティカル性、検出可能性、可逆性）を、コードの外の生成物に当てます。

| 生成物 | 誤りの影響 | 可逆性 | 掛けるゲート |
| --- | --- | --- | --- |
| 顧客に送る文章 | 誤情報が顧客の判断材料になる | 送信後は戻せない | 出所欄つきの下書きと、人間の承認 |
| 社内向けの周知 | 誤った運用が広まる | 訂正できるが浸透済み | 出所欄つきの下書き |
| 社内オペレーションの自動化 | 状態を書き換える | 操作によって異なる | 不可逆な操作を実行させない |
| 企画・プロトタイプ | 判断材料が誤る | 作り直せる | ゲートなし |
| 仕様書・設計文書 | 実装が誤る | 実装前なら戻せる | 第5章の根拠表 |

「企画・プロトタイプ」にゲートを掛けないことを明示しているのは意図的です。
全部にゲートを掛けると、いちばん効率が上がる用途が止まります。
座談会で挙がっているアイデアのデータ化や画像化は、誤っていても作り直せばよい種類の作業です。
第3章で「作らない判断」を扱ったのと同じ理由で、掛けないと決めることも設計です。

### 顧客に出る文章の下書きテンプレート

顧客向けの文章で問題になるのは、文体ではなく事実です。
根拠が曖昧なまま断言してしまうのがAIの特性だ、という指摘が座談会にあります。
案内文で断言される「事実」は、リリース日、影響範囲、料金、代替手段です。
どれも間違えると問い合わせが増えます。

```markdown
# 顧客向け案内の下書き

## 本文
<顧客に送る文章。AIに書かせてよい>

## 本文に含まれる事実と出所
| 記述 | 出所 | 確認者 |
| --- | --- | --- |
| 3月10日にリリース | リリース計画のチケット | <名前> |
| 既存の設定は引き継がれる | 実装（マイグレーション処理） | <名前> |
| 影響を受けるのは管理者権限のみ | 未確認 | - |

## 未確認の記述の扱い
<「未確認」が1件でもあれば、その記述を本文から削るか、確認を取るまで送らない>
```

出所の列に「実装」と書けることが条件になります。
「たぶんそうなっている」を出所として書けない形にしておくと、書けない記述が浮きます。
浮いた記述は、削るか確認するかの二択になります。

運用の勘所は、この表を送信後に捨てることです。
第5章の使い捨てドキュメントと同じで、残す価値があるのは表そのものではなく、確認したという事実だけです。
表を残す運用にすると、埋めるコストが上がって使われなくなります。

### 社内オペレーションの自動化

チャットのステータス変更やスケジューリングのような社内オペレーションは、コードより先に自動化が進みます。
コードレビューが要らないので、止める仕組みもありません。

第7章で組んだブリンカー型の制約と、第11章で扱った不可逆操作の扱いを、そのまま持ってきます。
エージェントに実行させない操作を列挙する形です。

```markdown
## 社内オペレーション自動化の禁止操作

エージェントに実行させず、提案までで止める操作。

- 削除（データ、チャンネル、カレンダー予定、ファイル）
- 権限の変更（メンバーの追加と削除、ロールの変更）
- 社外への送信（メール、顧客向けチャット、SNS投稿）
- 課金が発生する操作（外部APIの有料プラン、広告出稿）
- 一斉通知（全社チャンネル、全顧客へのメール）

上記以外は実行させてよい。
判断に迷うものは提案側に置く。
```

列挙の形にしているのは、「危険なものは避ける」という書き方では機能しないからです。
何が危険かの判断をエージェントに委ねることになり、判断が外れたときに止まりません。
禁止の列挙は決定論で、危険の判断は確率論です。

「上記以外は実行させてよい」を明記するのも意図的です。
禁止だけを列挙すると、書かれていない操作をどう扱うか毎回迷います。
迷うと、結局全部を人間が承認する運用に戻ります。

## 鍛える対象

座談会の最後で、これから磨くべき能力として4つが挙げられています。
ドメイン分解能力、抽象能力、言語化能力、そして事業全体を俯瞰できる広い視野です。
加えて、顧客の現場に立って提案する働き方（Forward Deployed Engineer と呼ばれる役割）への言及があります[^fde]。

[^fde]: Forward Deployed Engineer。顧客の現場に入り、その場で実装しながら課題を解く役割を指します。

抽象的な標語に見えます。
ドメイン分解能力を磨きましょうと言われて、明日から何をするかは決まりません。

ただ、4つとも本書の各章に対応物があります。

| 挙げられた能力 | 本書で対応する仕組み | その仕組みで外部化できた部分 |
| --- | --- | --- |
| ドメイン分解 | 第5章の変更粒度 | 1つの変更に入れるコンテキストの上限 |
| 抽象 | 第8章の観点の抽象度 | 指摘を観点へ書き上げる手順 |
| 言語化 | 第4章の規範の明文化 | 繰り返す説明を規範へ移す判断基準 |
| 事業理解 | 第3章の作らない判断 | 機能追加の判断チェックリスト |

対応関係を見ると、仕組みが何をしているかが分かります。
仕組みは能力の外部化です。
毎回の判断を、書いたものに肩代わりさせています。

そして外部化しきれなかった残りが、そのまま能力として要求されます。
第5章の粒度設計は、どこで切るかの判断基準までは書けますが、目の前のドメインをどう切るかは書けません。
第8章の観点の抽象度は、4段階の候補を出す手順までは書けますが、どの段階が自分のコードベースに合うかは書けません。

つまり4つの能力は、本書の仕組みを運用する能力そのものです。
仕組みを入れても要求は下がらず、要求される場所が変わります。

第13章で引いたハーネスの登壇資料は、ここに5つ目を足しています。
エージェントのログを読み、失敗を分析し、仕組みに還元することそのものがエンジニアリングスキルである、という指摘です。
座談会の4つが判断の質に関わる能力だとすると、こちらは記録を読む能力です。
第13章で `pipeline_run` と `edit_failure` のテーブルを置きましたが、テーブルは読まれなければ何も生みません。
そして記録を読む作業は、割り込みが入れば真っ先に飛ぶ種類の作業です。
第9章で週次ワークフローの負荷が実行ではなく監視と想起にあると書いたのと、同じ場所に来ます。

### 週次の練習に落とす

能力の話を能力の話として終わらせると、何も起きません。
第9章で作った週次ワークフローに、練習を1つ載せます。

| 鍛える力 | 週次でやること | 所要時間 |
| --- | --- | --- |
| ドメイン分解 | 今週マージした最大のPRを、3つに割り直す案を書く（実際には割らない） | 15分 |
| 抽象 | 今週の指摘1件を、狭い・中間・広いの3段の観点に書き直し、どれを採るか決める | 15分 |
| 言語化 | 今週2回以上説明したことを1つ、規範として書く | 15分 |
| 事業理解 | 今週の依頼1件について、作らない案を1つ書いて比べる | 15分 |
| 記録を読む | 先週いちばん多く落ちた段を1つ選び、落ちた理由を1行で書く | 15分 |

5つを毎週やる必要はありません。
週次の会で1つ選び、順に回します。
1周5週間で、5〜6週に1回ずつ当たる形になります。

「実際には割らない」と書いてあるのが、ドメイン分解の練習の要点です。
割り直しを実行に紐づけると、割る価値のないPRのために作業が発生します。
案を書くだけなら15分で終わり、次に似た変更が来たときの初期案として使えます。

抽象の練習は、第8章の自己改善スキルが提案する4パターンを人間の側でも1回やってみる、というだけのものです。
スキルが出した抽象度に違和感を持てるようになるのが目的で、違和感が持てないなら承認プロセスは形だけになります。
第8章で承認を人間に残した理由が、ここで練習の理由になります。

## アンチパターン

### 対話時間の割合を目標にする

「AIとの対話を業務の80%にする」を目標に置くと、対話しなくても済む作業まで対話に回します。
第12章で扱ったPR数やAI利用率と同じ罠で、測れる数字を目標にすると、その数字を作る行動が増えます。
座談会の3人の割合に差があるのは、ミーティングの量が違うからです。
割合は結果であって、揃えるものではありません。

### 「楽しくない」を個人の問題として処理する

のめり込めないという申告は、モチベーションの相談として扱われがちです。
そう扱うと、対処は面談になります。

前述したとおり、この申告は認知負債の予兆です。
対処は、並行本数の上限と、読んだ範囲の記録と、説明の要求です。
面談で解決する種類の問題ではありません。

逆に、全員が「楽しい」と答えているチームでも、事業側に没入が移っていればコードの細部の違和感は減ります。
申告の有無ではなく、説明できるかどうかで見ます。

### 説明責任をAIが書いた説明で満たす

PRテンプレートに「やりたいこと」欄を作って、そこもAIに書かせると、チェックは通って中身は空になります。
前述の分担表のとおり、差分から導ける欄と導けない欄を分けます。

導けない欄を人間が書いていることは、機械では確認できません。
第6章の線引きで人間側に残るものが、また1つ増えます。
増えることを認めておかないと、全部を自動化したつもりで穴が空きます。

### コードの外の生成物を対象外にしたまま量を増やす

いちばん静かに進むのがこれです。
コードには第10章のゲートが掛かっているので、事故の頻度は下がります。
一方で顧客向けの文章や社内オペレーションの自動化は、ゲートなしで量が増えます。

事故が起きるまで誰も担当を決めません。
第12章の劣化の表に、コード外の生成物の行を足しておくのが実務的です。
検知方法の列が埋まっていない行は、劣化しても誰も気づかない行だと書きました。
コードの外は、まだ行そのものがない状態です。

## この章のまとめ

- 業務時間の半分以上がAIとの対話になると、手を動かす回数は減りますが判断の回数は減りません。割合ではなく内訳（指示を書く・読んで判断する・手で直す・待つ）を1週間記録すると、次に戻るべき章が決まります
- 「自分が書いていないからのめり込めず、浅く広く並行する」という申告は、認知負債の完成した状態ではなく、その発生過程です。没入が起きない、浅く見る、違和感が立たない、通す、という順に進みます。第6章の線引きは対象を決めますが、注意の深さは保証しません
- 対策は数で決めます。同時2本まで、うち1本は全部読む、不可逆な変更は必ず読む側に置く。読んだかどうかをPRラベルで記録し、比率が下回った週は口頭説明で確かめます。比率そのものを目標にすると、ラベルだけが付きます
- 出荷条件に「コードを見ずに3行で説明できるか」を入れます。差分から導ける欄はAIに書かせてよく、導けない欄は人間が書きます。CIで判定できるのは空欄かどうかまでで、中身は第6章の線引きの人間側に残ります
- AIは曖昧な指示を聞き返さずに埋めるので、解釈合わせが担っていた曖昧さの検出が働きません。埋めた前提を「書かれている・既存実装から推定した・仮に決めた」に分類させ、推定には根拠のパスを必須にします。第5章の根拠表を、仕様ではなく指示に当てた形です
- 品質保証の仕組みはリポジトリの中で完結しています。顧客向けの文章、社内周知、社内オペレーションの自動化には何も掛かっておらず、しかも顧客に届いた文章は戻せません。第6章の3軸で線引きを外へ広げ、企画やプロトタイプには掛けないことも明示します
- 挙げられている4つの能力（ドメイン分解、抽象、言語化、事業理解）は、本書の第5章、第8章、第4章、第3章の仕組みが外部化しきれなかった残りです。仕組みを入れても要求は下がらず、要求される場所が変わります。週次の会で4つのうち1つを15分だけ練習し、4週で1周させます

## おわりに

まえがきで、ボトルネックは潰すと移動すると書きました。
ここまで14章かけて、移動の軌跡を追ってきたことになります。
実装からレビューへ、レビューから観点の陳腐化とドキュメント劣化へ、検知と計測と定着へ、仕組みの総体をどう投資対象として扱うかへ、そしてこの章で扱った開発者自身の変化へ。

ボトルネックの移動を論じた記事では、この移動の行き着く先が示されています。
ボトルネックは潰すと移動し、最後は「人と人の間」に来る、という指摘です。
技術で解ける部分を解き切った後に残るのは、意思決定、合意形成、認識の共有です。
同記事には厳しい指摘もあります。
「後知恵は先見につながらない。学習にはつながるが、予測能力は与えない」。
本書に並べた事例も同じです。
公開されている取り組みは学ぶ材料になりますが、自分のチームで次にどこが詰まるかは予測できません。

同記事はクネビン・フレームワークの区別を引いています。
Complicated は折りたたまれたもので、分解して再構成できます。
Complex は絡み合ったもので、分解すると壊れます。
本書が扱った仕組みの多くは Complicated 側にあります。
レビュー観点、テストゲート、承認フロー。
分解して組み直せます。
しかし人と人の間にあるものは Complex 側です。
設計しようと分解すると壊れるので、小さく試して観察するしかありません。

同記事のキーワードが「着眼大局、着手小局」です。
大きなゴールを見据えながら、小さな試行を積み重ねる。
権限を委譲し、信頼の貯金を作っていく。
そしてもうひとつのキー概念が「視点を動かす能力」です。
ボトルネックを直視するだけでなく、角度を変えて状況を再評価する。
同じ詰まりを別の面から見ると、違う手が見えることがあります。

そこで、明日から何を始めるかを3ステップにします。

1. **自分のチームで今どこが詰まっているかを、1つだけ特定する**。レビュー待ちの列か、仕様が決まらないことか、障害からの復旧の遅さか、あるいはこの章で扱った「誰も深く読んでいない変更が増えていること」か。詰まりの場所が分かれば、読むべき章が決まります
2. **その1箇所に対応する章の仕組みを、1つだけ入れる**。14章分を一度に実装しないでください。一度に作った仕組みは、育てられずに陳腐化します
3. **2週間後に、劣化していないかを見る**。第12章前半の表を使ってください。入れた仕組みが使われているか、使われた結果が実際に何かを変えたか。変わっていなければ、直すか捨てます

3ステップ目が本書の主題そのものです。
1と2は多くの記事が教えてくれます。
3を続ける人が少ないのです。

本書で作った仕組みも、必ず劣化します。
CLAUDE.md はずれ、観点は陳腐化し、テストは形骸化し、フラグは残ります。
第12章はそれを検知する方法を書きましたが、検知の仕組み自体も劣化します。
だから最後に残るのは、仕組みではありません。
劣化を見つけて直し続ける習慣です。
仕組みは半年で古くなりますが、習慣があれば作り直せます。
習慣がなければ、どれだけ精巧な仕組みを作っても、半年後には誰も使っていない設定ファイルが残るだけです。

そして、その習慣を持つのは仕組みではなく、一日の半分以上を対話に使っている開発者自身です。
この章で見たとおり、その開発者はコードへの没入を失いつつあります。
仕組みを育てる習慣と、育てる人がコードを理解していることは、別々に手を入れないと両方は残りません。

育てる、というのはそういう意味です。
