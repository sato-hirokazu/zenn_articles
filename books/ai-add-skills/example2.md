---
title: "第1章 レビューが詰まる構造"
---

この章では処方箋を書きません。
書くのは診断です。
AIコーディングエージェントを導入したチームで何が起きているのか、なぜそれが起きるのか、そしてなぜ「がんばってレビューする」「レビュアーを増やす」「AIに全部任せる」のいずれもが解決策にならないのか。
ここを構造として理解しておかないと、第3章以降で紹介する仕組みは「流行っているから入れる」だけの飾りになります。

## 書く速度と読む速度の非対称

MonotaRO社の技術ブログでは、Claude Code / Cursor / Codex といった複数のAIコーディングツールを組織に導入した結果として、「書く」工程が明確に加速した一方で、その加速がそのままレビュー負荷として現れた経過が報告されています。
PRの数が増え、PRについたコメントの数も増え、そしてその増分を読む仕事がシニアエンジニアに集中していきました。

ここで起きているのは、単なる「忙しくなった」ではありません。
組織のもっとも希少なリソース、つまりシニアエンジニアの集中力が、レビューという一点に吸い込まれていく構図です。
設計判断ができる人、事業ドメインを理解している人、過去の失敗を知っている人。
その人たちの時間が、増え続けるPRの読解に消費されます。

mtx2s氏の記事では、この状態を「コード生成スループットが人間のレビュー能力を上回る」状況として整理しています。
そして、この状況が組織内に対立を生むという指摘が続きます。

| 立場 | 主張 | 恐れているもの |
| --- | --- | --- |
| 品質懸念派 | 人間によるレビューは維持すべきだ | 誰も理解していないコードが本番に出ること |
| 停滞懸念派 | レビューを自動化して流量を上げるべきだ | AIを入れたのに前より遅くなること |

この対立は、どちらかが間違っているという話ではありません。
両方とも正しいことを言っています。
品質懸念派は「レビューが担っている機能」を守ろうとしていて、停滞懸念派は「レビューという工程」を疑っています。
守るべき機能と、その機能を実装している工程が、区別されないまま議論されている。
これが対立の正体です。

そして機能と工程を区別するには、まず「レビューが何を担っていたのか」を分解する必要があります。
それは第2章の仕事です。
この章では、分解が必要である理由を固めます。

### 3つの速度を並べる

症状を一段抽象化すると、こうなります。

| 速度 | 内容 | AI導入による変化 |
| --- | --- | --- |
| 書く速度 | 実装、修正、リファクタのコード産出 | 大きく上がる |
| 読む速度 | 差分の意図理解、設計妥当性の判断、リスク評価 | ほぼ変わらない |
| 維持する速度 | 検証、運用、セキュリティ対応、仕様の説明責任 | ほぼ変わらない、むしろ総量が増える |

3つのうち1つだけが上がる。
これが本書全体の出発点です。

```text
  従来                          AI導入後
  ┌──────────┐                ┌──────────────────────────┐
  │  書く    │                │         書く             │
  └──────────┘                └──────────────────────────┘
  ┌──────────┐                ┌──────────┐
  │  読む    │                │  読む    │  ← ここで詰まる
  └──────────┘                └──────────┘
  ┌──────────┐                ┌────────────┐
  │ 維持する │                │  維持する  │  ← 総量だけ増える
  └──────────┘                └────────────┘
```

上流が広がったのに、その下の口径が変わっていない。
だから詰まります。
詰まった場所が今のボトルネックです。

## なぜ人間のレビューはスケールしないのか

「読む速度」が上がらないのは、レビュアーの努力不足ではありません。
認知の構造上の制約です。
freee社の技術ブログでは、AI駆動開発を認知科学の枠組みで説明しています。
ここが本章の理論的な芯になります。

### ワーキングメモリの容量制限

人間が同時に保持して操作できる情報の項目数は、およそ 4±1 とされています。
この数字は訓練で大きく伸びるものではありません。

レビューの実作業では、差分を読みながら頭の中で次のものを同時に保持しています。

- この変更が何を実現しようとしているのか（意図）
- 変更前のコードがどう動いていたのか（現状）
- 呼び出し元と呼び出し先への影響（波及）
- 過去に似た変更で起きた障害（履歴）
- チームの規約や設計方針との整合（規範）

すでに5つです。
4±1の上限に届いています。
ここに「差分が大きい」「関連PRが複数ある」が加わると、保持しきれません。
保持しきれないとき人間が何をするかというと、読むのをやめて雰囲気で承認します。
レビューの形式は保たれ、機能だけが失われる。
これがもっとも危険な失敗モードです。

差分の量が増えたとき、レビューの質は緩やかに落ちるのではありません。
ある閾値を越えたところで崖のように落ちます。
容量制限とはそういうものです。

### 分散認知と共通基盤形成のコスト

freee社の記事では、認知が3つの軸に分散するという整理が示されています。

| 軸 | 意味 | 開発現場での例 |
| --- | --- | --- |
| 社会的分散 | 複数の人間の間に知識が分かれている | 設計者とレビュアーと運用担当が別人 |
| 時間的分散 | 過去の判断が現在の作業に影響する | 数年前の設計判断の理由を今調べる |
| 内部-外部分散 | 頭の中と外部の記録の間に知識が分かれている | 仕様書、コメント、チケット、コード |

そして、分散した認知を協働させるには「共通基盤形成（グラウンディング）」が必要です。
同じものを同じように理解している状態を作る作業であり、これにはコストがかかります。
レビューコメントのやり取り、設計相談、口頭での補足説明。
あれは全部グラウンディングのコストです。

ここでAI導入によって何が変わるか。
freee社の記事の指摘で本書がもっとも重視しているのは、次の転換です。

```text
  従来:  社会的分散が主
         人間A ←→ 人間B ←→ 人間C
         （会話、レビュー、相談でグラウンディング）

  AI導入後:  外部分散が主
         人間 ←→ 外部化された規範・仕様・コード
                    ↑
                  AIが読み書きする
```

社会的分散が外部分散へ転換する。
知識は人と人の間ではなく、人と外部記録の間に分かれるようになります。

この転換には良い面があります。
外部化された規範はAIが読めます。
人間相手の口頭説明はスケールしませんが、明文化された規範はコピーできます。
第4章でCLAUDE.mdやSkillsを扱うのは、この外部化を意図的にやるためです。

同時に、悪い面が明確に出ます。
外部記録が実態とずれていると、AIはずれたまま高速に走ります。
そしてどの工程を高速化しても、最後に「これで良いか」を決める人間の判断が残ります。
人間の意思決定が律速段階になる。
生成が速くなればなるほど、律速段階の存在感が増します。

### 認知負債と意図負債

freee社の記事では、技術的負債とは別に2種類の負債が示されています。
本書ではこれを繰り返し参照します。

| 負債 | 状態 | AIが返済できるか |
| --- | --- | --- |
| 技術的負債 | コードが読みにくい、設計が古い | できる |
| 認知負債 | コードは動いているが、理解している人間がいない | できない |
| 意図負債 | 何を実現したかったのかが失われている | できない |

技術的負債は、AIにとって比較的得意な領域です。
リファクタリング、テストの追加、型の整備。
人間より速くやれる場面が増えました。

一方、認知負債と意図負債はAIでは返済できません。
理由は単純で、これらは「コードの外」にある情報だからです。
なぜこの実装を選んだのか。
なぜこの選択肢を捨てたのか。
何を許容し、何を許容しなかったのか。
コードには「どう動くか」しか書かれていません。
「なぜそうしたか」は人間が保持しなければならない。

そして生成が速くなると、この2つの負債は自動的に積み上がります。
動くコードは増える。
理由を知っている人間は増えない。
AI駆動開発で本当に管理すべき負債は、技術的負債ではなくこちらです。

## なぜ「レビュアーを増やす」では解決しないのか

読む速度が足りないなら人を増やせばよい、という発想は自然です。
しかしこれはスケールしません。

リクルート社の黒田氏の資料では、コミュニケーションパスが人数の二乗で増えることが示されています。
8人のチームで、相互作用のパスは56本になります[^paths]。
人を1人増やすと、増えるのはその人の生産力だけではなく、その人が関わるパスの本数です。

[^paths]: 方向を区別して数えた場合の n×(n−1) です。

```text
  人数   パス数   1人増やしたときの増分
  ----   ------   ----------------------
   3人     6本     ＋6本（4人で12本）
   4人    12本     ＋8本（5人で20本）
   8人    56本     ＋16本（9人で72本）
```

レビュアーを増やすと、レビュー容量は線形に増えますが、認識を揃えるためのグラウンディングコストは二乗で増えます。
「レビュアーAは通したがBは差し戻した」「誰がどのPRを見ているのか分からない」。
この状態は容量不足より悪い場合があります。

さらに、黒田氏の資料は、生成コストが下がるほど工程間の受け渡しが相対的に高く見えることを示しています。

| 工程 | AIによる高速化 |
| --- | --- |
| 要件を整理する | される |
| 設計する | される |
| 実装する | される |
| テストを書く | される |
| 工程間のハンドオフ（引き継ぎ、合意、待ち） | されない |

各工程の作業時間が大きく縮んでも、工程と工程の間で人間が引き継ぎ、合意し、待つ時間は変わりません。
作業時間が縮むほど、リードタイムに占めるハンドオフの比率が上がります。
人を増やすことは、ハンドオフの本数を増やすことです。
だから増員は、いちばん縮まない部分を太らせます。

## なぜ「AIに全部任せる」でも解決しないのか

では反対に、レビューを丸ごとAIに渡せばよいのか。
これも現時点では成立しません。
mtx2s氏の記事では、「現時点では、AIによるコードレビューだけで、すべての問題を安定的に検出できるとは言いがたい」と述べられています。
ポイントは「安定的に」です。
AIレビューは当たるときは人間より速く深く当たります。
しかし当たり方が安定しない領域があります。

とくに次の2種類で人間の役割が残ります。

- **仕様意図**：この実装が「動くか」ではなく「求められていたものか」の判断。要求そのものが外部記録に完全に書かれていない場合、AIには判定材料がありません
- **文脈依存的な知識**：この顧客だけ例外運用がある、この機能は来期廃止予定、このテーブルは他システムが直接読んでいる。コードにもドキュメントにも書かれていない知識です

そしてもう一つ、実務でより頻繁に問題になるのがノイズです。
MonotaRO社の事例では、AIレビューの導入において「単なるノイズではない、価値あるAIレビューをどう実現するか」が課題として立てられています。

ノイズレビューが厄介なのは、害が二重だからです。

| 段階 | 起きること |
| --- | --- |
| 1 | 的外れな指摘が大量に出る |
| 2 | 開発者が読み飛ばすようになる |
| 3 | 読み飛ばす習慣ができ、本物の指摘も飛ばされる |
| 4 | AIレビューがあるという事実だけが残り、機能しない |

つまり「AIレビューを入れた」ことは何の保証でもありません。
それが読まれているか、指摘の的中率が維持されているかが問題です。
的中率は放っておくと下がります。
コードベースは変わり、規約は変わり、去年有効だった観点は今年ノイズになるからです。
ここが本書のタイトルにある「育てる」が必要な理由であり、第7章から第9章で扱う内容です。

## ジェボンズのパラドックスとROI成立境界

ここまでの話に対して、「そのうち落ち着くのでは」という期待があるかもしれません。
開発が速くなれば、いずれ作るものがなくなって、レビュー負荷も落ち着くのではないか。
これは期待できません。

黒田氏の資料では、ジェボンズのパラドックスが引かれています。
効率化は消費量を減らさず、むしろ増やすという現象です。
蒸気機関の効率が上がって石炭を節約できるようになったとき、石炭の消費は減りませんでした。
用途が広がり、1900年までに消費は3倍になりました。

ソフトウェア開発でも同じことが起きています。
同資料では、日本のITエンジニア数が1985年の約32万人から2024年の約144万人へ、4.5倍に増えたことが示されています。
開発が効率化されるあいだ、必要な人数は減っていません。

### ROI成立境界の低下

なぜそうなるのか。
メカニズムは「ROI成立境界の低下」です。

```text
                      初期開発コストが高い   下がった後
  全社システム                 作る            作る
  事業部システム               作る            作る
  ------------------------- ROI成立境界 ---
  部署単位の業務ツール        諦める           作る
  顧客個別の作り込み          諦める           作る
                              --------- ROI成立境界 ---
  さらに小さいもの            諦める          諦める
```

初期開発投資が減ると、従来は採算割れだった案件が経済的に成立します。
部署単位のツール、顧客単位の作り込み、社内の小さな自動化。
これまで「やりたいが割に合わない」として棚上げされていたものが実行可能になります。
結果として、開発の総量は自然に増えます。

### コスト構造の非対称性

そして、ここに本章でもっとも効く非対称性があります。
同資料の整理を借りると、こうです。

**初期開発コストは下がる。維持保守、検証、セキュリティ、責任は自動では下がらない。**

| 項目 | AIによるコスト変化 |
| --- | --- |
| 初期開発 | 大きく下がる |
| 維持保守 | 自動では下がらない |
| 検証（テスト、レビュー） | 自動では下がらない |
| セキュリティ対応 | 自動では下がらない |
| 説明責任、意思決定 | 自動では下がらない |

作られるシステムの数は増える。
1つあたりの維持コストは減らない。
掛け算の結果として、維持側の総量は増えます。

この章の最初に置いた「3つの速度」の表に戻ります。
書く速度だけが上がり、読む速度と維持する速度は上がらない。
しかも需要は減らないので、読む対象と維持する対象は増え続ける。
放置すれば必ず詰まります。
詰まるかどうかではなく、いつどこで詰まるかの話です。

## 診断のチェックリスト

自分のチームが今どの状態にあるかを確認するための項目です。
当てはまるものが多いほど、この章で述べた症状が進行しています。

- [ ] PRの差分行数が、以前より明らかに大きくなっている
- [ ] 特定の1〜2名にレビュー依頼が集中している
- [ ] 「読み切れないが、テストが通っているので承認」が起きている
- [ ] レビューコメントの量は増えたが、設計に関する議論は減った
- [ ] マージされたコードについて「なぜこの実装か」を説明できる人がいない箇所がある
- [ ] 仕様の根拠がチケットにもコードにも残っておらず、担当者の記憶だけにある
- [ ] AIレビューの指摘を、開発者が読まずに閉じている
- [ ] レビュー待ちの時間が、実装時間より長くなっている
- [ ] 「レビューを厳しくすべきだ」と「レビューが遅すぎる」が同じチーム内で同時に主張されている

最後の項目が出ているなら、それは前述の品質懸念派と停滞懸念派の対立です。
これは人の問題ではなく構造の問題です。

## 本章の結論

ここまでの診断が示すのは、打つべき手が「レビューを速くする」ではないということです。
レビューを速くしようとすると、次のどちらかになります。
1つは、人間が無理をして読み、質が崖のように落ちる。
もう1つは、AIに丸投げして、仕様意図と文脈依存的な知識の検査が抜け落ちる。
どちらも、レビューという工程を1つのブラックボックスとして扱っているために起きます。

必要なのは、レビューが背負っているものを分解し、それぞれを適切な場所に配置し直すことです。
あるものは生成の前に移し、あるものは自動化し、あるものは人間の手元に残す。
配置し直せば、人間が読む量は減り、それでも守られるものは守られます。

そのためには、まず「レビューは何を背負っていたのか」を明らかにしなければなりません。
それを第2章で行います。

## この章のまとめ

- AI導入で上がるのは「書く速度」だけであり、「読む速度」と「維持する速度」は上がりません。この非対称がボトルネックをレビューに移動させています
- 人間のレビューがスケールしないのは努力不足ではなく、ワーキングメモリが4±1項目に制限されているという認知の構造上の制約です。容量を超えたときレビューの質は崖のように落ちます
- AI導入は社会的分散を外部分散へ転換させ、人間の意思決定が律速段階になります。そして認知負債と意図負債は、AIでは返済できず人間が保持するしかありません
- レビュアー増員はグラウンディングコストを二乗で増やし、AIへの丸投げは仕様意図と文脈依存的な知識を取りこぼします。どちらも単独では解になりません
- ジェボンズのパラドックスにより需要は減らず、ROI成立境界の低下で開発総量は増えます。初期開発コストだけが下がり、維持と検証と責任は下がらないという非対称が残ります
- したがって打つべき手はレビューの高速化ではなく、レビューが背負っているものの分解と再配置です。分解は第2章で行います
