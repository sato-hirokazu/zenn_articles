第7章から第9章では、レビュー工程をAIに任せ、その観点を育て、更新候補を自動検出する仕組みを作りました。
ここでひとつ、構造的な問題が残っています。

生成は推論です。
同じ指示を10回与えれば、10通りの出力が返ってきます。
そしてレビューも、AIに任せた部分は推論です。
同じ差分を10回見せれば、指摘の数と内容が揺れます。
つまり、ここまで作ってきた2段階は、どちらも確率論的でした。

確率論的な工程をいくら積み重ねても、確率論的なままです。
95%の精度のゲートを2枚重ねても、通り抜ける5%の性質が変わるだけで、絶対に止まる保証は生まれません。
品質保証の連鎖のどこかに、揺れないものが1枚必要です。

ここから第4部に入ります。
第4部の主題は「パイプラインで保証する」ことです。
この章では、確率論的な生成に対して決定論的な評価をぶつける構造を作ります。

## 品質責任を確率論と決定論に分ける

リクルート社の黒田氏の資料は、この章の柱になる原則を示しています。
確率論ベースの生成と、決定論ベースの評価系へ、品質責任を分離するという原則です。

言い換えると、こうなります。
生成が揺れること自体は、直す対象ではありません。
揺れは推論の性質であり、消せません。
代わりに、揺れた出力を受け止める評価側を、揺れない仕組みで固めます。
生成の品質を上げる努力と、評価の確実性を上げる努力は、別の場所に投じる必要があります。
この原則が実務でどう機能するかは、同じ資料にある失敗と改善が対になった事例が示しています。

## 『Airワーク』EOSL対応の事例

同資料では、『Airワーク』のEOSL（End of Service Life、サポート終了）対応を題材に、AIによる移行の取り組みが報告されています。

### 初期構成とラルフループ

最初の構成では、AIに生成と検証の両方を任せていました。
AIがコードを書き、テストを実行し、失敗したら自分で直す。
この自律的なループを回せば移行が進むはずだという設計です。

結果は、ラルフループと呼ばれる無限ループでした。
同資料の報告によれば、数日で数百万円のトークン代を消費しています。

なぜ止まらなかったのか。
ループの終了条件を判定する側も、AIだったからです。
AIが「これで正しい」と判断する基準そのものが推論なので、判断が揺れます。
あるとき正しいと判断したものを、次の周回で誤りと判断し、直し、また誤りと判断します。
収束の保証がありません。
これは能力の問題ではなく構造の問題です。
確率論的な工程の中に、確率論的な停止条件を置いた。
だから止まりませんでした。

### 改善後の3段構成

改善後の構成では、責任が3段に分かれました。

1. AIは観点出しとYAML仕様書の生成のみを担当する
2. テストコードの生成は、決定論的なプログラムが行う
3. 評価は、テストの実行とカバレッジで決定論化する

境界を図にすると、次のようになります。

```text
 ┌─ 確率論の領域（推論・揺れる） ──────────────────────────┐
 │  ソースコード ──▶ AI:観点出し ──▶ AI:YAML仕様書の生成   │
 └───────────────────────────────────────────┬────────────┘
                                             │
                     ┌───────────────────────▼──────────┐
      ここが境界 ──▶ │  YAML 仕様書（機械検証可能）      │
                     └───────────────────────┬──────────┘
                                             │
 ┌─ 決定論の領域（プログラム・揺れない） ─────▼────────────┐
 │  ジェネレータ ──▶ テストコード ──▶ 実行＋カバレッジ     │
 │                                        └──▶ 合否       │
 └─────────────────────────────────────────────────────────┘
```

YAMLより下にAIが一切入っていません。
AIの出力はYAMLで止まります。
そこから先は、同じYAMLを入れれば必ず同じテストコードが出て、同じテストコードは必ず同じ合否を返します。
停止条件が決定論になったので、ループは収束します。

### なぜ中間表現がYAMLなのか

この形は、第4章で扱った中間ファイル戦略と同じ構造です。
ZOZO社の事例では、ソースと成果物の間に規約ファイルと構造ファイルを挟んでいました。
AIに直接ゴールを作らせず、検証可能な中間表現を経由させる形です。

中間表現をYAMLにしたことには理由があります。
機械的に検証できるからです。

- スキーマ定義と照合すれば、必須項目の欠落を自動で検出できる
- 差分が構造単位で読める。テストケースが1件増えたことが1ブロックの追加として見える
- パーサに通せば、ジェネレータが確実に解釈できる
- 人間が読める。テストコードより短く、観点の一覧として目視レビューできる

もしAIにテストコードを直接書かせていたら、この4つのどれも成立しません。
生成物の妥当性を判定する手段が、結局レビューか実行しかなくなります。
中間表現を挟むと、AIの担当区間の出口に決定論的な検証点を1枚置けます。

そして、この事例から取り出せる示唆が、冒頭に書いた原則そのものです。
確率論ベースの生成と決定論ベースの評価系へ、品質責任を分離する。
分離の境界に置くものが、機械検証可能な中間表現になります。

## AIが書いたテストは信用できるのか

テストをゲートにするなら、そのテストが正しくなければ意味がありません。
そしてそのテストは、多くの場合AIが書いています。

### 実装に合わせたテストが書かれる

AIにテストを書かせると、実装を読んで書きます。
実装を読んで書いたテストは、実装の振る舞いを期待値として固定します。
したがって、実装が間違っていれば、テストも間違った期待値を持ちます。
そしてそのテストは通ります。

テストが通ることは、実装が正しいことを意味しません。
実装と期待値が一致していることしか意味しません。
期待値の出所が実装であるなら、この一致は同語反復です。

人間が書く場合も同じ罠はあります。
ただしAIの場合は量が違います。
第1章で見たとおり生成スループットは上がっているので、同語反復のテストが大量に生産されます。
カバレッジは上がり、合否は緑になり、しかし仕様との一致は誰も検証していない、という状態が成立します。

この問題への対処は「AIが書いたテストを人間が全部レビューする」ではありません。
それをやるなら第1章の入口に戻ってしまいます。
別の道が4つあります。

### 対策1 期待値の出所を実装以外に置く

構造的にはこれが本筋です。
期待値を実装から取らせないようにします。
参照先の候補は2つあります。

ひとつは仕様です。
第5章で扱った正常系と異常系のテーブルが、そのまま期待値の一覧になります。
テーブル形式で書く価値がここで回収されます。
入力と期待出力が行として並んでいれば、AIはそれを読んで期待値を埋められます。
散文の仕様では、期待値の抽出自体が推論になるので、結局実装を見に行きます。

もうひとつは、既存の別実装です。
dely社の事例では、Androidの実装に対してiOSの既存実装を参照情報として使ったところ、かなり精度の高い出力が得られたと報告されています。
同じ機能の別プラットフォーム実装は、期待値の独立した出所になります。
移植やリライトの案件では、移行前の実装がこの役割を果たします。
前節の『Airワーク』EOSL対応も、この構造に当てはまります。

いずれの場合も、指示に含めるべき一文は同じです。
期待値は仕様（または参照実装）から取り、対象の実装からは取らないこと。

### 対策2 テストケースの一覧を先に人間が見る

期待値の出所を変えても、網羅の妥当性は残ります。
ここは人間が見ます。
ただし、テストコードを見るのではなく、テストケースの一覧を見ます。

理由は認知コストです。
第6章で触れたfreee社の開発者ブログの論点は、生成物を判断単位に分割して提示することでレビュー可能性を上げるというものでした。
テストコード500行と、テストケース一覧20行は、含んでいる判断の数が同じでも負荷が違います。
一覧なら「異常系が1件しかないのはおかしい」という判断が数秒でできます。
コードでは、同じ判断に到達するまでにアサーションを読み解く必要があります。

前節のYAML仕様書は、まさにこの一覧です。
AIの出口に中間表現を置くと、決定論的な検証点と、人間の低コストなレビュー点が同じ場所に手に入ります。

### 対策3 意図的にコードを壊してテストが落ちるか確認する

ミューテーションテストの発想です。
実装の条件を反転させる、境界値をずらす、戻り値を定数に置き換える。
そのうえでテストを走らせ、落ちるかどうかを見ます。

落ちなければ、そのテストは実装の振る舞いを検証していません。
通っているだけです。
カバレッジは満たしていても、アサーションが実質的に何も主張していないケースはこれで露出します。

全体に常時かけるとコストが高いので、第6章の3軸でクリティカル性の高い領域に限定して適用するのが現実的です。
決済、認可、金額計算。
ここだけでも、テストが空虚かどうかの判定は得られます。

### 対策4 カバレッジは必要条件であって十分条件ではない

カバレッジは、テストが通った行を数えているだけです。
その行の振る舞いが正しいかは何も言っていません。

だからカバレッジ単独をゲートにすると、目的が「数字を満たすこと」に置き換わります。
AIは指示された目的を効率的に達成するので、アサーションのないテストや、通るだけのテストが量産されます。
カバレッジ90%で、実質的な検証がゼロという状態は簡単に作れます。

カバレッジの正しい使い方は、低いことを異常として検出する下限の網です。
上限の品質指標ではありません。
この章の後半のゲート設計では、カバレッジを必須ゲートではなく警告として扱います。

## ゲートを設計する

ここからは、パイプラインを止める条件の設計です。
各ゲートについて「何を保証するか」と同時に「何を保証しないか」を書きます。
保証しない範囲が、そのまま次章の担当範囲になります。

| ゲート | 保証すること | 保証しないこと | 扱い |
| --- | --- | --- | --- |
| 型チェック | 型の整合性、シグネチャの不一致、null安全性 | 型が合っていても意味が正しいか | 必須 |
| lint とフォーマット | 規約準拠、既知のアンチパターン、未使用コード | 設計の妥当性 | 必須 |
| 単体テスト | 明示的に書かれた期待値との一致 | 書かれていないケースの挙動、期待値そのものの正しさ | 必須 |
| カバレッジ | テストが到達した行の範囲 | 到達した行の振る舞いが正しいか | 警告 |
| 依存関係の脆弱性スキャン | 既知のCVEを持つ依存の混入 | 未知の脆弱性、自作コードの脆弱性 | 必須 |
| 破壊的変更の検出 | 公開シグネチャとAPIスキーマの互換性 | 振る舞いの互換性（型は同じで意味が変わる変更） | 必須 |
| マイグレーションの検査 | 危険な操作の混入、ロールバック手順の有無 | 本番データ量での実行時間、ロック時間 | 必須＋人間 |
| 統合テスト | 結合点の疎通、代表シナリオの成立 | 本番のデータ分布、同時実行、負荷 | 必須 |
| 性能と負荷試験 | 代表シナリオでの応答時間の回帰 | 本番の実トラフィックパターン | 対象を限定 |

右の2列が、この表の本体です。
「保証しないこと」の列に書かれているものは、パイプラインでは捕まりません。
捕まらないものをどう扱うかが第11章の主題になります。
ゲートの一覧を作る作業は、同時に「ゲートで守れない範囲」の一覧を作る作業でもあります。

### 3軸に対応させてゲートの厚さを変える

第6章で、クリティカル性、検出可能性、可逆性の3軸を線引きの基準として採用しました。
ゲートの設計にも同じ軸を使います。

原則は、可逆性が低い変更にはゲートを厚くすることです。
戻せる変更は、多少通り抜けても検知して戻せます。
戻せない変更は、通り抜けたら終わりです。
同じリポジトリの中で、パスによってゲートの厳しさを変えます。

| 変更の性質 | 可逆性 | ゲートの厚さ |
| --- | --- | --- |
| 表示、文言、スタイル | 高 | 必須ゲートのみ。カバレッジは警告 |
| 一般のアプリケーションコード | 高 | 必須ゲート＋カバレッジ低下の警告 |
| 公開APIとスキーマ | 低 | 破壊的変更の検出を必須。人間レビューも必須 |
| マイグレーション | 低 | 危険操作の検査＋ロールバック手順の存在確認＋人間レビュー |
| 決済と認可 | 低 | 上記すべて＋ミューテーションテスト＋カバレッジも必須化 |

第6章で作った人間レビュー必須パスの一覧と、この表は対応します。
同じパス定義を、CODEOWNERS とパイプラインの両方から参照する形にします。
片方だけ更新されて乖離するのが典型的な劣化です。

### Hooks と CI の分担を再確認する

第4章で、Claude Code の4つの拡張ポイントのうち Hooks だけが決定論的だと整理しました。
この章の文脈では、Hooks と CI は同じ役割を別の場所で担っています。

| | Hooks | CI |
| --- | --- | --- |
| 実行場所 | ローカル | リモート |
| 速度の要件 | 速くなければならない | 遅くてよい |
| 決定論性 | 決定論的 | 決定論的 |
| AIが結果を見て直せるか | 直せる | 直せない（ループの外） |
| 担当するもの | フォーマット、型チェック、変更範囲の単体テスト | 全テスト、統合テスト、脆弱性スキャン、性能試験 |

分担の基準は速度です。
フィードバックが速いものはローカルに置きます。
AIが自分で結果を見て直せるので、CIに到達する前に消えます。
時間のかかるものはCIに置きます。
第4章で書いたとおり、遅いチェックを `PostToolUse` に入れると開発体験が壊れます。

そして、ローカルにあるからCIから外してよいわけではありません。
Hooks はローカル環境に依存するので、環境差で動かないことがあります。
同じチェックを両方に置き、CIを最終的な合否の根拠にします。

## コード外の制約はゲートで捕まらない

ゲートの限界を正直に書きます。
ここを曖昧にすると、パイプラインが緑であることを安全の証明だと誤解します。

第5章と第6章で見たバッチ処理の失敗例が、この節の根拠になります。

ここで見るべきは、偽陽性がパイプラインを通過したことです。
テストは通っていました。
それでも本番相当の環境で検証するまで、問題は見えませんでした。
単体テストが保証する範囲の外にあったからです。

単体テストで捕まらないものを列挙します。

- **実行時間**：単体テストは1件のデータで通ります。本番で100万件を処理したときに終わるかは分かりません
- **リソース消費**：メモリ使用量、コネクション数、ファイルディスクリプタ。テストでは上限に触れません
- **同時実行時の整合性**：競合状態、デッドロック、ロック待ち。単体テストは直列に走ります
- **データ量に依存する挙動**：N+1クエリ、インデックスが効かないクエリ、ページング境界。少量データでは顕在化しません
- **データ分布に依存する挙動**：想定外のnull、過去に作られた不整合データ、文字コードの混在
- **外部システムとの結合**：モックは自分が書いた想定どおりに振る舞います。実物は違う振る舞いをします
- **冪等性と再実行性**：途中で落ちたジョブを再実行したときに二重計上しないか。テストは正常完了しか通しません
- **上流データの到着タイミング**：前日データが揃う前に走ったときの挙動。時間の依存関係はコードに現れません
- **運用手順との整合**：手動オペレーションと自動処理の順序、切り戻し手順の実行可能性

この一覧には共通の性質があります。
いずれも、判断材料がコードの中にありません。
第6章の分類で「検出困難」に置いたものと同じ集合です。
コードを読んで判断できないものは、コードを読む仕組みでは捕まりません。
静的解析でもテストでも同じです。

だから、本番相当の検証環境が必要になります。
本番に近いデータ量、本番に近い並行度、実物の外部システム。
ここまでやれば、実行時間やデータ量依存の挙動、外部システムとの結合は捕まります。
それでも全部は捕まりません。
本番相当は本番ではないので、トラフィックのパターン、データの偏り、同時に起きる他システムの障害といった再現できないものが残ります。

この残りが、第11章の入口です。
ゲートを厚くし、本番相当で検証しても、通り抜けるものがある。
だから防ぐ努力の隣に、戻す能力を用意する必要があります。

## GitHub Actions で組む

ここまでの設計を実装に落とします。
必須ゲートと警告を分け、変更パスによって厳しさを変える構成です。

まず、変更されたパスを判定して後続ジョブの条件にします。

```yaml
name: quality-gates

on:
  pull_request:

jobs:
  changes:
    runs-on: ubuntu-latest
    outputs:
      critical: ${{ steps.filter.outputs.critical }}
      migration: ${{ steps.filter.outputs.migration }}
      public_api: ${{ steps.filter.outputs.public_api }}
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: filter
        with:
          filters: |
            critical:
              - 'app/services/payment/**'
              - 'app/policies/**'
              - 'app/auth/**'
            migration:
              - 'db/migrate/**'
            public_api:
              - 'api/public/**'
              - 'openapi/**'
```

次に、必須ゲート、警告のみのチェック、パス限定の追加ゲートを並べます。
以下は同じファイルの続きで、環境構築ステップ（`checkout` と `setup-node`、`npm ci`）は各ジョブ共通なので省略しています。

```yaml
  # すべての変更に適用する必須ゲート。落ちたらマージできない
  required:
    runs-on: ubuntu-latest
    steps:
      # 型チェック。型の整合性のみを保証する
      - run: npm run typecheck
      # lint。規約準拠と既知のアンチパターンのみを保証する
      - run: npm run lint -- --max-warnings=0
      # 単体テスト。書かれた期待値との一致のみを保証する
      - run: npm test -- --run
      # 依存の既知脆弱性。未知の脆弱性は保証しない
      - run: npm audit --audit-level=high

  # 警告のみ。落ちてもマージは止めず、PRコメントとして残す。
  # カバレッジを必須ゲートにすると、通るだけのテストが量産される
  advisory:
    runs-on: ubuntu-latest
    continue-on-error: true
    steps:
      - run: npm run test:coverage
      - uses: davelosert/vitest-coverage-report-action@v2
        with:
          json-summary-path: ./coverage/coverage-summary.json

  # 可逆性の低いパスにだけ適用する追加ゲート（第6章の3軸）
  critical-gates:
    needs: changes
    if: needs.changes.outputs.critical == 'true'
    runs-on: ubuntu-latest
    steps:
      # この領域だけはカバレッジも必須ゲートにする
      - run: npm run test:coverage -- --coverage.thresholds.lines=90
      # 意図的にコードを壊してテストが落ちるかを確認する。
      # 生存したミューテーションは「通るだけのテスト」の候補
      - run: npx stryker run --mutate 'app/services/payment/**/*.ts'

  api-compat:
    needs: changes
    if: needs.changes.outputs.public_api == 'true'
    runs-on: ubuntu-latest
    steps:
      # 破壊的変更の検出。型レベルの互換性のみを保証する。
      # 振る舞いの互換性は人間レビューの担当
      - run: npx oasdiff breaking origin/main:openapi/api.yaml openapi/api.yaml

  migration-gates:
    needs: changes
    if: needs.changes.outputs.migration == 'true'
    runs-on: ubuntu-latest
    steps:
      # 危険な操作の混入とロールバック手順の存在を検査する。
      # 本番データ量での実行時間とロック時間は保証しない（第11章）
      - run: ./scripts/check-migration.sh
```

ブランチ保護では `required`、`critical-gates`、`api-compat`、`migration-gates` を必須のステータスチェックに指定し、`advisory` は指定しません。
この指定が、必須と警告の実質的な境界になります。

`check-migration.sh` のような自作スクリプトの中身は、組織のドメイン制約そのものです。
カラム削除を単独のマイグレーションで行っていないか、`NOT NULL` 制約を既存テーブルにデフォルトなしで追加していないか、ダウンマイグレーションが定義されているか。
第4章で明文化した規範のうち、機械的に判定できるものはここに移せます。
CLAUDE.md に書いた「守ってほしいこと」を、パイプラインで「守らせること」に変える作業です。

## AIにパイプラインを直させるときの注意

決定論的なゲートを置くと、次の問題が起きます。
AIがゲートを通そうとします。

「テストを通してください」という指示に対して、最も効率的な解は実装を直すことではありません。
テストを直すことです。
期待値を実際の出力に書き換える、アサーションを緩める、`skip` を付ける。
どれもテストは緑になります。
目的は達成されています。

これは第4章で述べた原則の応用場面です。
AIが判断を誤ると困るものは、決定論的な仕組みへ移す。
ただし「テストを書き換えてはいけない」という判断は、コードの意図に踏み込むので完全には自動判定できません。
したがって、規範として明文化する部分と、仕組みで縛る部分の両方が必要になります。

まず CLAUDE.md への記述です。

```markdown
## テストと静的解析への対応

失敗したチェックに対しては、実装を直してください。
チェックそのものを変更して通すことは、以下のとおり禁止します。

### 禁止（人間の明示的な承認なしに行わない）

- 失敗したテストの期待値を、実装の実際の出力に合わせて書き換える
- アサーションを削除する、または条件を緩める
  （`toEqual` を `toBeDefined` に変える、比較対象を減らす等）
- `skip` / `only` / `xit` / `todo` を付けてテストを実行対象から外す
- lint ルールを無効化するコメント（`eslint-disable` 等）を追加する
- 型エラーを `any` / `as` / `@ts-ignore` / `@ts-expect-error` で回避する
- カバレッジ閾値や lint の設定値を下げる
- CI 設定に `continue-on-error` を追加する、必須ジョブを削除する

### 期待値の扱い

テストの期待値は、仕様（`docs/spec/`）または参照実装から取ってください。
対象の実装を読んで期待値を決めることは禁止します。
実装と期待値が一致していても、仕様と一致している保証がありません。

### テストが失敗したときの手順

1. 失敗の原因が実装にあるか、テストの期待値にあるかを切り分ける
2. 実装にある場合は実装を直す
3. テストの期待値が仕様と食い違っている場合は、修正せずに報告する。
   仕様の解釈が必要な変更は人間が判断する
4. どちらとも判断できない場合は、変更を加えずに状況を報告する

### 報告の義務

チェックを通すために実装以外を変更した場合は、
PR の説明に「変更したチェック」「変更した理由」「代替案を採らなかった理由」
を記載してください。記載のない変更はレビューで差し戻します。
```

手順の4番目が実質的な出口になります。
判断できないときの逃げ道を用意していないと、AIは何らかの解を出そうとします。
そして最も手近な解が、テストの書き換えです。
「変更を加えずに報告する」を正当な終了状態として明示してください。

そして、規範だけでは足りません。
第4章で見たとおり、CLAUDE.md は確率論的です。
守るかどうかが推論に依存します。
守られない数パーセントが事故になるなら、決定論的な仕組みが必要です。

- テストファイルと設定ファイルへの変更を検出して警告するCIジョブを置く
- `skip` の数を数え、増加したら落とす
- `eslint-disable` と `@ts-ignore` の総数を記録し、増加をPRコメントで可視化する
- `.github/workflows/**` と設定ファイル群を CODEOWNERS でオーナー承認必須にする

最後のものが構造的な歯止めになります。
ゲートの定義自体を、ゲートで守ります。
パイプラインを緩める変更が、緩められていないパイプラインとオーナーの承認を通らなければならない構造です。

## ゲートが残す範囲

この章でやったことを整理します。
確率論的な生成に対して決定論的な評価をぶつけ、その境界に機械検証可能な中間表現を置きました。
AIが書いたテストの信頼性については、期待値の出所を実装の外に置く、一覧を人間が見る、意図的に壊して確認する、カバレッジを十分条件と誤解しない、という4つの対処を用意しました。
そしてゲートの一覧を、保証することと保証しないことの対で定義しました。

この「保証しないこと」の列が残っています。
実行時間、同時実行時の整合性、データ量に依存する挙動、冪等性。
判断材料がコードの外にあるものは、コードを読む仕組みでは捕まりません。
本番相当の検証環境を用意しても、本番そのものではないので、残りが出ます。
ここでゲートをさらに厚くする方向に進むと、投資に対する見返りが急速に落ちます。
捕まらないものの性質が、厚さでは解決しないからです。

だから発想を変えます。
第11章では、防ぐから戻せるへ、という転換を扱います。
障害をゼロにする前提を捨て、起きたときにどれだけ速く戻せるかを設計対象にします。
ゲートで守れなかった範囲を、そこで受けます。

## この章のまとめ

- 生成もAIレビューも確率論的です。確率論的な工程を重ねても確率論的なままなので、品質保証の連鎖に決定論的な評価を1枚入れる必要があります。リクルート社の黒田氏の資料が示す原則は、確率論ベースの生成と決定論ベースの評価系へ品質責任を分離することです
- 『Airワーク』EOSL対応の事例では、AIに生成と検証の両方を任せた初期構成がラルフループに陥り、数日で数百万円のトークン代を消費しました。改善後はAIを観点出しとYAML仕様書の生成のみに限定し、テストコードの生成をプログラムが行い、評価をテスト実行とカバレッジで決定論化しています。境界に機械検証可能な中間表現を置く形は、第4章のZOZO社の中間ファイル戦略と同じ構造です
- テストが通ることは、実装と期待値が一致していることしか意味しません。期待値の出所を実装の外（第5章の仕様テーブル、dely社の事例のような既存の別実装）に置き、テストケースの一覧を人間が見て、クリティカルな領域では意図的にコードを壊して確認します。カバレッジは必要条件にすぎず、単独でゲートにすると通るだけのテストが量産されます
- ゲートは「何を保証するか」と「何を保証しないか」を対で定義します。可逆性が低いパスにはゲートを厚くし、速いチェックは Hooks に、遅いチェックは CI に置きます。ゲートの一覧を作る作業は、ゲートで守れない範囲の一覧を作る作業でもあります
- コード外の現実制約はゲートで捕まりません。本番相当の検証環境でも残りが出るため、第11章の回復性が必要になります
