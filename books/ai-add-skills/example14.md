第12章までに、仕組みを7つか8つ作りました。
CLAUDE.md の書き分け、仕様テンプレート、レビュースキル、承認ワークフロー、テストゲート、フィーチャーフラグ、劣化の検知表。
それぞれは独立して動きます。

全部を足したものには、まだ名前がありません。

名前がないと困ることが3つあります。
予算が付きません。
担当が決まりません。
そして、効いているかどうかを議論する土台がありません。

この総体を指す言葉として、**ハーネスエンジニアリング**という呼び方が使われはじめています[^harness]。
創業半年のスタートアップで1人でプロダクト開発を担った開発者が、この領域にどう向き合ったかを整理した登壇資料があり、そこに扱いやすい枠組みが示されています。

[^harness]: harness は馬具、あるいは装置を装着して制御することを指します。ソフトウェアの文脈では、テスト対象を動かすための足場を指す「テストハーネス」の用法が先にありました。

## ハーネスという括り

定義は揺れています。
あるフレームワークの提供元は「モデルでなければハーネス」と呼び、モデルの提供元は「ツールコールをルーティングする制御ループ」と定義しています。
前者は極端に広く、後者は極端に狭い。
提供者側が設計するもの（エージェントハーネス）と、利用者側が設計するもの（ユーザーハーネス）でスコープが違うことも、揺れの原因として挙げられています。

登壇資料は、広いほうの捉え方を採っています。
モデルの外側は全部ハーネスの範囲だと考えると、ワークフロー、パイプライン、評価、組織、顧客接点まで発想が広がる、という理由です。
広すぎて全部がハーネスになってしまう、という留保も同じ資料に付いています。

留保は妥当です。
ただ、本書の読者にとっては広いほうが実用的です。
本書が扱ってきたものは、第4章の CLAUDE.md から第12章の計測まで、すべてモデルの外側にあります。
モデルそのものには手を入れていません。
つまり本書は、最初から最後までハーネスの本でした。

### 利用者側から見た構成要素

利用者側のスコープとして、登壇資料は記憶と文脈、そして品質と安全を挙げ、具体物として system prompt、CLAUDE.md、skills、tools、orchestration、hooks、observability を並べています。

そして達成したいことを「エージェントが動く環境とシステムの設計」と定義し、3つの機能に分けています。

| 機能 | 内容 | 例として挙げられているもの |
| --- | --- | --- |
| 行動を制約する | 何をどう作るかを定め、解空間を絞る | CLAUDE.md、スキル定義、ワークフロー、spec.md |
| 正しいか確かめる | 検証し、問題があれば差し戻す | 静的チェック、ブラウザテスト、探索的テスト、AIレビュー |
| 次をもっと良くする | 学びを蓄積する | Self-Refinement、メモリ、実行ログ分析、ハーネスの自動修正、パターンDB |

「事前の予防と事後の検証を設計する」という言い方も同じ資料にあります。
テストは事後の検出だけを担い、ハーネスは事前の予防と失敗からの学習まで含む、という区別です。

この3機能に本書の各章を並べると、抜けている場所が見えます。

| 機能 | 本書で対応する章 |
| --- | --- |
| 行動を制約する | 第3章（作らない判断）、第4章（規範の明文化）、第5章（仕様と粒度） |
| 正しいか確かめる | 第6章（線引き）、第7章（レビュースキル）、第10章（テストゲート） |
| 次をもっと良くする | 第8章（自己改善サイクル）、第9章（週次ワークフロー）、第12章（劣化の検知と計測） |

第11章の可逆性と復旧は、3機能のどこにも入りません。
事前の予防でも事後の検証でも学習でもなく、防ぎきれなかった後の話です。
枠組みに入らないものが残るのは、枠組みが間違っているからではありません。
ハーネスの範囲がリポジトリの中で終わっていて、本番が範囲外だからです。

### 3つの難しさ

同じ資料は、この領域の難しさを3つに整理しています。
どれも本書が作ってきた仕組みに直接効くので、そのまま引きます。

**何をすべきか分からない**。
定義もスコープも揃っていないので、着手点が決まりません。
本書の12章は着手点の一覧として読めますが、順番の根拠は「自分のチームで最も詰まっている場所」という判断に委ねてあります。

**効いているか分からない**。
「このハーネスは効いている」と言い切るための物差しまでは無いことが多い、という指摘です。
そして、ルールファイルの整備でも同じことが起きた、と続きます。
定量的で実験的で継続的な改善活動を回すのが手探りな状態、という表現です。
第12章で計測を扱いましたが、あそこで測ったのはレビュー観点の採用率とコストでした。
仕組み全体が効いているかは測っていません。

**いつ消えるか分からない**。
モデルの進化で不要になる制御や処理があり、マネージドなエージェント実行環境の登場によって、自分で組んだ部分が丸ごと要らなくなる可能性もあります。

3つ目が、本書にまだ答えのない問いです。
第12章で扱った劣化は「仕組みが現状に追いつけていない」種類の劣化でした。
ここで言われているのは、仕組みそのものが不要になる種類の陳腐化です。
検知しても直しようがありません。

## 消えないレイヤーに投資する

不要になるかもしれないものに、どこまで時間を使えばよいのでしょうか。

登壇資料の答えは、今後の向き合い方として2行で書かれています。
モデルやマネージドサービスの進化によって消えづらいレイヤーに投資する。
LLMプロバイダーを切り替えても同様に利用可能な仕組みを中心にする。

後半が判定に使えます。
モデルを別のプロバイダーに差し替えたとき、書き直しになるかどうか。
書き直しになるものは消えやすく、そのまま使えるものは消えにくい。

本書で作った仕組みを、この基準で分類します。

| 仕組み | プロバイダー変更時 | 消えやすさ |
| --- | --- | --- |
| プロンプトの言い回しの工夫 | 書き直し | 高 |
| 特定モデルの癖に対する回避策 | 不要になる | 高 |
| 出力フォーマットを整えるための指示 | 書き直しの可能性 | 中 |
| CLAUDE.md の細則 | 一部書き直し | 中 |
| Hooks の禁止操作リスト | そのまま使える | 低 |
| レビュー観点（自チームの失敗に由来） | そのまま使える | 低 |
| 仕様テンプレートと根拠表 | そのまま使える | 低 |
| テストゲートとCI | そのまま使える | 低 |
| 線引きと承認プロセス | そのまま使える | 低 |
| 実行ログと評価の基盤 | そのまま使える | 低 |

並べると、消えにくいものの共通点が出ます。
根拠が自分たちの側にあるものです。
自チームが踏んだ失敗、自チームが決めた線引き、自組織の合意、自プロダクトの制約。
モデルが変わっても、これらは変わりません。

消えやすいものの共通点も同じ構造で、根拠がモデルの側にあります。
「このモデルはこう書くと従いやすい」は、モデルが変われば無効になります。

### 消えやすいものを書かない、ではない

分類の使い道を間違えると、動けなくなります。
消えやすいものを書かない運用にすると、目の前の出力が改善しません。
言い回しの工夫は、今週の生成物の質を上げます。

分けるのは、置き場所と期限です。
第11章でフィーチャーフラグに削除期限を宣言して入れたのと同じ扱いにします。

```markdown
## ハーネス台帳

| # | 仕組み | 置き場所 | 消えやすさ | 見直し期限 | 消えたと判断する条件 |
| --- | --- | --- | --- | --- | --- |
| 1 | 出力を必ず表形式にする指示 | `.claude/skills/review/SKILL.md` | 高 | 2026-06-30 | 指示なしでも表で出るようになった |
| 2 | 長い差分を分割して渡す前処理 | `scripts/split_diff.py` | 高 | 2026-06-30 | コンテキスト長の制約が実務上消えた |
| 3 | 不可逆操作の禁止リスト | `.claude/settings.json` | 低 | 期限なし | - |
| 4 | 観点: N+1 クエリの検出 | `.claude/skills/review/SKILL.md` | 低 | 期限なし | - |
| 5 | 仕様テンプレート | `.github/ISSUE_TEMPLATE/spec.md` | 低 | 期限なし | - |
```

消えやすさが「高」の行にだけ期限を入れます。
期限が来たら、その仕組みを一度外して同じ入力を流し、出力が変わるかを見ます。
変わらなければ削除します。
変わるなら期限を延ばします。

「消えたと判断する条件」を書いておくのが要点です。
条件を書かずに期限だけ置くと、期限が来たときに判断できず、延長だけが繰り返されます。
第12章で「検知方法の列が埋まっていない行は、劣化しても誰も気づかない行」と書いたのと同じ形です。

台帳そのものも劣化します。
第12章の劣化の表に、ハーネス台帳の行を1つ足しておく必要があります。

## 個人の工夫を、誰が起動しても同じプロセスに

登壇資料の中で、いちばん耳が痛い問いはこれです。

> Claude Code / Codex を配り、ルールファイルを整備すればAIネイティブな開発か？

答えは、少なくともプロダクト組織とプロセス全体では No、と書かれています。
理由は「個人がどれだけうまく使えるか」に閉じてしまいがちだから、という指摘です。
ルールやスキルの整備が個人の感性による「俺の考える最強のX」に留まっていないか、という言い方もされています。

本書はこの罠に片足を入れています。
第4章で規範を明文化し、第7章でレビュースキルを組み、第8章で自己改善サイクルを作りました。
どれもリポジトリに置く前提で書いたので、個人の設定には留まりません。
一方で、実行は各自の手元です。
誰がいつどのスキルを起動するかは、その人の判断に任されています。

任されている部分に、熟練度の差が乗ります。
同じリポジトリで同じ CLAUDE.md を読ませても、指示の出し方が違えば結果が違う。
第14章で扱う言語化の精度の話は、この差の中身です。

### パイプラインをコードにする

登壇資料の実践のひとつは、開発プロセス全体をスクリプトにしたことです。
Claude Agent SDK と TypeScript で、人間が Claude Code や Codex で行っている開発プロセスをそのまま型にしています。
仕様からブラウザテストとスクリーンショット付きのPR作成までを、1本のスクリプトで通す構成です。

コードにする利点として、3つが挙げられています。

| 利点 | 内容 |
| --- | --- |
| 再現性と属人性の排除 | 誰が起動しても同じプロセスが走り、個人の熟練度に依存しなくなる |
| 品質保証の組み込み | ブラウザテストと証跡のスクリーンショットまで終わった状態でPRが出る。不良な仕様を早期に弾き、別モデルによるクロスレビューで検証する |
| 計測と改善の基盤 | スクリプトの中で全実行のログが取れる。設計判断やインシデント履歴の永続化も組み込みやすい |

3つ目が「効いているか分からない」への足場になります。
手元で対話している限り、何をどう変えたら何が良くなったのかは記録に残りません。
プロセスがスクリプトなら、入力と出力とログが揃います。

### 決定論と確率論を交互に置く

構成の呼び方として、資料は「ハイブリッドオーケストレーション」を使っています。
決定論的なステップと、エージェントの自由に任せるステップを交互に配置する形です。
決定論的なステップの例として lint とブランチへの push、エージェント側の例として実装と CI の修正が挙げられています。

第10章でも決定論と確率論を分けましたが、あそこでの配置は直列でした。
生成が終わったらゲートを通す、という順番です。
交互に置くというのは、生成の途中に何度も決定論を挟むという意味になります。

違いは、失敗が分かるまでの距離です。
最後にまとめてゲートを通すと、落ちたときに原因の候補が全工程に散ります。
段ごとに挟めば、落ちた段が原因の段です。

段の設計例を書きます。

| 段 | 種別 | 内容 | 落ちたときの扱い |
| --- | --- | --- | --- |
| 1 | 決定論 | 仕様テンプレートの必須欄が埋まっているかを検査する | 中断。仕様の作成者へ差し戻す |
| 2 | 確率論 | 仕様から実装計画を作る | 3回まで再試行 |
| 3 | 決定論 | 計画がPhaseに分割され、各Phaseに検証手順があるかを検査する | 段2へ戻す |
| 4 | 確率論 | Phase単位で実装する | Phase単位で再試行 |
| 5 | 決定論 | lint、型チェック、単体テストを実行する | 段4へ戻す（最大2回） |
| 6 | 確率論 | 落ちたテストとlintを修正する | 段5へ戻す |
| 7 | 決定論 | ブラウザテストを実行し、スクリーンショットを保存する | 中断。人間へ |
| 8 | 確率論 | 別モデルでレビューする | 指摘があれば段6へ |
| 9 | 決定論 | ブランチをpushし、証跡を添えてPRを作る | 中断 |

段1が最初に来ているのが実務上いちばん効きます。
不良な仕様を早期に弾く、という表現が資料にありますが、弾かずに段2へ進めると、以降の全段が無駄になります。
第5章で仕様テンプレートに「コード外制約は該当なしと明記する」という規則を入れたのは、この段1を機械的に判定可能にするためでもあります。

再試行の回数に上限を置くのも要点です。
上限がないと、段5と段6の間で往復し続けます。
第10章で触れたラルフループが、ここで発生します。

疑似コードにすると、構造は単純です。

```typescript
// scripts/pipeline.ts
import { query } from "@anthropic-ai/claude-agent-sdk"
import { execSync } from "node:child_process"

type Result = { ok: boolean; detail: string }

// 決定論の段。プログラムが判定する
function gate(name: string, cmd: string): Result {
  try {
    const out = execSync(cmd, { encoding: "utf8" })
    return { ok: true, detail: out }
  } catch (e: any) {
    return { ok: false, detail: String(e.stdout ?? e.message) }
  }
}

// 確率論の段。エージェントに任せる
async function agentStep(prompt: string): Promise<string> {
  let text = ""
  for await (const msg of query({ prompt })) {
    if (msg.type === "assistant") text += msg.text ?? ""
  }
  return text
}

async function run(specPath: string) {
  // 段1: 仕様の必須欄チェック（落ちたら進めない）
  const spec = gate("spec", `python scripts/check_spec.py ${specPath}`)
  if (!spec.ok) throw new Error(`不良な仕様: ${spec.detail}`)

  // 段2-3: 計画の生成と検査
  await agentStep(`${specPath} を読み、Phase分割した実装計画を .tmp/plan.md に書く`)
  const plan = gate("plan", "python scripts/check_plan.py .tmp/plan.md")
  if (!plan.ok) throw new Error(`計画が要件を満たさない: ${plan.detail}`)

  // 段4-6: 実装と自動修正。回数上限を必ず置く
  await agentStep(".tmp/plan.md の Phase 1 から順に実装する")
  for (let i = 0; i < 2; i++) {
    const checks = gate("checks", "npm run lint && npm run typecheck && npm test")
    if (checks.ok) break
    await agentStep(`次の失敗を修正する。実装方針は変えない\n${checks.detail}`)
  }

  // 段7: ブラウザテストと証跡。ここで落ちたら人間へ
  const e2e = gate("e2e", "npm run test:e2e -- --screenshot=on")
  if (!e2e.ok) throw new Error(`ブラウザテスト失敗: ${e2e.detail}`)

  // 段8-9: クロスレビューとPR作成
  await agentStep("差分を別モデルでレビューし、指摘があれば修正する")
  gate("pr", "bash scripts/open_pr.sh")
}
```

`gate` と `agentStep` の2種類しか出てこないのが、この構成の要点です。
どちらで実装するかを段ごとに決めれば、パイプラインは組めます。
第10章で「品質保証の連鎖に決定論的な評価を1枚入れる」と書きましたが、1枚ではなく交互に入れる形がこれです。

### コマンド1本で起動できる形にする

パイプラインがスクリプトなら、起動元を選びません。
登壇資料では npx コマンドで起動する形にしてあり、そのため GitHub Actions から Issue をトリガーにするのも容易だと述べられています。
Issue から一定の品質が担保された PR までが実現可能、という報告です。

```yaml
# .github/workflows/pipeline-from-issue.yml
name: Run pipeline from issue

on:
  issues:
    types: [labeled]

jobs:
  run:
    if: github.event.label.name == 'agent-ready'
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - run: npm ci

      # Issue 本文を仕様ファイルとして書き出す
      - name: Write spec
        env:
          BODY: ${{ github.event.issue.body }}
        run: |
          mkdir -p .tmp
          printf '%s' "$BODY" > .tmp/spec.md

      - name: Run pipeline
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: npx tsx scripts/pipeline.ts .tmp/spec.md

      # 段1で落ちた場合も、理由を Issue に返す
      - name: Report failure
        if: failure()
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          gh issue comment ${{ github.event.issue.number }} \
            --body "パイプラインが中断しました。ログを確認してください。"
          gh issue edit ${{ github.event.issue.number }} \
            --remove-label agent-ready
```

`agent-ready` ラベルを起動条件にしているのは、Issue が立った瞬間には仕様が揃っていないからです。
ラベルを付ける行為が、第9章で扱った承認と同じ役割を持ちます。
失敗時にラベルを外すのも同じ理由で、外さないと編集のたびに再実行が走ります。

## 入口を増やす前に決めること

パイプラインができたら、次は起動する導線を増やす。
登壇資料はそう進み、エンジニア以外でも、ターミナル以外からも開発をトリガーできるようにしたと報告しています。

実例として、画面上でピン留めとテキスト入力ができる Chrome 拡張が挙げられています。
画面で指した内容がそのままパイプラインに流れ、PR が作られる形です。
一般的なハーネスエンジニアリングに含めるかは議論がある、という留保付きで、「エージェントが動く環境の設計」として取り組んでいると説明されています。
自社プロダクトの中でAIが顧客からヒアリングした結果を、そのまま開発に回す試みにも触れられています。

入口が増えると、起案の量が増えます。
第9章で、自動更新の量が増えるほど承認の質が全体の品質を決めると書きました。
同じことが、入口の拡張でも起きます。

しかも入口ごとに、起案者の前提知識が違います。
ターミナルから起動するエンジニアは仕様の書き方を知っています。
画面から指す人は知りません。
知らない人の起案を同じパイプラインに流すと、段1の仕様チェックで大量に落ちます。

落ちること自体は正しい動作です。
問題は、落ちた理由が起案者に伝わらないことです。

### 入口ごとにゲートを固定する

| 入口 | 起案者 | 入力の形 | 通すゲート | 承認 |
| --- | --- | --- | --- | --- |
| ターミナル | エンジニア | 仕様ファイル | 全段 | 不要（本人が見る） |
| Issue + ラベル | エンジニア、PM | Issue本文 | 全段 | ラベル付与が承認 |
| 画面のアノテーション | 誰でも | 座標とテキスト | 段1の前に仕様化の段を追加 | エンジニアがラベルを付ける |
| 顧客からのヒアリング結果 | 顧客（間接） | 会話ログ | 仕様化と、要否判断の段を追加 | プロダクト側の判断が必須 |

下2行に段が増えているのが要点です。
入力が仕様の形をしていない入口では、仕様に変換する段を先に置きます。
変換した仕様を起案者に見せて確認を取る形にすれば、段1で落ちたときの理由も伝わります。

いちばん下の行には、要否の判断を入れています。
第3章で扱った「作らない判断」です。
顧客の要望をそのまま開発に流す導線は、作らない判断を飛ばす導線にもなります。
資料でもこの試みは基本的にドッグフーディング目的と説明されており、そのまま本番の開発フローに繋ぐものとしては提示されていません。

入口を増やす前に決めることは、1文にまとめられます。
この入口から入ったものを、誰が「作らない」と言えるか。

## 効いているかを測る

「効いているか分からない」への答えとして、登壇資料は評価基盤にログを送る構成を挙げています。
評価用のSaaSに実行ログを送り、分析と改善を回す仕組みを作っている、という報告です。
追跡している内容として、どの類のタスクがどの程度の成功率か、そして人間から追加介入なしでマージされているかが挙げられています。

2つ目が、本書に無かった指標です。
第12章で扱った Actioned と Engaged は、レビュー観点1つ1つの有効性を測る指標でした。
「人間の追加介入なしでマージされた割合」は、パイプライン全体の有効性を測る指標です。
粒度が違うので、両方必要になります。

### 実行を1行ずつ記録する

パイプラインがスクリプトなら、記録は難しくありません。
段の入口と出口で1行ずつ書きます。

```sql
-- ローカルの SQLite でも、共有DBでも同じ形で使える
CREATE TABLE IF NOT EXISTS pipeline_run (
  run_id        TEXT PRIMARY KEY,
  started_at    TEXT NOT NULL,
  finished_at   TEXT,
  trigger       TEXT NOT NULL,   -- terminal | issue | annotator | hearing
  task_kind     TEXT NOT NULL,   -- bugfix | ui | schema | infra | copy
  outcome       TEXT,            -- merged | abandoned | running
  human_edits   INTEGER,         -- マージ前に人間が加えた変更の数
  retries       INTEGER,         -- 段の再試行の合計回数
  failed_stage  TEXT,            -- 中断した段の名前。完走なら NULL
  cost_usd      REAL
);

CREATE TABLE IF NOT EXISTS pipeline_stage (
  run_id     TEXT NOT NULL,
  stage      TEXT NOT NULL,
  kind       TEXT NOT NULL,   -- deterministic | agent
  ok         INTEGER NOT NULL,
  attempt    INTEGER NOT NULL,
  detail     TEXT,
  PRIMARY KEY (run_id, stage, attempt)
);
```

`human_edits` を数える列を置いているのが要点です。
マージされたかどうかだけでは、パイプラインが仕事をしたのか人間が直したのかが区別できません。

この2つのテーブルから、4つの数字が出ます。

```sql
-- 1. タスク種別ごとの完走率
SELECT task_kind,
       COUNT(*) AS runs,
       SUM(outcome = 'merged') AS merged,
       ROUND(1.0 * SUM(outcome = 'merged') / COUNT(*), 2) AS rate
FROM pipeline_run
WHERE started_at >= date('now', '-28 day')
GROUP BY task_kind
ORDER BY runs DESC;

-- 2. 人間の介入なしでマージされた割合
SELECT ROUND(1.0 * SUM(human_edits = 0) / COUNT(*), 2) AS untouched_rate
FROM pipeline_run
WHERE outcome = 'merged' AND started_at >= date('now', '-28 day');

-- 3. どの段でいちばん落ちているか
SELECT failed_stage, COUNT(*) AS n
FROM pipeline_run
WHERE outcome = 'abandoned' AND started_at >= date('now', '-28 day')
GROUP BY failed_stage
ORDER BY n DESC;

-- 4. 再試行が多い段（確率論の段の不安定さ）
SELECT stage, AVG(attempt) AS avg_attempt, COUNT(*) AS n
FROM pipeline_stage
WHERE kind = 'agent'
GROUP BY stage
ORDER BY avg_attempt DESC;
```

1と2は経営に説明する数字です。
3と4は、次に何を直すかを決める数字です。

3が示すのは、パイプラインのどこが現実に合っていないかです。
段1で落ちる件数が多ければ、仕様テンプレートが厳しすぎるか、起案側に伝わっていません。
段7で落ちる件数が多ければ、ブラウザテストが不安定か、実装が画面まで届いていません。

4が示すのは、エージェントに任せた段のうち、任せきれていない段です。
平均試行回数が2を超える段は、指示が足りていないか、その段の粒度が大きすぎます。
第5章の粒度の議論を、パイプラインの段に適用する形になります。

### 変更を1つずつ入れる

数字が取れるようになったら、ハーネスの変更を実験として扱えます。
登壇資料は、その修正が何にどう、どの程度Hitするのかを分かることの重要性を挙げています。

実験として扱うには、1回に1つしか変えないという制約が必要です。

```markdown
## ハーネス変更の記録

| 日付 | 変更した箇所 | 変えた理由 | 見る指標 | 判定日 | 結果 |
| --- | --- | --- | --- | --- | --- |
| 2026-05-07 | 段3の計画チェックに「Phaseごとの検証手順」を必須化 | 段5の再試行が平均2.4回 | 段5の平均試行回数 | 2026-05-21 | 2.4 → 1.6 |
| 2026-05-21 | 段8のクロスレビューを追加 | 人間の介入なしマージ率が0.31 | untouched_rate | 2026-06-04 | 0.31 → 0.38 |
```

2週間の判定期間を置いているのは、週次の件数が少ないと差が出ないからです。
チームの流量が少なければ、判定は4週間になります。
判定日を先に書いておくと、都合のよいタイミングで結果を読む余地が減ります。

同時に3つ変えたときは、どれが効いたか分からないままになります。
分からないまま全部残すと、消えやすいレイヤーの仕組みが積み上がります。

## 失敗を蓄積する

3つ目の機能が「次をもっと良くする」でした。
登壇資料の実践は2つあります。

ひとつは、ルールファイルの整合性確認と修正を自動化することです。
同じ Claude Agent SDK でスクリプトを書き、ツールとして自動実行する形にしてあります。
第8章で作った自己改善スキルは、レビュー観点を対象にしていました。
ここで対象になっているのはルールファイル自身です。

もうひとつが、エラー履歴のメモリ化です。
自動ブラウザテストを回しているので、「Xを編集したら、Yでエラーが出た」という履歴が取れる。
それをローカルの SQLite にエージェントから格納している、と報告されています。
資料自身が「workするかは定かではない」と留保を付けています。

留保が付いているものを本書に載せるのは、着想の形が使えるからです。
第8章の自己改善サイクルは、修正PRという教師データを使いました。
教師データとして使えるものが、修正PRの他にもあるという指摘になります。

### 編集と失敗の対応を残す

```sql
CREATE TABLE IF NOT EXISTS edit_failure (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  observed_at  TEXT NOT NULL,
  edited_path  TEXT NOT NULL,   -- 編集したファイル
  failed_at    TEXT NOT NULL,   -- 失敗が出た場所（テスト名、画面、エンドポイント）
  failure_kind TEXT NOT NULL,   -- e2e | unit | type | runtime
  message      TEXT,
  run_id       TEXT
);

CREATE INDEX IF NOT EXISTS idx_edit_failure_path ON edit_failure(edited_path);
```

貯めるだけでは効きません。
使う場所を決めます。

パイプラインの段2、実装計画を作る前に、これから触る予定のファイルで過去に起きた失敗を引いて、計画のコンテキストに入れます。

```bash
# これから触るファイルで過去に起きた失敗を引く
sqlite3 -header .harness/memory.db "
  SELECT edited_path, failed_at, failure_kind, COUNT(*) AS n
  FROM edit_failure
  WHERE edited_path IN ('src/checkout/total.ts', 'src/checkout/view.tsx')
  GROUP BY edited_path, failed_at, failure_kind
  HAVING n >= 2
  ORDER BY n DESC
  LIMIT 10
"
```

`HAVING n >= 2` を入れているのが要点です。
1回だけ起きた失敗は偶然を含みます。
2回以上同じ組み合わせで起きているものだけを渡せば、ノイズが減ります。

第4章で「同じ説明を2回したら、3回目の前に書く」という規則を置きました。
同じ閾値を、人間の気づきではなく実行ログに適用した形になります。

### ハーネス自身を自動で直せるか

登壇資料は、開発パイプライン自体の改善は基本的に人間とエージェントの協働で頑張っている、と述べています。
自動化しているのはルールファイルの整合性確認までで、パイプラインの構造は人間が触っています。

研究段階の方向として、LLM自身が制約を発見してハーネスを生成し改善する取り組みにも触れられています。
現時点で実務に持ち込む段階ではありません。

第8章で自己改善スキルに人間の承認を残した理由が、ここで補強されます。
観点の追加は承認を挟めば安全に自動化できますが、パイプラインの構造変更は影響範囲が違います。
段を1つ削ると、その段が守っていたものが全部通ります。

そして登壇資料は、最後にこう置いています。
エージェントのログを読み、失敗を分析し、仕組みに還元すること自体が、重要なエンジニアリングスキルである。

第12章までの本書は、還元先の仕組みを作る話でした。
ログを読む部分は、担当を決めていませんでした。

## アンチパターン

### ハーネスを増やすことを成果にする

スキルが何個、Hooks が何本、という数え方を成果指標にすると、消えやすいレイヤーの仕組みが積み上がります。
第12章で PR 数を目標にすると「作らない判断」と衝突すると書いたのと同じ構造です。
数えるなら、台帳のうち期限切れになっていない行の割合を数えます。

### 評価基盤より先にダッシュボードを作る

見た目のあるものから作りたくなります。
記録が2週間分しか無い状態でダッシュボードを作ると、読める差が出ないので誰も見なくなります。
先に記録を始め、4週間貯まってから集計します。
上に挙げた4つのクエリは、ダッシュボードが無くても手で叩けます。

### パイプラインを組む前にトリガーを増やす

画面から起動できる導線は魅力的です。
ただ、流れ込む先のパイプラインが整っていないと、仕様の形をしていない起案が大量に届くだけになります。
入口の拡張は、段1の仕様チェックが安定してからです。

### 交互に置いたはずのゲートが全部末尾にある

段を交互に配置したつもりで、実際には確率論の段が連続していて、決定論の段が末尾に集まっている構成になりがちです。
判定は簡単で、上記の `pipeline_stage` テーブルで `kind` の並びを見ます。
`agent` が3つ以上連続している箇所は、失敗の原因が特定できない区間です。

### 個人の設定を配って終わりにする

いちばん多いのがこれです。
自分の `~/.claude/` の中身を共有して、あとは各自でどうぞ、という形にすると、熟練度の差がそのまま成果の差になります。
リポジトリに置く、スクリプトにする、コマンド1本で起動できるようにする、の3つが揃って初めて属人性が抜けます。

## この章のまとめ

- 本書が第4章から第12章まで作ってきたものは、すべてモデルの外側にあります。この総体を指す言葉として「モデルでなければハーネス」という広い捉え方を採ると、ワークフロー、パイプライン、評価、組織、顧客接点まで同じ設計対象として扱えます
- ハーネスの機能は3つです。行動を制約する（第3章から第5章）、正しいか確かめる（第6章、第7章、第10章）、次をもっと良くする（第8章、第9章、第12章）。第11章の可逆性はこの3つに入りません。ハーネスの範囲がリポジトリの中で終わっているためです
- 難しさは3つで、何をすべきか分からない、効いているか分からない、いつ消えるか分からない。3つ目は第12章の劣化の検知では捕まえられません。仕組みが現状に追いつけない劣化ではなく、仕組みが不要になる陳腐化だからです
- 対処は「消えづらいレイヤーに投資する」です。判定は1文で足ります。モデルを別のプロバイダーに差し替えたとき、書き直しになるか。書き直しになるものには置き場所を分けて期限を付け、「消えたと判断する条件」を台帳に書きます
- ルールファイルを整備して各自に配る形は、個人がどれだけうまく使えるかに閉じます。パイプラインをスクリプトにすると、再現性と属人性の排除、品質保証の組み込み、計測と改善の基盤の3つが同時に手に入ります
- 決定論の段と確率論の段は、直列に並べるのではなく交互に置きます。落ちた段が原因の段になるので、原因の特定が段の粒度まで絞れます。確率論の段には必ず再試行の上限を付けます
- 入口を増やすと起案の量が増えます。入口ごとに通すゲートを固定し、入力が仕様の形をしていない入口には仕様化の段を先に足します。決めるべきことは1つで、この入口から入ったものを誰が「作らない」と言えるか
- パイプライン全体の有効性は「人間の追加介入なしでマージされた割合」で測ります。第12章の Actioned と Engaged は観点1つ1つの指標で、粒度が違うため両方必要です。ハーネスの変更は1回に1つだけ入れ、判定日を先に決めます
- 教師データは修正PRだけではありません。「Xを編集したらYで失敗した」の対応を記録し、2回以上繰り返した組み合わせだけを次の計画に渡します。ただしパイプラインの構造変更は自動化せず、人間が触る側に残します
