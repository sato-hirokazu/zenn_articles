## 毎回同じ指摘をしているなら、それは規範が書かれていない

レビューコメントを一週間分ためて眺めてみてください。同じ内容が繰り返し出てきていないでしょうか。次のようなコメントです。

- 「このディレクトリに新しいファイルを置かないでください」
- 「ここは既存のユーティリティを使ってください」
- 「エラーは握りつぶさずに上位へ伝播させてください」
- 「マイグレーションは別 PR に分けてください」

これらはレビューで指摘するべきことでしょうか。指摘して直ってはいるので、レビューは機能しています。しかし、同じ指摘が毎回発生しているという事実は別のことを意味しています。そのルールがどこにも書かれていない、ということです。

第 2 章で、コードレビューが兼ねていた 4 つの役割を分解しました。そのうちの一つ「変更容易性の維持」は、本来なら生成される前に効かせられる種類の役割です。命名規則、ディレクトリ構成、依存の方向、使ってよいライブラリ。これらは変更後に指摘するのではなく、変更前に伝えておけば済みます。人間相手だとこれは難しい話でした。ドキュメントを書いても読まれないからです。ところが AI コーディングエージェントは、渡したものを毎回読みます。読まないという問題が消えた代わりに、「渡していないものは知らない」という問題だけが残りました。だから明文化が効きます。

この章は、暗黙知を外部化して生成段階に効かせるための土台です。Claude Code が持つ 4 つの拡張ポイント（CLAUDE.md / Skills / Subagents / Hooks）を、それぞれの向き不向きと書き分けの基準とともに整理します。

## 操作できるレバーは 2 つしかない

リクルートの黒田氏の資料では、AI に安定して仕事をさせるために操作できるレバーは 2 つだと整理されています。

1. 必要なコンテキストを減らす（境界設計、分割）
2. 与えるコンテキストを増やす（Skills、カスタムエージェント、一般論での拘束）

同資料の『Airワーク採用管理』の事例では、ベテランの暗黙知を Skills・カスタムエージェント・パイプラインへ外部化したことが報告されています。加えて興味深いのは、アーキテクチャ側の記述です。UI / BFF / API が独立しており、冗長ではあるが疎結合な構造になっていたことで、「一つの変更に必要なコンテキストが小さく、推論が安定した」とされています。

つまり、良い設計は AI に対しても効くということです。密結合なコードベースでは一箇所を変えるために広い範囲を理解する必要があり、人間もエージェントも同じように苦労します。ただし 1 つ目のレバーは、この章の範囲を超えてアーキテクチャの話になります。

この章が扱うのは 2 つ目のレバーです。ただし「与えるコンテキストを増やす」を素朴にやると失敗します。全部を CLAUDE.md に書けば、常時コンテキストを食い潰して肝心の作業に使える余地が減ります。増やす対象と、増やし方の設計が必要です。そのための道具が 4 つある、という話をこれからします。

## 4 つの拡張ポイントの比較

まず全体像を並べます。

| 観点 | CLAUDE.md | Skills | Subagents | Hooks |
| --- | --- | --- | --- | --- |
| いつ読まれるか | 常に（セッション開始時） | 必要と判断されたときだけ | 呼び出されたとき | 指定イベント発生時に必ず |
| コンテキストの消費 | 常時消費する | 発火時のみ消費する | 別コンテキストなのでメインを消費しない | ほぼ消費しない |
| 決定論的か確率論的か | 確率論的（守るかは推論次第） | 確率論的（発火するかも推論次第） | 確率論的 | 決定論的（必ず実行される） |
| 向いている用途 | プロジェクトの前提、禁止事項、参照先の案内 | 時々必要な長い手順書、参照資料、生成物の規約 | 調査、横断的な検証、大量の出力を伴う作業 | フォーマット、危険コマンドの遮断、コミット前チェック |
| 向かない用途 | 長い手順、条件分岐の多い作業 | 毎回必ず必要な前提 | 会話の流れに密着した対話的作業 | 判断や解釈を要する作業 |
| 主な失敗モード | 肥大化して読まれ方が薄まる | description が曖昧で発火しない | 呼び出し粒度が細かすぎて非効率 | 実行が重くて開発体験を損なう |

判断基準を 1 文にまとめます。

> AI が判断を誤ると困るものは Hooks へ、毎回必要なものは CLAUDE.md へ、時々必要な長い手順は Skills へ、文脈を分けたいものは Subagents へ。

この 1 文が、以降の節すべての背骨です。迷ったときはここに戻ってください。

### CLAUDE.md は目次であって本文ではない

CLAUDE.md は常に読まれます。それが最大の利点であり、同時に唯一の制約です。常に読まれるということは、常にコンテキストを消費するということです。

したがって CLAUDE.md に置くべきものは、次の 3 種類にほぼ限定されます。

- プロジェクトの前提（言語、フレームワーク、ビルド・テストの実行コマンド）
- 禁止事項（触ってはいけない場所、使ってはいけない手段）
- 参照先の案内（詳細な手順は Skills にあると伝える）

3 つ目が重要です。CLAUDE.md は本文を書く場所ではなく、目次を置く場所として設計するとうまくいきます。「データベースのマイグレーションを行うときは migration スキルの手順に従う」と 1 行書いておけば、長い手順の本体は必要になったときだけ読み込まれます。第 3 章で触れた「AI のコンテキストを無駄に食う」問題は、CLAUDE.md でもっとも起きやすい形で現れます。書きたくなったら、まず「これは毎回必要か」と自問してください。毎回必要でないなら、行き先は Skills です。

### Skills は手順書であり、description が本体

Skills は必要と判断されたときだけ読まれます。長い手順、参照資料、生成物の規約など、分量を気にせず置けるのが利点です。

ただし発火しなければ存在しないのと同じです。発火を決めるのは front matter の `description` です。ここが曖昧だと、AI は「このスキルを使うべき場面かどうか」を判断できません。description には、何をするスキルかだけでなく、どういうときに使うのかを具体的なトリガー語彙とともに書きます。

## Skills の設計 ─ 中間ファイルを挟む

ZOZO の事例に、Skills の設計として学べる形があります。アーキテクチャ図を Claude Code に作らせる `create-diagram` スキルです。手順は次の 4 段階で構成されています。

1. 対象リポジトリを確認する
2. IaC・アプリコードからノードとエッジを抽出し、`structure.yaml` に出力する
3. 表現要件を `conventions.md` に記録する
4. D2 形式で図を生成し、レンダリングして自動チェックする

この事例の核心は、ソースと成果物の間に 2 つの中間ファイルを挟んだことです。

- **規約ファイル（`conventions.md`）**: アイコンのルール、フローの方向、矢印の種別といった表現ルール
- **構造ファイル（`structure.yaml`）**: リソースの物理名、接続関係、トリガー種別といった構造情報

こう分けたことで責務が分離され、レンダラへの依存を避けつつ、AI が効率的にコンテキストを処理できるようになったと報告されています。効果としては、図の作成時間が 1 時間以上から 10 分程度へ、約 6 分の 1 に短縮されました。あわせて、規約ファイルに表現ルールが蓄積されることで作成者ごとのばらつきが解消し、リリース連動の自動更新によって図の陳腐化も防がれています。ここから一般原則を抽出できます。

> AI に直接ゴールを作らせるのではなく、検証可能な中間表現を経由させる。

図を直接描かせると、出来上がったものが正しいかどうかを人間が目で見るしかありません。しかし構造を `structure.yaml` として先に出させれば、そこに実在しないリソース名が混ざっていないか、接続関係が IaC と矛盾していないかを機械的に検証できます。表現ルールを `conventions.md` として分離すれば、ばらつきはルールの差分として観測でき、ルールを直せば次回から全員に効きます。

この「中間ファイル戦略」は図に限りません。仕様から実装を一気に出させるのではなく、まずインターフェース定義を出させる。テストを一気に書かせるのではなく、まずテストケースの一覧を出させる。いずれも、確率論的な生成の途中に、決定論的に検証できる関門を差し込む形になっています。

### SKILL.md のサンプル

```markdown
---
name: create-diagram
description: >
  リポジトリのIaCとアプリコードからアーキテクチャ図を生成する。
  「構成図を作って」「アーキ図を更新して」「システム構成を図にして」
  と依頼されたとき、またはインフラ変更のリリース後に図を更新する必要が
  あるときに使用する。図の新規作成・既存図の更新の両方に対応する。
---

## 前提

- 出力形式は D2。中間ファイルは `docs/diagram/` 配下に置く

## 手順

### 1. 対象範囲の確認

対象リポジトリと図の粒度（全体構成 / サブシステム単位）を確認する。
不明な場合は推測せずユーザーに確認する。

### 2. 構造の抽出

Terraform の `.tf` とアプリの設定からノードとエッジを抽出し、
`docs/diagram/structure.yaml` に出力する。含める情報は次の通り。

- リソースの物理名（推測で補完しない。コードに存在するものだけ）
- 接続関係（呼び出し方向を明示する）
- トリガー種別（同期呼び出し / イベント / スケジュール）

出力後、リソース名がコード内に実在するかを検証し、実在しない名前が
含まれていた場合はこの段階で修正する。

### 3. 表現規約の適用

`docs/diagram/conventions.md` を読み、アイコンルール・フロー方向・
矢印種別を適用する。規約に記載のない表現が必要になった場合は、
図を描く前に conventions.md へ追記してから進める。

### 4. 生成と検証

2 つの中間ファイルから D2 を生成し、レンダリングする。失敗した場合は
D2 を手直しするのではなく structure.yaml 側の記述を見直す。
```

注目してほしいのは 3 点です。第一に、`description` にトリガーとなる言い回しを複数書いています。第二に、各手順に「検証」が組み込まれています。第三に、手順 3 で「規約に無い表現が必要なら規約に追記してから進める」としています。これは、スキルを使うたびにスキル側の資産が育つ構造です。育てる仕組みの最小単位がここにあります。

## Subagents は文脈を分けるための道具

Subagents は別コンテキストで動くため、メインの会話を汚しません。向いているのは、大量の出力を読む必要があるが結論だけあれば足りる作業です。ログの探索、依存関係の横断調査、複数ファイルにまたがる規約違反の洗い出しなど。メインで実行すると大量の中間出力がコンテキストを埋めますが、Subagent に任せれば戻ってくるのは要約された結果だけです。

逆に向かないのは、会話の流れに密着した対話的な作業です。文脈を共有していないので、これまでのやりとりを前提にした判断はできません。呼び出し粒度が細かすぎると、毎回コンテキストを与え直すコストで割に合わなくなります。第 7 章で扱うレビュースキルはこの性質を使って観点ごとに並列実行する構成を取りますが、ここでは「文脈を分けたいものは Subagents へ」という原則だけ押さえておいてください。

## Hooks の設計 ─ AI に判断させない

Hooks は指定したイベントで必ず実行されます。4 つの拡張ポイントの中で唯一、決定論的です。

なぜこれが重要なのか。「コミット前に必ずフォーマッタを走らせてください」と CLAUDE.md に書いたとしましょう。だいたい守られます。しかし「だいたい」です。忘れられた回では差分にフォーマット由来のノイズが混ざり、レビューがしづらくなります。守られるかどうかが推論に依存している以上、これは避けられません。一方 Hooks に書けば、判断が介在しないので必ず実行されます。

### settings.json のサンプル

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | { read -r f; case \"$f\" in *.ts|*.tsx) npx prettier --write \"$f\" ;; *.py) uvx ruff format \"$f\" ;; esac; }"
          }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": ".claude/hooks/block-dangerous-command.sh"
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "npm run lint --silent && npm run typecheck --silent"
          }
        ]
      }
    ]
  }
}
```

3 種類を入れています。`PostToolUse` はファイルが編集された直後にフォーマッタを走らせます。`PreToolUse` は Bash 実行の前に割り込み、禁止コマンド（本番環境への直接接続、`git push --force`、破壊的な削除など）を非ゼロ終了で遮断します。`Stop` は応答終了時に lint と型チェックを走らせ、壊れた状態で作業が終わるのを防ぎます。

遮断スクリプト側は、禁止パターンに一致したら理由を標準エラーへ出して非ゼロで終了する、という単純な形にします。

```bash
#!/usr/bin/env bash
set -euo pipefail
cmd=$(jq -r '.tool_input.command // ""')
deny=('git push .*--force' 'rm -rf /' 'DROP (TABLE|DATABASE)' 'psql .*prod')

for p in "${deny[@]}"; do
  printf '%s' "$cmd" | grep -Eiq "$p" || continue
  echo "禁止コマンド（$p）です。必要なら人間が手動で実行してください。" >&2
  exit 2
done
```

ここで先取りしておきたい原則があります。第 10 章で扱う「確率論的な生成と決定論的な評価を分ける」という考え方です。生成は推論なので揺れます。揺れることを前提に、評価側を揺れない仕組みで固める。Hooks はその原則をローカルの開発ループで実現する道具です。CI が同じことをリモートで担いますが、Hooks のほうがフィードバックが早く、AI 自身が結果を見て直せます。したがって注意点は実行時間です。時間のかかるチェックを `PostToolUse` に入れると開発体験が壊れるので、速いものをローカルの Hooks へ、遅いものを CI へ、という分担にしてください。

## 規範をどうやって書き溜めるか

ここまでで置き場所は決まりました。残る問題は、何を書くかをどう見つけるかです。

stmn の記事では、スキル化の頻度が週 1 回程度であることが報告されています。ゼロから網羅的な規範集を書き下ろしたのではなく、セッション内で繰り返し現れたパターンを抽出してスキルにしていく運用です。同記事では「ドキュメント整備で自動的によい動きを実現する」という方針、および「まず一度考えさせるという明示的指示」を置くことの効果にも触れられています。

この運用形態のほうが現実的です。最初から完璧な規範集を作ろうとすると、書き終わる前に飽きるか、使われないものが大量に混ざります。それより、次の 1 行のループを回してください。

> 同じ説明を 2 回したら、3 回目の前に書く。

2 回目に気づけるかどうかが分かれ目です。気づいたら、判断基準の 1 文に照らして置き場所を決めるだけです。判断ミスが怖いなら Hooks、毎回必要なら CLAUDE.md、長い手順なら Skills、文脈を分けたいなら Subagents。

このループは、第 8 章で扱う自己改善サイクルの原型です。第 8 章では、レビュー後の修正 PR を材料に「指摘されたのに直っていなかった観点」を検出して観点自体を更新する仕組みを作ります。材料が「人間が繰り返しに気づいたこと」から「修正 PR の差分」に変わり、検出が手動から自動になるだけで、構造は同じです。ここで手動のループを回した経験があると、第 8 章の設計が腹に落ちやすくなります。

## アンチパターン

### CLAUDE.md に全部書く

もっともよく見る失敗です。気づいたことを追記し続け、数百行に育ちます。常時コンテキストを食う上に、重要な禁止事項が大量の細則に埋もれて相対的に効きが弱まります。定期的に読み返し、「毎回必要でないもの」を Skills へ移してください。CLAUDE.md は増えていく前提ではなく、上限を決めて運用する対象です。

### description が曖昧でスキルが発火しない

「コードの品質を改善する」のような description では、どういうときに使うのか判断できません。結果として、書いたのに一度も使われないスキルができます。トリガーとなる依頼の言い回しを複数書き、逆に「こういう場合は使わない」も添えると精度が上がります。作った後に、実際に発火するかを試すところまでやってください。

### Hooks でやるべきことをプロンプトでお願いしている

「必ずフォーマッタを実行してください」「絶対に本番 DB へ接続しないでください」。これらを CLAUDE.md に書いている状態は、決定論で解ける問題を確率論で解こうとしています。守られない残りの数パーセントが事故になる種類のものは、すべて Hooks の担当です。

### 書いた規範を誰も検証していない

stmn の記事では、「誰も深く見ていない箇所で AI が誤った内容を書き込んでも気づけない」というドキュメント劣化のリスクが指摘されています。規範を明文化するとは、AI が読む正解データを作るということです。そこに誤りが混ざると、誤りが増幅されて生成物へ広がります。しかも規範ファイルは日常的にレビューされないため、気づくのが遅れます。この劣化の検知と計測は第 12 章で扱います。

## この章のまとめ

- レビューで毎回同じ指摘が出ているなら、それはレビューの問題ではなく規範が明文化されていない問題です。第 2 章で分解した「変更容易性の維持」の役割は、生成段階へ前送りできます
- 4 つの拡張ポイントの書き分けは 1 文に集約できます。AI が判断を誤ると困るものは Hooks へ、毎回必要なものは CLAUDE.md へ、時々必要な長い手順は Skills へ、文脈を分けたいものは Subagents へ
- ZOZO の事例が示す中間ファイル戦略は一般原則として使えます。AI に直接ゴールを作らせず、検証可能な中間表現を経由させることで、機械的な検証点と規約の蓄積場所が同時に手に入ります
- Hooks の価値は決定論性です。守られるかどうかが推論に依存してよいものと、100% 実行されなければならないものを分けてください
- 規範は書き下ろすものではなく書き溜めるものです。「同じ説明を 2 回したら 3 回目の前に書く」というループが、第 8 章の自己改善サイクルの原型になります

規範が明文化できると、生成物のばらつきは目に見えて減ります。しかし規範は「どう作るか」までしか決めません。「何を作るか」は個々の変更ごとに与える必要があります。次の第 5 章では、仕様と計画をどの粒度で書き、どこまでを使い捨てにしてよいのかを扱います。
