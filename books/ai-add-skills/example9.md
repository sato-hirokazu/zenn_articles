## 精度は自動で上がるのか

第7章でレビュースキルを実装しました。
観点を設計し、ハーネスを組み、AIがPRを読んで指摘を返す状態までは到達しています。
ここで多くのチームが暗黙に期待することがあります。
「使っているうちに、だんだん精度が上がっていくだろう」という期待です。

上がりません。

メルペイの梅津雄哉氏の資料は、この点をまっすぐに指摘しています。
同資料が挙げる課題認識は次の3つです。

1. AIは使い続けても自動では賢くならない
2. 見落としパターンの学習には仕組みが必要
3. 手動更新は運用負荷が高い

1つ目は、当たり前でありながら見過ごされやすい事実です。
レビュースキルの中身はSKILL.mdに書かれたテキストであり、誰かが書き換えなければ1文字も変わりません。
100回レビューを回しても、101回目のレビューは1回目とまったく同じ観点で動きます。
「AIが学習する」という言葉のイメージと、プロンプトが固定されているという実態のあいだには大きな溝があります。

2つ目は、その溝を埋めるには仕組みが必要だという話です。
人間のレビュアーは障害を1回経験すれば次から同じ箇所を疑います。
経験が暗黙知として蓄積されるからです。
AIには蓄積する場所がありません。
正確には、SKILL.mdという場所はあるのに、そこへ書き込む経路がないのです。
経路を作るのがこの章の仕事です。

3つ目が実務的にはもっとも重い問題です。
「気づいたらSKILL.mdに追記する」という運用は、始めた週はうまくいきますが、3週目には忘れられています。
第4章で「同じ説明を2回したら、3回目の前に書く」というループを紹介しましたが、あれは人間が繰り返しに気づけることを前提にしていました。
レビューの見落としは気づくのが難しい種類の情報です。
見落としたということは、そのとき誰も気づいていないということだからです。

つまり必要なのは2つです。
見落としを事後的に検出する方法と、検出したものを観点へ変換する方法。
この章は後者を扱い、前者にあたる検出の自動化は第9章で扱います。

## 修正PRという教師データ

発想の転換はここです。
不具合を直したPRが存在するなら、その不具合を混入させた元のPRが必ず存在します。
そして元のPRはレビューを通過しています。
通過したのに不具合が入ったということは、そのときのレビューは何かを見落としていたということです。
この構造は、教師データそのものです。

- 入力：元PRの差分（レビューが見ていた情報）
- 正解ラベル：修正PRの差分（本来指摘されるべきだった内容）
- 誤り：その差分について、レビューが何も言わなかったという事実

機械学習の教師データを人間が手作業でアノテーションするのは高コストですが、このケースではアノテーションが既に完了しています。
修正PRを書いた開発者が、「ここが間違っていた」を差分の形で明示してくれているからです。
しかも修正PRの説明文には、多くの場合その不具合が何だったのか、どういう条件で起きたのかが書かれています。
梅津氏の資料が「修正PRを食べてレビュースキルが賢くなる」と表現しているのは、この構図です。

```text
   ┌──────────────────┐  観点を適用
   │     SKILL.md     │ ────────────┐
   │ （レビュー観点）   │             ▼
   └──────────────────┘        ┌──────────┐  マージ  ┌────────┐
            ▲                  │  元PR     │ ───────▶ │  本番   │
            │ (6) 人間の承認    └──────────┘          └───┬────┘
            │                                           │ 不具合が発覚
   ┌────────┴────────┐                                   ▼
   │  差分の分析      │◀──── (1) 修正PR情報の取得 ──── ┌──────────┐
   │  = 見落ちの証拠  │      (2) 元PRの特定            │  修正PR   │
   └─────────────────┘                                └──────────┘
     (3) なぜ見落としたかの分析
     (4) 汎用パターンへの抽象化
     (5) 既存観点との重複チェック
```

このループが1周回るたびに、レビュースキルは「前回見落とした種類の問題」を見るようになります。
これは個別の不具合の再発防止ではありません。
同じ不具合はもう修正されているので再発しません。
狙いは、同じ構造を持つ別の不具合を次のレビューで捕まえることです。
だから(4)の抽象化が中核になります。

## 自己改善スキルの6ステップ

梅津氏の資料で紹介されている `/improve-review-pr` は、このループを6ステップに分解しています。
1つずつ、なぜそのステップが必要か、省略すると何が起きるかを見ていきます。

### (1) 修正PR情報の取得

起点は修正PRです。
番号やURLを受け取り、`gh pr view --json body,files` と `gh pr diff` で差分と説明文を取得します。
ここで欲しい情報は差分だけではありません。
説明文が要ります。
差分だけを見ると「nilチェックを追加した」という機械的な事実しか分かりませんが、説明文には「特定の顧客区分でアドレスが未設定のときに詳細画面が500を返していた」という文脈が書かれていることがあります。
省略すると入力が「変更された行」だけになり、意図の分からない差分から観点をひねり出すことになります。
結果として「nilチェックを書く」のような、既に誰でも知っている当たり前の観点しか出てきません。

### (2) 元PRの特定

次に、その不具合を混入させたPRを特定します。
修正PRが触った行の履歴を辿って混入元のコミットを推定し、コミットからPRへ逆引きします。

```bash
# 変更行の履歴から混入元コミットを推定する
git log -n 3 --format='%H %s' -L "$START,$END:$FILE" "$BASE_SHA"
# コミットSHAから、それを含むPRを逆引きする
gh api "repos/$OWNER/$REPO/commits/$SUSPECT_SHA/pulls" \
  --jq '.[] | {number, title, url}'
```

自動判定が曖昧なケースは必ずあります。
リファクタリングで行が動いていた場合、履歴が指すのは真の混入元ではなくリファクタPRです。
したがって候補を複数出して確認する設計にします。
1件に決め打ちすると、無関係なPRを分析して的外れな観点を生みます。
省略すると「レビュー時点で見えていた情報の範囲」が分からなくなります。
元PRの差分を見て初めて、その情報だけを見て気づけたのか、気づけない話だったのかを判定できます。
後者ならレビュー観点にしても意味がなく、テストや監視の担当です。
この切り分けができないと、観点に「レビューでは検知不能なもの」が混ざり続けます。

### (3) 対応漏れの分析

元PRの差分と、当時のSKILL.mdの観点を並べて、なぜ見落としたのかを分析します。
原因はだいたい次のいずれかです。

- 観点が存在しなかった：そもそもその種類の問題を見る指示がなかった
- 観点はあったが発火しなかった：記述が曖昧で、この差分に当てはまると判断されなかった
- 観点はあったが判定を誤った：見たうえで、問題ないと結論した
- 原理的に検知不能だった：実行時の外部状態やデータ依存で、差分からは分からない

分類が違えば打ち手が違います。
1つ目なら新規追加、2つ目なら記述の具体化、3つ目なら判定基準やコード例の追加、4つ目ならレビュー観点ではなくテストや可観測性の課題です。
省略するとすべてが「新規追加」に流れます。
本当は既存の観点の記述が弱かっただけなのに似た観点が2つ並び、後述する「増え続ける問題」を自分で加速させることになります。

### (4) パターンの抽象化

個別事例を、次に効く形へ変換します。
この章でもっとも難しいステップなので、節を分けて詳しく扱います。
ここでは梅津氏の資料が採用している3分類を挙げておきます。
リポジトリ固有のパターン、汎用的なパターン、既存チェック項目の強化の3つです。
省略するとSKILL.mdに「UserServiceのGetProfileでAddressのnilチェックをすること」という記述が残ります。
その1箇所はもう直っているので、この観点は永久に何も検出しません。
何も検出しないのにトークンだけを消費します。

### (5) 重複チェック

現在のSKILL.mdを読み込み、類似する既存項目がないかを確認します。
すでに近い観点があるなら、新規追加ではなく「既存強化」に切り替えます。
梅津氏の資料では、この段階でプロンプトの抽象度を4パターン提案するとされています。
同じ観点を具体寄りから抽象寄りまで複数の書き方で並べ、どれを採用するかを選べるようにするわけです。
抽象度は書いてみないと妥当性が判断できないので、案を並べて比較するのが一番速く、実践的です。
省略するとSKILL.mdの中に意味が重なる観点が並びます。
重なった観点はレビュー時に同じ箇所を二重に指摘してノイズを増やし、第7章で設計した観点の構造も崩します。

### (6) SKILL.mdの更新

最後に、差分を提示してユーザーの承認を得てから更新します。
承認なしに自動でコミットはしません。
理由は後の節で扱います。
省略すると更新が「提案の提示」で終わり、実際にSKILL.mdが変わりません。
人間が手でコピーする運用に戻り、課題認識の3つ目（手動更新は運用負荷が高い）に逆戻りします。
ステップの最後を自動化しきることが、このサイクルが回り続ける条件です。

## 抽象化はどこで止めるか

(4)が実務で一番失敗し、しかも失敗は両方向に起きます。
具体的すぎる観点は再発しないケースにしか効きません。
修正済みの1箇所を見張る観点は、定義上もう何も見つけません。
一方、抽象的すぎる観点は誤検知を量産します。
「境界値の扱いに注意する」という観点はほぼすべての差分に当てはまるので、ほぼすべての差分に対して何かを言い始めます。
指摘が増えれば人間は読まなくなり、レビュースキル全体の信頼が落ちます。

### 抽象度の階段

「`UserService.GetProfile` で外部APIレスポンスの `Address` フィールドが未設定のときにpanicする」という不具合があったとします。
抽象度の階段は次のようになります。

| 段 | 観点の記述 | 検出範囲 | 誤検知 |
| --- | --- | --- | --- |
| 0 | `UserService.GetProfile` で `Address` のnilチェックがあるか | 修正済みの1箇所のみ | ほぼゼロ |
| 1 | `Address` 型を参照する箇所すべてでnilチェックがあるか | 同じ型を扱う箇所 | 低い |
| 2 | 外部APIレスポンスのoptionalフィールドを参照する箇所で、未設定時の分岐があるか | 外部連携を含む変更全般 | 中程度 |
| 3 | 境界値・異常値の扱いが妥当か | ほぼすべての差分 | 高い |

段0は死んだ観点です。
段3は生きているが騒がしい観点です。
実務で採用すべきは段2、迷ったら段1と段2を併記する、というのが目安になります。
段2を選ぶ根拠は3つの問いで説明できます。

1. 再発可能性：同じ構造の変更が今後も発生するか。外部APIを叩くコードは繰り返し書かれるので段2はイエスです。段1は `Address` 型を使わなくなれば死にます
2. 判定可能性：差分だけを見て機械的に判定できるか。「optionalフィールドを参照しているか」は判定できます。「境界値の扱いが妥当か」は妥当性の基準が書かれていないため判定できません
3. 打ち手の明確さ：指摘を受けた開発者が何をすればよいか分かるか。段2は「未設定時の分岐を書く」で終わります。段3は「何をすればよいのか」から議論が始まります

段3のような抽象的な観点は、判定基準とコード例を添えてはじめて使えるようになります。
逆に言えば、判定基準とコード例を書けないなら、その抽象度はまだ早いということです。

### 3分類の判定基準

抽象化した結果は、次の3つのいずれかに必ず振り分けます。

| 分類 | 判定の問い | 記述の書き方 | 主な失敗モード |
| --- | --- | --- | --- |
| リポジトリ固有 | 他のリポジトリに持っていっても通用するか。ノーならこちら | 具体的なパス、型名、内部ライブラリ名を明記する。抽象化しすぎない | 汎用側に混ぜてしまい、他リポジトリで誤検知の温床になる |
| 汎用 | 言語やフレームワークのレベルで成立するか。イエスならこちら | 判定条件とコード例を必ず添える。固有名詞を含めない | 抽象度が上がりすぎて誤検知が増える |
| 既存強化 | すでに近い観点が存在するか。イエスならこちら | 既存項目に判定基準・具体例・除外条件を追記する。新規項目を作らない | 気づかず新規追加し、重複した観点が並ぶ |

「既存強化」を独立した分類として持つことに意味があります。
観点は増やすだけでなく、強くすることができるからです。
たとえば `- エラーハンドリングが適切か確認する` という1行は、何も言っていません。
適切とは何か、何を見れば判定できるかが書かれていないので、AIは差分を眺めて雰囲気で判定します。
同じ観点を強化すると次のようになります。

```markdown
- エラーハンドリングが適切か確認する
  - 判定条件: エラーを受け取る箇所で、(a) 上位への伝播、(b) リトライ、
    (c) 明示的なフォールバックのいずれでもなく、ログ出力のみで処理を
    続行している箇所がないか
  - 対象外: ベストエフォートの通知処理（`notify/` 配下）はログのみで可
  - 悪い例: `if err != nil { log.Warn(err) }` の直後に正常系の処理が続く
```

同じ1つの観点ですが、検出力はまったく違います。
「見落としが1件見つかった」という入力に対して、新しい観点を1つ増やすのではなく既存の観点をこの形に育てるほうが効くケースは、実際にはかなり多いのです。

## Human-in-the-Loopをなぜ挟むのか

(6)で承認を求める設計にする理由を、梅津氏の資料は3つ挙げています。

1. AIが導出したパターンが常に最適とは限らない
2. 不適切なチェック項目が混入するリスクを下げる
3. チームの知識として定着させる機会を作る

1つ目と2つ目は、ここまでの議論の通りです。
抽象度の判断にはそのコードベースが今後どう変わるかという見通しが必要で、それは差分だけからは出てきません。
3年後には使われない型に対する観点を、AIは判断できません。

3つ目が、実は一番の効用かもしれません。
承認を求めるとは、人間に「なぜこの不具合が見落とされたのか」を読ませることです。
承認時に並ぶのは、元PR、修正PR、見落ちの原因分析、そして提案される観点。
これに目を通した人は、その週にチームで何が起きたかを構造として理解します。
つまりこのサイクルには二重の効果があります。

> スキルが賢くなると同時に、チームも賢くなる。

これを自動でSKILL.mdにコミットする設計にすると、1つ目の効果だけが残り2つ目が消えます。
そしてSKILL.mdは「誰も読んでいないのに全レビューに影響するファイル」になり、第4章の最後で触れた規範ファイルの劣化が誰にも気づかれないという問題がそのまま再現します。
承認は、面倒だから残しているのではなく、価値があるから残しています。

## 自己改善スキルの実装

`/improve-review-pr` 相当のスキルを、最小の形で書きます。

````markdown
---
name: improve-review-pr
description: >
  不具合を修正したPRを入力として、レビュー観点（review-pr スキルの
  SKILL.md）を更新する。「修正PRから観点を追加して」「レビューの
  見落としを分析して」「この修正PRを学習させて」と依頼されたとき、
  または障害対応後のふりかえりで使用する。新機能のPRには使用しない。
---

## 前提

更新対象は `.claude/skills/review-pr/SKILL.md`。承認なしに書き換えない。
リポジトリ固有の観点と汎用の観点は、同じファイル内で節を分けて管理する。

## 手順

1. **修正PR情報の取得**: `gh pr view --json body,files` と `gh pr diff` で
   差分と説明文を取得する。説明文が空、または「fix bug」程度しかない場合は
   再現条件と影響範囲をユーザーに確認する。推測で埋めない
2. **元PRの特定**: `git log -L` で変更行の履歴を辿り、
   `gh api repos/{o}/{r}/commits/{sha}/pulls` で混入元PRを逆引きする。
   候補が複数、または確信度が低い場合は候補一覧を提示して確認する
3. **対応漏れの分析**: 元PRの差分と現在の SKILL.md を読み、原因を選ぶ
   （A: 観点が無かった / B: 曖昧で発火しなかった / C: 判定を誤った /
   D: 差分からは原理的に検知できない）。D の場合は観点を追加せず、
   テスト・監視で扱うべき旨を報告して終了する
4. **パターンの抽象化**: 抽象度の候補を4段階で並べ、検出範囲と誤検知
   リスクを併記する。そのうえで推奨案を1つ示し、再発可能性・判定可能性・
   打ち手の明確さの3問で理由を述べる。分類は「リポジトリ固有 / 汎用 /
   既存強化」のいずれかに必ず割り当てる
5. **重複チェック**: SKILL.md の既存項目と意味が重なるものがないか確認し、
   重なる場合は新規追加ではなく「既存強化」に切り替える
6. **更新の提案と承認**: 下記の形式で提示し、承認を得てから書き込む

## 承認を求めるときの形式

```text
## 提案する SKILL.md の更新

対象: .claude/skills/review-pr/SKILL.md
分類: 汎用 / 既存強化
根拠: 修正PR #482 ← 元PR #455（見落とし原因: B）

- エラーハンドリングが適切か確認する
+   - 判定条件: エラーを受け取る箇所で、上位への伝播・リトライ・
+     明示的なフォールバックのいずれでもなく、ログ出力のみで
+     処理を続行している箇所がないか
+   - 対象外: notify/ 配下のベストエフォート通知

想定される影響:
- 検出が増える見込みの箇所: 12ファイル（grep 概算）
- 誤検知の懸念: notify/ 以外にログのみで許容している箇所があれば増える

この内容で SKILL.md を更新しますか。「はい」で適用、
「抽象度を上げる / 下げる」で案を再提示、「却下」で更新せず終了します。
```

承認後、更新根拠（元PR / 修正PRのURL）を該当項目のコメントとして残す。
````

意図を3点補足します。
第一に、`description` に「新機能のPRには使用しない」という除外条件を書いています。
第4章で述べたとおり、Skillsは発火しなければ存在しないのと同じですが、余計な場面で発火するのも同じくらい問題です。

第二に、手順3にDの分岐を置いています。
「レビューでは検知不能」と判定したら観点を追加せずに終わる出口を明示的に作っています。
これがないとAIは何かしら観点を出そうとします。
何も追加しないのが正解であるケースを、正解として扱えるようにする必要があります。

第三に、承認フォーマットに「想定される影響」を入れています。
追加する観点が既存コードのどれくらいにヒットしそうかを事前に見積もると、誤検知の量を承認前に判断できます。
承認者が判断できる材料を渡すのが、Human-in-the-Loopを形式で終わらせないための条件です。
あわせて更新根拠のURLを残すのも意図的で、半年後に「この観点はなぜあるのか」を誰も説明できない状態になると削除の判断ができなくなります。

## 観点の単調増加

このサイクルには構造的な副作用があります。
放っておくと観点が単調増加します。
観点が増えるほどプロンプトは長くなり、コンテキストを食い、レビュー1回あたりのコストが上がり、そして精度が落ちます。
指示が50個あるとき、AIは50個すべてに均等な注意を向けられません。
重要な観点が細則に埋もれる現象は、第4章でCLAUDE.mdの肥大化として扱ったものと同じです。
第3章で引用した「AIのコンテキストを無駄に食う。それも永劫」という表現は、機能だけの話ではありません。
死んだ観点、効かない観点、誤検知しか出さない観点も、まったく同じようにAIの思考予算を恒久的に削り続けます。

したがって、追加と同じ強さで削除と統合を回す必要があります。

- 削除：一度も指摘を出していない観点、出した指摘が常に却下されている観点
- 統合：同じ箇所を重複して指摘する観点、上位の観点に吸収できる観点
- 降格：誤検知が多いが捨てたくない観点を、必須項目から参考項目へ落とす

問題は「効かなかった観点をどう見つけるか」です。
ここは計測の話になります。
ある観点が何回発火し、そのうち何回が実際の修正につながったのかを追う必要があり、第12章で扱うActioned と Engaged の指標がこの判断の材料になります。
指摘が採用された割合が低い観点は、削除か降格の候補です。

運用のリズムについては、stmnの記事が参考になります。
同記事ではスキル化の頻度は週1回程度であり、セッション内の繰り返しパターンを自動抽出する形で運用されていることが報告されています。
週1回という頻度は、観点の追加と棚卸しを同じ会に載せるのにちょうどよい間隔です。
追加だけの会にすると、棚卸しは永久に後回しになります。

## レビュー以外への適用

この章で作ったのは「スキル単位の学習」です。
SKILL.mdという長期の資産に、時間をかけて知識を積んでいく仕組みです。
同じ「育てる」構造は、別の時間スケールや別の対象にも現れます。

MonotaROの事例では、アウターループでPR上の会話の積み重ねをプロンプトに引き継ぐことで、同じ指摘の繰り返しを防いでいると報告されています。
これはPR単位の学習です。
1つのPRの中でレビューコメントが蓄積し、次のイテレーションではその文脈を踏まえて生成されます。
効果はそのPRの中に閉じますが、フィードバックは数分から数時間で戻ります。

| | PR単位の学習 | スキル単位の学習 |
| --- | --- | --- |
| 蓄積先 | そのPRの会話コンテキスト | SKILL.md |
| フィードバック速度 | 分〜時間 | 週〜月 |
| 効果の範囲 | そのPRのみ | 以降のすべてのPR |
| 人の承認 | 不要（会話がそのまま入力） | 必要 |

どちらか一方ではなく、両方が要ります。
PR単位の学習がないと、同じPRの中で同じ指摘を3回することになります。
スキル単位の学習がないと、PRをまたいだ知識が消えます。
速いループと遅いループの二段構えで見るのが正しい理解です。

LayerXのAgent基盤Haroの事例は、これを組織のレイヤーまで押し上げたものです。
同資料では「使われるほど賢くなるAgent」を目標に据え、Agentの実績、失敗、feedbackをPlatform側で回収し、Custom Agentや共通toolの改善に還流させる設計が示されています。
さらに、個人が作った自動化を組織の資産へ転換するMarketplaceの仕組みも紹介されています。
ここから読み取れるのは、還流させる先が階層になっているということです。
この章のサイクルを個人で回すと個人が速くなり、チームで回すとチームが速くなり、Platformで回すと組織が速くなります。
構造は同じで、回収の範囲だけが違います。

第4章で紹介したZOZOの事例も、同じ構造で読めます。
規約ファイルに表現ルールを蓄積していくことで、作成者ごとのばらつきが解消したと報告されています。
ばらつきが出るたびにルールを1行追記し、追記したルールは次回から全員に効く。
「作成者ごとのばらつき」を、個人のスキル向上ではなく共有ファイルの成長で解いているわけです。
レビュー観点を育てることと、まったく同じ形をしています。
つまり育てる対象はレビュー観点に限りません。
AIに渡しているテキストはすべて、育てる対象です。
共通しているのは3点で、蓄積する場所が1つに決まっていること、そこへ書き込む経路が仕組みとして存在すること、そして書き込む内容を人間が一度は見ていることです。

## この章のまとめ

- AIは使い続けても自動では賢くなりません。レビュースキルの中身は固定されたテキストであり、書き換える経路を作らないかぎり、101回目のレビューは1回目とまったく同じ観点で動きます
- 修正PRは、レビューが見落とした証拠です。元PRの差分が入力、修正PRの差分が正解ラベルという教師データが、追加のアノテーションなしで手に入ります
- サイクルは6ステップです。修正PR情報の取得、元PRの特定、対応漏れの分析、パターンの抽象化、重複チェック、承認を経た更新。とくに「見落としの原因分類」と「レビューでは検知不能という出口」を持つことが観点の質を保ちます
- 抽象化は具体すぎても抽象すぎても失敗します。再発可能性、判定可能性、打ち手の明確さの3問で段を選び、結果を「リポジトリ固有 / 汎用 / 既存強化」に振り分けてください。観点は増やすだけでなく強くできます
- 追加と同じ強さで削除と統合を回す必要があります。効かない観点はAIの思考予算を永久に削ります。承認を挟む理由は品質担保だけでなく、スキルが賢くなると同時にチームも賢くなるからです

サイクルは設計できました。
しかし、このサイクルには起動条件があります。
誰かが「これは修正PRだ」と気づいて `/improve-review-pr` を叩くことです。
気づかなければ1周も回りません。
そして修正PRは、日々のマージの中に紛れて流れていきます。
次の第9章では、修正PRを自動で検出し、更新候補として人間の前に運ぶ仕組みを作ります。
