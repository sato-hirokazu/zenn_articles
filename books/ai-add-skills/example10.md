---

第8章で、修正PRを入力にレビュー観点を育てるサイクルを見ました。
修正PRを渡せば、対応漏れが分析され、パターンが抽象化され、承認を経てスキルに反映されます。
仕組みとしては完結しています。
しかしこのサイクルには、設計図に描かれていない前提があります。
誰かが修正PRに気づいて、コマンドを実行することです。
ここが抜けていると、サイクルは一度も回りません。
この章では、その「気づく」を人間の善意から仕組みへ移します。
第3部の最後の章です。

## サイクルの入口にある負荷

メルペイの梅津雄哉氏の資料でも、この点が課題として明示されています。
手動での更新は運用負荷が高い、という認識です。
より具体的には「修正PRを都度見逃さずスキルに反映する」ことの負荷が問題でした。
この負荷を分解すると、3つの作業が混ざっています。

**監視**：マージされるPRを継続的に見て、修正PRかどうかを判別し続ける作業です。
1件あたりのコストは小さいものの、常時発生します。

**想起**：修正PRを見たときに「これはスキル更新の候補だ」と思い出す作業です。
制度を知っていて、かつその瞬間に思い出せる人にしかできません。

**実行**：`/improve-review-pr` を叩いて出てきた提案を確認する作業で、ここは短時間で終わります。

3つのうち、実行は負荷として大きくありません。
問題は監視と想起です。
この2つは業務のタスクリストに現れないのに時間を要求します。
誰のスプリントにも積まれておらず、やらなくても誰にも怒られません。
だから摩耗します。
忙しい週は飛ばされ、飛ばされた週が続くと思い出す確率が下がり、やがて制度そのものが忘れられます。
半年後に「そういう仕組みを作ったよね」という会話が発生して終わります。

これは第4章で規範を明文化したときと同じ構造です。
ドキュメントに書いただけでは飛ばされるので、Hooks や CI で機械的に効かせました。
ここでも同じことをします。
監視と想起を機械に渡し、人間には実行と判断だけを残します。

## 梅津氏の週次ワークフロー

梅津氏の資料では、この入口を GitHub Actions で自動化する構成が示されています。
毎週月曜に GitHub Actions が実行され、先週マージされたPRの中から修正対象と思われるものを自動検出します。
検出された候補は Slack に自動通知され、チームで共有されます。
メンバーは通知を確認したうえで `/improve-review-pr` を実行します。
検出ロジックは、単一の条件ではなく複合判定です。
資料で挙げられているのは次の組み合わせです。

- タイトルや本文に「#XXXX で漏れ」「対応漏れ」といった記述がある
- バグ修正ラベルと、先行するPRへの言及の組み合わせ
- タイトルに「fix」「修正」「hotfix」「漏れ」を含み、かつ新機能追加ではない

3つめの条件には「かつ新機能追加ではない」という否定条件が入っています。
機能追加のPRのタイトルにも fix という語は現れるので、単純なキーワード一致では拾いすぎるという判断です。
そしてこの構成の要点は、機械がやる範囲を限定していることです。
機械は候補を出すだけです。
それが本当に見落としだったのか、そこから抽象化すべきパターンがあるのかは、AIと人間に渡されます。

## 検出ロジックを自分のチーム用に設計する

ここからが実務です。
前節の条件はそのままコピーしても動きません。
PRのタイトル規約、ラベル体系、言語、ブランチ運用がチームごとに違うからです。
設計の考え方を3つの角度から押さえます。

### 再現率に寄せる、ただし限度がある

検出には2種類の失敗があります。
取りこぼし（見逃し）と誤検出（ノイズ）です。
両方を同時にゼロにはできないので、どちらを許容するかを先に決めます。
結論として、この用途では再現率寄りに振ります。
出力が「候補の提示」に過ぎないからです。
検出されたPRがそのままスキルに反映されるわけではありません。
人間が通知を見て実行するかを決め、さらにその先に第8章の承認ステップがあります。
つまり誤検出のコストは「候補を見て、違うと判断して閉じる」だけで、数十秒です。
一方、取りこぼしのコストは学習機会が永久に失われることです。
その修正PRは翌週には検出対象期間から外れ、二度と候補に上がりません。
この非対称があるので、再現率に寄せます。

ただし限度があります。
ノイズが多すぎると通知が読まれなくなります。
これは第1章で見たノイズレビューとまったく同じ失敗モードです。
量が多く当たりの比率が低いと、読み手は個別に判断するのをやめて全体を無視します。
無視された通知は、通知がないのと同じです。
むしろ「仕組みはある」という錯覚を残すぶん悪質です。
目安として、週次通知で人間が真面目に見るのは数件までです。
第6章で触れたワーキングメモリの制約と同じ話で、数が増えると精度ではなく態度が変わります。
それを超えるなら、条件を絞るか、確信度の高いものだけを本文に出して残りは折りたたみます。

### 検出シグナルを評価する

使えるシグナルを列挙し、精度と取得コストで評価します。
精度が高くコストが低いものから採用します。

| シグナル | 内容 | 精度 | 取得コスト | 採用の判断 |
| --- | --- | --- | --- | --- |
| 本文中の明示的な言及 | 「#1234 の対応漏れ」など、先行PRと漏れの両方を書いている | 高 | 低（本文の正規表現） | 必ず採用。単独で候補にする |
| revert コミット | `Revert "..."` のマージ | 高 | 低（タイトル一致） | 採用。ただし原因分析には別の情報が要る |
| バグ修正ラベルとPR参照 | ラベルと本文中の `#番号` の組み合わせ | 高 | 低（API のラベル情報） | 採用。ラベル運用が定着している場合に限る |
| 障害チケットとの紐付け | 本文にインシデント管理チケットのリンクがある | 高 | 中（外部システム参照） | 採用。ただし紐付け率に依存する |
| hotfix ブランチ | `hotfix/*` からのマージ | 中〜高 | 低（`headRefName`） | 採用。緊急対応の運用があれば強い |
| タイトルの語彙のみ | 「fix」「修正」「漏れ」を含む | 低〜中 | 低（タイトル一致） | 単独では採用せず、否定条件と併用する |
| 同一ファイルの短期間内再変更 | 一定期間内に同じファイルが再び変更された | 低〜中 | 中（変更ファイルの突き合わせ） | 補助のみ。リファクタと区別できない |
| 差分が極端に小さい | ごく数行の変更 | 低 | 低 | 単独では使わず、他と組み合わせる |

使い方は、上の4行を単独条件、5行目以降を組み合わせ条件として実装することです。
精度が高いものは単独で候補にし、低いものは2つ以上重なったときだけ候補にします。
なお「レビューコメント数がゼロ」のような指標は検出には使いません。
誰も見ずにマージされたことは別の問題の兆候であって、修正PRであることを示しません。
そして否定条件も明示します。
新機能追加を示すラベル、`feat:` のようなプレフィックス、依存関係更新の自動PR、リリースPRは除外します。
除外を入れないと、ノイズの大半がここから来ます。

### 日本語と英語が混在するチームの語彙設計

日本語の開発現場では、PRのタイトルと本文で言語が混ざります。
タイトルは英語のプレフィックスで本文は日本語、あるいはその逆。
この前提で語彙を設計します。
注意点が3つあります。

ひとつめは、日本語には単語境界がないことです。
英語なら `\bfix\b` で単語として区切れますが、日本語の「修正」は他の語の一部として現れます。
「修正不要」「仕様修正の予定なし」といった文脈でも一致します。
単語境界に頼れないぶん、他のシグナルとの組み合わせで担保します。

ふたつめは、表記のゆれです。
「漏れ」「もれ」「モレ」「抜け」「不足」「考慮漏れ」「対応漏れ」「実装漏れ」。
同じ意味の表現が複数あります。
語彙リストは自分のリポジトリの過去のPRタイトルを見て作ります。
想像で作ると外れます。

みっつめは、英語側の偽陽性です。
`prefix`、`fixture`、`suffix` は `fix` を部分文字列として含みます。
`fix` を検出語に入れるなら単語境界を必須にします。

## 検出スクリプトとワークフロー

最小構成を示します。
週次で起動し、先週マージされたPRを列挙し、判定し、Slack に投げます。
判定は決定論的なスクリプトにします。
ここに生成AIを入れません。
第4章の Hooks の思想、そして第10章で扱う「確率論的な生成と決定論的な評価を分ける」原則と同じです。
同じ入力に対して常に同じ候補が出ることを保証します。
そうしないと通知の内容が週によってぶれます。
ぶれると「先週は出なかったのに」という不信が生まれ、通知そのものが信用されなくなります。

そのぶん判定は粗くなりますが、それでいいという設計です。
粗い判定で候補を広く出し、「これは本当に見落としだったのか」「そこから抽象化できるパターンは何か」という判断はAIと人間に渡します。
工程ごとの役割分担は次のとおりです。

| 工程 | 担当 | 求める性質 |
| --- | --- | --- |
| 検出（候補の列挙） | 決定論的スクリプト | 再現性。同じ入力なら同じ出力 |
| 分析（原因とパターンの抽象化） | 生成AI（`/improve-review-pr`） | 文脈理解。第8章の手順 |
| 承認（観点として採用するか） | 人間 | 説明責任。理解を伴う判断 |

```python
# scripts/detect_review_gaps.py
import json, re, sys

STRONG = [  # 単独で候補にする高精度シグナル
    (re.compile(r"#\d+\s*(で|の)?\s*(対応)?(漏れ|もれ|抜け)"), "先行PRへの漏れの明示"),
    (re.compile(r"(対応|実装|考慮|テスト)(漏れ|もれ)"), "漏れの明示的な記述"),
    (re.compile(r'^Revert\s+"'), "revert"),
]
# 以下は2つ以上重なったときだけ候補にする弱いシグナル
WEAK_TITLE = re.compile(r"(\bfix\b|\bhotfix\b|修正|不備|誤り)", re.IGNORECASE)
PR_REF = re.compile(r"#(\d+)")
BUG_LABELS = {"bug", "bugfix", "incident", "障害"}
EXCLUDE_LABELS = {"feature", "enhancement", "dependencies", "release"}
EXCLUDE_TITLE = re.compile(r"^(feat|chore|docs|release)(\(.+\))?[:!]", re.IGNORECASE)


def evaluate(pr):  # 該当しなければ None を返す
    title, body = pr["title"], pr.get("body") or ""
    labels = {l["name"].lower() for l in pr.get("labels", [])}
    # 否定条件。新機能・自動更新・リリースは候補から外す
    if labels & EXCLUDE_LABELS or EXCLUDE_TITLE.search(title):
        return None

    reasons = [r for p, r in STRONG if p.search(f"{title}\n{body}")]
    confidence = "high"
    if not reasons:
        reasons = [r for hit, r in [
            (WEAK_TITLE.search(title), "タイトルに修正系の語彙"),
            (labels & BUG_LABELS, "バグ修正ラベル"),
            (PR_REF.search(body), "本文に先行PRへの言及"),
            (pr.get("headRefName", "").startswith("hotfix/"), "hotfix ブランチ"),
        ] if hit]
        if len(reasons) < 2:  # 弱いシグナルは2つ以上重なって初めて候補
            return None
        confidence = "medium"

    refs = PR_REF.findall(body)
    return {"number": pr["number"], "title": title, "url": pr["url"],
            "author": pr["author"]["login"], "origin_pr": refs[0] if refs else None,
            "reasons": reasons, "confidence": confidence}

prs = json.load(sys.stdin)
found = sorted((c for c in map(evaluate, prs) if c),
               key=lambda c: (c["confidence"] != "high", c["number"]))
# 母数を必ず出力する。候補ゼロの週にも通知するため
json.dump({"total": len(prs), "candidates": found}, sys.stdout, ensure_ascii=False)
```

`origin_pr` は推定です。
本文に複数のPR番号があれば最初のものを取ります。
正確な特定は第8章で見たとおりAI側の仕事なので、ここでは通知に載せるヒントで足ります。
これを週次で起動する側は次のようになります。

```yaml
# .github/workflows/detect-review-gaps.yml
name: detect-review-gaps
on:
  schedule:
    - cron: "0 0 * * 1" # 毎週月曜 09:00 JST（UTC 00:00）
  workflow_dispatch: # 検出条件の調整時に cron を待たずに試すため
permissions:
  contents: read
  pull-requests: read
jobs:
  detect:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 先週マージされたPRを列挙して判定する
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          SINCE=$(date -u -d '7 days ago' +%Y-%m-%d)
          gh pr list --state merged --search "merged:>=${SINCE}" --limit 200 \
            --json number,title,body,url,author,labels,headRefName,mergedAt \
          | python scripts/detect_review_gaps.py > candidates.json
      - name: Slack に通知する
        env:
          SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK_URL }}
        run: python scripts/notify_slack.py < candidates.json
```

### Slack 通知のメッセージ設計

通知の要件は、読んだ人がその場で次の行動に移れることです。
リンクを開いて調べ直さないと動けない通知は、開かれずに流れます。
必要な要素は4つで、対象PRへのリンク、推定される元PR、なぜ検出されたかという理由、そして実行すべきコマンドそのものです。

```text
[レビュー観点の更新候補] 先週分 / 走査したPRから2件を候補として検出しました。

■ 確信度 高
1. #4821 認可チェックの対応漏れを修正 (@taro)
   https://github.com/org/repo/pull/4821
   推定される元PR: #4780 / 検出理由: 先行PRへの漏れの明示
   → /improve-review-pr 4821

■ 確信度 中
2. #4840 集計バッチのタイムゾーン誤りを修正 (@jiro)
   https://github.com/org/repo/pull/4840
   推定される元PR: #4799 / 検出理由: タイトルに修正系の語彙 + バグ修正ラベル
   → /improve-review-pr 4840

確認担当（今週）: @taro
候補に該当しないものは、このスレッドに理由を書いて閉じてください。
```

確信度で区切っているのは、読む順序を作るためです。
上から数件見て力尽きても、価値の高いものを見たことになります。
第6章で見たとおり、人間に渡す判断は並べ替えて上位に注意を誘導します。
コマンドを文字列として置いているのは、想起のコストを消すためです。
コマンド名を思い出す必要がなく、コピーして貼るだけになります。
思い出す必要がある手順は飛ばされます。
確認担当を名前で書いている理由は、次節の主題です。

## 承認プロセスの設計

検出を自動化しても、承認は残します。
第8章で見たとおり、梅津氏の資料が挙げる Human-in-the-Loop の理由は3つあり、そのうち見落とされやすいのは「チームの知識として定着させる機会を作る」ことです。
承認は品質のチェックだけではなく、「こういう漏れがあったから、こういう観点を追加する」という会話が発生する場そのものに価値があります。
自動更新にすると、この会話が消えます。

```text
 [毎週月曜] Actions(cron) → PR列挙 → 決定論的スクリプトで判定
      |                                    +──（候補ゼロ）──> 母数つきで通知
      v
 Slack へ通知（確信度順・確認担当を明記）
      v
 [週次ふりかえり 冒頭5分] 担当者が候補を確認
      |  +──（該当しない）──> スレッドに理由を書いて閉じる
      v （該当する）
 /improve-review-pr を実行（第8章の手順）→ SKILL.md の差分をPRとして起票
      v
 人間がレビュー ──（却下）──> 理由をPRに記録してクローズ
      v （承認）
 マージ。次回以降のレビューに反映される
```

このフローの要点は、SKILL.md の更新を直接コミットではなくPRにしている点です。
利点が3つあります。
第一に、観点の変更履歴が git に残ります。
「この観点はいつ、どの障害を契機に追加されたか」が追えます。
第8章のサイクルを何か月も回すと観点は増え続けます。
由来が分からない観点は、消していいのか判断できないのであとから消せません。
第二に、レビューの単位が明確になります。
差分として提示されるので、追加される文言をそのまま読めます。
「AIが提案した内容を確認してください」と口頭で言われるより判断しやすくなります。
第三に、却下の記録が残ります。
同じパターンが数か月後に再提案されたとき、前回却下した理由を参照できます。

承認者は、そのレビュー観点が適用されるコードの責任を持つ人にします。
第6章で CODEOWNERS によってパスごとのオーナーを決めました。
同じ人がレビュー観点のオーナーになるのが自然です。
決済のレビュー観点を、決済コードを触らない人が承認するのは形式です。
粒度はパターン単位で分けます。
1回の実行が複数のパターンを提案したなら、一括で承認しないほうがよいです。
ほとんどは妥当だが1つは過剰、という結果はよく起きるので、まとめて承認すると過剰なものが混ざります。

### 週次のリズムに組み込む

通知だけ作っても、それを見る時間が確保されていなければ流れます。
既存の定例に組み込みます。
Uzabase社の記事では、スプリントレビューの中に学習共有の時間を5分確保するという実践が紹介されています。
学びを共有する場を、意図をもって短く確保するという発想です。

この形はレビュー観点の更新候補の確認にそのまま使えます。
週次のふりかえりの冒頭5分で Slack の通知を開き、候補を1件ずつ見ます。
該当しないものはその場で閉じ、該当するものは担当を決めてから解散します。
5分という長さが適切なのは、その場で分析までやろうとしないからです。
分析は `/improve-review-pr` がやります。
人間がその場でやるのは、候補の取捨と担当決めだけです。
担当は輪番にします。
固定すると、その人が休んだ週に止まります。
輪番にすれば全員が定期的に自分たちのスキルを読むことになり、これも定着の機会になります。

### 承認が形式化する危険

ここで第6章の論点を再確認します。
要件は「承認する人が中身を理解しているか」です。
この承認プロセスは形式化しやすい構造を持っています。
AIが提案した文章がそれらしく整っているからです。
もっともらしいレビュー観点の追加を、内容を吟味せずに承認することは容易です。
しかも承認しても短期的には何も起きません。
悪い観点が混ざったコストは、しばらく経ってからノイズ指摘という形で現れます。
因果が離れているので、承認の質が低いことに気づけません。
対策は、承認時に問いを固定することです。
SKILL.md 更新PRのテンプレートに置きます。

```markdown
## 追加・変更するレビュー観点

（`/improve-review-pr` の出力を貼る）

## 承認前チェック
- [ ] 元になった修正PRを自分で開いて読んだ
- [ ] この観点があれば、その修正PRの原因を実際に検出できたと言える
- [ ] 既存の観点と重複していない
- [ ] この観点が偽陽性を出す状況を1つ以上想定した
- [ ] 提案されたパターンのうち、採用しなかったものがあれば理由を書いた
```

2つめと4つめが実質的な項目です。
「この観点があれば検出できたか」は、観点の有効性を過去の実例で検証する問いです。
「偽陽性を出す状況」は、コストの側を考えさせる問いです。
この2つに答えられなければ、その承認は理解を伴っていません。

## 起動条件を差し替えられるようにする

この章の仕組みは、cron で起動して Slack に通知する形でした。
もう一段先の形があります。
LayerX社の Agent 基盤 Haro の資料では、入口を統一する設計が示されています。
WebUI、HTTP API、CLI、Slack、Webhook、cron、Mail といった複数の入口を、単一のエントリーポイントに集約する構成です。
そのうえで、イベント駆動で起動する Ambient Agent への展開が語られています。
チャット起点ではない自律稼働を目指す方向です。

この設計の意味は、起動条件を後から差し替えられることです。
この章では月曜の cron を起動条件にしましたが、本来もっと適した契機があります。
修正PRがマージされた瞬間、インシデントがクローズされた瞬間、revert が実行された瞬間。
cron を使ったのは実装が簡単だからで、本質ではありません。
入口が統一されていれば、cron をイベントに置き換えても下流は変わりません。

また同じ資料では「使われるほど賢くなる Agent」という考え方も示されています。
実績、失敗、feedback を Platform 側で回収し、Custom Agent や共通ツールの改善に還流させる構成です。
Marketplace を通じて、個人の自動化を組織の資産に転換するという発想も含まれています。
これは本書がここまで扱ってきたことの一般形です。
第8章のサイクルはレビュースキル1つに対する還流でしたが、それを基盤の層でやると、個人が作った自動化が組織の共有物になります。

本書の文脈での読み替えを整理します。
検出、通知、承認、更新という4つの工程のうち、人間のトリガーを外していけるのは検出と起案です。
検出はイベント駆動にできます。
起案も、候補を検出した時点で SKILL.md 更新PRの下書きまで自動生成できます。
しかし承認は残します。
前節で述べた3つの理由が、自動化の度合いに関係なく成立するからです。
むしろ検出と起案が自動化されて量が増えるほど、承認の質が全体の品質を決めます。
ここを外すと、次節のアンチパターンの最後の形になります。

## アンチパターン

この仕組みで壊れる形は4つあります。

**通知だけ作って誰も見ない。**
最も多い失敗です。
ワークフローは正常に動き、Slack にはメッセージが積まれ続け、誰も開きません。
原因はオーナーが決まっていないことです。
「気づいた人が対応する」は、誰も対応しないという意味です。
通知に確認担当を名前で書き、定例で見る時間を確保することが対策になります。

**候補ゼロの週が続いて、動いているか分からなくなる。**
検出条件を厳しく作りすぎるとゼロが続きます。
このとき問題は、ゼロが「健全な状態」なのか「ワークフローが壊れている」のか区別できないことです。
区別できないと、いつの間にか壊れていても気づけません。
候補ゼロでも母数つきで「先週のPRを走査、候補なし」と通知します。
母数が入っていれば、集計自体が動いていることが分かります。

**ノイズだらけで通知がミュートされる。**
逆の失敗です。
毎週大量の候補が並び、その大半が的外れだと通知はミュートされます。
しかも一度ミュートされたチャンネルは元に戻りません。
再現率に寄せるという原則と矛盾して見えますが、矛盾しません。
広く検出しつつ、確信度で区切って本文に出す件数を制限すればよいのです。
検出条件の緩さと、通知の見た目の量は別に設計できます。

**検出から完全自動更新につなげてしまう。**
一見して最も効率的に見える形です。
検出したらAIが分析し、そのまま SKILL.md に反映する。
人間の手が一切かかりません。
これが最も危険です。
観点が誰にも把握されないまま増殖し、やがてレビュースキルが長大な観点リストになって、誰も全体を読んでいない状態になります。
そして観点が増えるほど指摘数が増え、ノイズ比率が上がり、第1章で見た「読まれないレビュー」に戻ります。
第8章のサイクルは、放置すると自分の首を絞める構造を持っています。
承認がそのブレーキです。

4つを並べると共通点が見えます。
いずれも「仕組みは動いているが、人間が関与していない」状態です。
この章で自動化したのは監視と想起であって、判断ではありません。
判断を自動化した瞬間に、この仕組みは劣化装置に変わります。

## レビューで見つけることの限界

第6章で線引きを決め、第7章でレビュースキルを実装し、第8章で観点を育てるサイクルを作り、この章でその入口を自動化しました。
レビュー工程の補強として、これで一巡です。

ただし前提を置き直します。
ここまでの全部が「レビューで見つける」という枠の中の話です。
第6章で確認したとおり、レビューには構造的な限界があります。
人間の承認は理解を伴わなくなりうるし、AIレビューはコード外の制約を見られません。
そしてレビューは、通してしまえば通ります。

だから次は、通せない仕組みの話に移ります。
第10章では、テストと静的解析をゲートにします。
レビューが「見て判断する」工程だったのに対して、ゲートは「条件を満たさなければ進めない」工程です。
確率論的な判断ではなく、決定論的な機械の判定で止めます。
この章の判定スクリプトで採った思想を、品質保証の本流に持ち込みます。

## この章のまとめ

- 良い自己改善サイクルが回らない理由は、たいてい入口にあります。梅津氏の資料が課題として挙げるとおり、負荷の実体は実行ではなく監視と想起です。この2つは業務のタスクリストに現れないため、善意に依存させると必ず摩耗します
- 梅津氏の週次ワークフローは、毎週月曜に GitHub Actions で先週マージされたPRを走査し、複合条件で修正対象を検出して Slack に通知する構成です。単一のキーワード一致ではなく、「fix を含み、かつ新機能追加ではない」といった否定条件を含む複合判定になっています
- 検出は再現率に寄せます。出力が候補の提示に過ぎず、下流に人間の確認とAIの分析があるため、誤検出のコストは数十秒、取りこぼしのコストは学習機会の永久喪失という非対称があります。ただし通知に出す件数は確信度で絞り、第1章のノイズレビューと同じ失敗を避けます
- 判定は決定論的なスクリプトにし、生成AIを入れません。検出は再現性、分析は文脈理解、承認は説明責任という役割分担を固定します。SKILL.md の更新をPRとして出せば、観点の由来と却下理由が git の履歴に残ります
- 自動化していいのは検出と起案までで、承認は残します。LayerX社の Haro が示す Ambient Agent の方向に寄せるほど起案の量が増えるため、承認の質が全体の品質を決めます。完全自動更新は、誰も把握していない観点を増殖させる劣化装置になります
