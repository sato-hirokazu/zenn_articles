## 当たり前は書かれていない水準

チームには、誰も明文化していないのに守られている水準があります。
konifar は、組織の地力は「当たり前のレベルがどういう水準か」に現れると書き、例として次のようなものを挙げています。

- このレイヤーのテストコードは当然書く
- Pull Request の description は、レビュアーや将来の自分たちのために丁寧に書く
- 皆が今期のチーム目標を言える
- 期日までに勤怠の提出を全員が終えている

一つ一つは小さな習慣です。
しかし、こうした「当たり前」の水準がそろって高いチームは、個々の判断に時間を使わずに済みます。
テストを書くかどうかを毎回議論しなくてよいからです。
同氏は、この水準を上げていくのはなかなか難しいとも書いています。

コーディングエージェントは、この難しさの性質を変えます。
上げにくいという問題に加えて、放っておくと水準が勝手にずれていく、という問題が加わるからです。

## エージェントによる当たり前のずれ

ずれ方は二つあります。

一つ目は、水準を測る目盛りが効かなくなることです。
「Pull Request の description を丁寧に書く」という水準は、書く手間がかかることを前提にしていました。
手間をかけて書かれた説明は、書いた人が変更をそれだけ考えたことの目印になります。
エージェントに書かせれば、長く整った説明が数秒で出てきます。
水準の文面は満たされますが、目印としての意味は失われます。
テストコードも同じで、エージェントは頼めばテストを書くので、「テストを書く」という水準はほぼ自動的に満たされます。
そのテストが何を確かめているかは、水準の文面からは分かりません。
前著の第14章では、プルリクエストの説明のうち差分から導けない欄を人が書くという分担を扱いました。
同じ問題が、チームの水準全体で起きます。

二つ目は、エージェントの既定の出力が、そのままチームの水準になりやすいことです。
yuk1tyd は、Addy Osmani の『バイブコーディングを超えて』を読んだ感想として、AI の出力は仕組み上「多数派の解決策」であり、一般解であって最適解ではない、と書いています。
チームが自分たちの水準を示さなければ、エージェントは一般的に妥当な水準でコードを書きます。
レビューで直されない限り、その水準が積み重なって、誰も選んでいないままチームの実質的な当たり前になります。

どちらのずれも、エージェントの出力の量が多いほど速く進みます。
人が書いていた頃の水準は、人の書く速度でしか変わりませんでした。
今は、一週間のうちにエージェントが書いたコードが、チームの慣習を上書きすることがありえます。
したがって、当たり前の水準は、意図して決め直す対象になります。

## 当たり前を上げる五つの段階

konifar は、当たり前のレベルを上げるステップを五つに分けています。

一つ目は、トップオブトップを知ることです。
トップの組織の当たり前がどの水準にあるかを知り、自分たちの相対的な位置をつかみます。
手段は Web や書籍、Podcast からのインプットでも、イベントやカンファレンスへの参加でもよい、と同氏は書いています。
世界を広げないと目指す水準を設定できず、筋の悪い方針で進めたり、無駄な再発明をしたり、井の中の蛙になったりする、という理由です。

二つ目は、目線を合わせることです。
どの水準を目指すかをチームでそろえます。
同氏は、デプロイ頻度のようにエリートレベルの指標が定義されているものは共通認識を持って話しやすいとし、DX Criteria で定量化するのもよいと書いています。
ここで合わせたことが、チーム目標になることもあります。

三つ目は、引っ張ることです。
同じ水準のメンバーが工夫するだけでは水準は上がらず、数人が先に当たり前を上げて見本を見せる必要があります。
ただし背中を見せるだけでは上がらないので、「おかん」のような一定の口うるささも要る、と同氏は書いています。
そのうえで、人に依存せずに強制する仕組みを作れるならそのほうがよく、実際にはその仕組みを作るところを引っ張る役割が必要になることが多い、と続けています。

四つ目は、振り返ることです。
定点観測して前と比べます。
そのためには、定量でも定性でもよいので指標を決めて計測する必要があります。
効果が測れないと、取り組みはだんだん形骸化して止まります。
同氏はこれを「ダイエットと同じ」と表現しています。

五つ目は、やり続けることです。
一から四を繰り返すことで少しずつ水準が上がり、続けるうちに文化になります。
同氏は、成果が出るまでやり続けることが一番難しいと書いています。

## エージェントに運ばせる当たり前

五つの段階のうち、コーディングエージェントで形が大きく変わるのは三つ目です。
konifar が「人に依存せず強制するような仕組み」と書いたものを、エージェントへの指示として作れるからです。

前著の第4章では、CLAUDE.md、Skills、Subagents、Hooks に規範を書き分ける方法を扱いました。
エージェントは渡されたものを毎回読むので、書いた規範は、誰がエージェントを起動しても適用されます。
チームの当たり前をそこに書けば、引っ張る人がその場にいなくても、エージェントの出力は書かれた水準にそろいます。
口うるさい人の指摘を、エージェントが毎回先に済ませる形です。
指摘が行動を変えるまでの過程は第13章で扱いましたが、エージェント相手であれば、行動を変えるのは指示を書き換えた時点です。

ただし、書き方を誤ると、前節の一つ目のずれをそのまま持ち込みます。
「テストを書く」と書けば、エージェントはテストを書きますが、水準は上がりません。
書くべきなのは、水準の文面よりも、その水準で何を守りたいかです。
たとえば、次のような形で書きます。

```markdown
## このチームの当たり前

各項目は「水準」「守りたいこと」「決めた日」の三つで書く。
「守りたいこと」が書けない項目は追加しない。

- 水準: 料金を計算する処理を変更したら、境界値のテストを追加する
  守りたいこと: 端数処理の変更が請求額に及ぶことを、リリース前に検知する
  決めた日: YYYY-MM-DD
- 水準: プルリクエストの説明の冒頭に、Issue の「目的」を引用する
  守りたいこと: 機能を削除するときに、作った理由を辿れるようにする
  決めた日: YYYY-MM-DD

## 当たり前を満たせないとき

- 水準を満たせない変更は、満たせない項目と理由をプルリクエストの説明に書く
- 水準を下げてよいかを自分で判断しない
- 「守りたいこと」に照らして水準が足りないと判断したら、追加の対応を提案する
```

「守りたいこと」の欄があると、エージェントは水準の文面だけでなく、その意図に照らして出力を調整できます。
人にとっても、この欄は水準を見直すときの材料になります。
守りたいことがもう存在しない項目は、削ってよい項目です。
第1章で、Why が残っていれば機能を削除する判断がしやすくなると書きましたが、水準についても同じことが言えます。
「決めた日」は、四つ目の段階で見直すときに、古い項目から順に確かめるためのものです。

置き場所の判断には、前著の第4章の基準がそのまま使えます。
CLAUDE.md に書いた水準が守られるかどうかは、エージェントの推論に依存します。
「秘密情報をコミットしない」のように、一度でも破られると困る水準は、CLAUDE.md ではなく Hooks や CI のチェックに置きます。
CLAUDE.md に残すのは、満たし方に判断が要る水準です。
境界値のテストをどこまで書けば端数処理の変更を検知できるかは、機械的には決まらないからです。

## 書き込めない当たり前

エージェントに運ばせられるのは、五つの段階のうち三つ目の一部です。
残りは人に残ります。

一つ目の段階（トップオブトップを知る）は、エージェントに任せると一般解に寄ります。
エージェントが示せるのは、多くの組織で妥当とされている水準です。
トップの組織の水準は、定義上その外側にあります。
コーディングエージェントの使い方は、ツールの機能も各社の公開事例も入れ替わりの速い領域です。
以前に調べた水準が今も上位にあるとは限らないので、知る作業を一度で終わらせるわけにはいきません。

二つ目の段階（目線を合わせる）は、チームの合意そのものです。
エージェントの使い方がメンバーごとに違えば、当たり前の感覚もメンバーごとに違ってきます。
一日に何本もプルリクエストを出す人と、エージェントの差分を全部読んでから出す人とでは、「十分に確かめた」の基準が違うはずです。
CLAUDE.md に水準を書いても、チームがその水準を目指すと合意していなければ、書かれた水準はエージェントだけが守る規則になります。
誰がその水準を決めるかは、第10章で扱った問題と同じです。

さらに、三つ目の段階で仕組みに移した水準にも、人に残る部分があります。
前著の第12章では、観点の更新を自動で適用すると「仕組みは賢くなりますが、人は賢くなりません」と書き、承認を挟むことで人が内容を読む機会を残しました。
当たり前の水準にも同じことが起きます。
エージェントが毎回水準を満たしてくれるチームでは、メンバーはその水準を意識しなくなります。
エージェントの指示が届かない場面（障害対応で手を動かすとき、指示に書かれていない種類の変更をするとき）では、水準は元に戻ります。
エージェントに運ばせた水準は、チームの水準ではなく、エージェントの出力の水準です。

そこで、四つ目の段階（振り返る）に、書いた水準そのものの点検を含めます。
たとえば月に一度、「このチームの当たり前」の項目を一つずつ読み上げ、守りたいことがまだ有効か、エージェントの出力で満たされているか、人が手で作業したときにも守れているかを確かめます。
最後の問いに答えられない項目は、エージェントにしか守られていない項目です。
指標は、konifar の言うとおり定性でもかまいません。
「この水準を説明できる人がチームに何人いるか」でも、形骸化の兆しは見えます。

## やり続ける役割

konifar は記事の最後で、読んで納得するだけでは意味がなく、自分もできたと言える経験はほとんどない、と書いています。
そして、結局は誰かが覚悟を決めて愚直にやり続けるしかなく、当たり前のレベルが高く見える組織は、誰かがその役割を担ってきた積み重ねによるものだろう、と結んでいます。

コーディングエージェントは、この役割を軽くはします。
書いた水準を毎回適用してくれるので、口うるさく言い続ける手間は減ります。
しかし、何を当たり前にするかを決め、書いたものが今も意味を持つかを確かめ続ける役割は、エージェントの外に残ります。
水準を書いた CLAUDE.md の更新履歴は、その役割を誰が担ってきたかの記録にもなります。

## この章のまとめ

- チームの地力は、明文化されていない「当たり前」の水準に現れる
- コーディングエージェントは、当たり前を二つの方向にずらす。手間を前提にした水準は文面だけ満たされて意味を失い、チームが水準を示さなければエージェントの一般的な出力が実質の水準になる
- konifar は当たり前を上げる段階として、トップオブトップを知る、目線を合わせる、引っ張る、振り返る、やり続ける、の五つを挙げている
- 引っ張る段階の一部は、水準とその水準で守りたいことを CLAUDE.md に書き、エージェントに運ばせられる。守りたいことが書けない項目は追加しない
- トップを知ること、目線を合わせること、書いた水準が人にも守れているかを確かめることは、人に残る。エージェントにしか守られていない水準は、チームの水準ではない

当たり前を上げ続けられるかどうかは、やり続ける人の覚悟だけでは決まりません。
次章では、人の行動を左右する組織の構造を扱います。
