## 見た目の整った画面に残るもの

コーディングエージェントを使えば、エンジニアでない人も動く画面を作れます。
第2章で扱った試作も、その一つです。
ラクスで社内向けのデザインシステムを作っている安彦は、AI によって UI の生成が容易になり、フロントエンドエンジニア以外がコードに手を入れたりプロトタイプを作ったりする場面が増えている、と書いています。

同氏によれば、そうして生成された画面は、一見すると見た目が整っています。
しかし、focus の制御が漏れていないか、選択状態が色だけで示されていないか、disabled のときに何が起きるか、といった見えない層の品質まで、生成段階で担保できているケースは多くありません。
見過ごされたものは、直す工数として後から現れます。

見えない層が漏れるのには理由があります。
安彦は、画面を組むときに画像という静的な形式では表しきれない領域として、次の三つを挙げています。

- **状態**：hover、押している途中、送信中、エラー、空のデータ、長い文字列、文字サイズの拡大
- **操作**：キーボードだけで操作できるか、スクリーンリーダーに何が読み上げられるか
- **更新**：使っているライブラリを更新した後の見た目

これらが仕様に書かれていなければ、実装するフロントエンドエンジニアの判断に委ねられる、と同氏は書いています。
機能開発の速さが優先される現場では、UI の細かな品質を受け入れ基準に入れる余裕がないことも多く、気付かれなかった実装は、次に誰かがそのコードに触れるまで残り続けます。

ここから先は本書の推論です。
フロントエンドエンジニアが画面を組んでいた頃は、仕様に書かれていない状態や操作を、その人の経験が埋めていました。
エージェントやエンジニアでない人が画面を組むと、この埋め手がいなくなります。
画面を頼む人が書くのは、たいてい目に見える完成形です。
エージェントは書かれた完成形を満たして作業を終え、頼んだ人は画面を見て確かめます。
どちらの段階でも、画像に表れない状態と操作は確かめられません。

## 確かめる場所を作り手から基盤へ移す

この漏れを防ぐ手は、大きく二つに分かれます。
一つは、作られた画面を一つずつ確かめることです。
レビューの観点に focus の制御やキーボード操作を加え、生成された画面ごとに見ていきます。
もう一つは、作り手が誰であっても通る場所に品質を置くことです。

前者の手間は、画面を作る人の数と画面の数に比例します。
作る費用が下がって作り手が増えれば、確かめる手間もその分増えます。
前著の第1章で扱ったレビューの詰まりと同じ形です。
後者の手間は、作り手の数に依存しません。
品質を置いた場所を一度確かめれば、そこを通った画面はすべてその品質を受け継ぎます。

安彦も、画面を作る費用が下がった分、コードを保守し続ける負担の比重が上がると書き、だからこそコードを書く人が増える時代に接点を絞る意味が大きくなる、と結論しています。
以下では、同氏のチームが作っているデザインシステム「Libero」の設計を、後者の手の具体例として見ていきます。

## 基盤が持たないものを先に決める

ラクスには、用途もブランドも異なる複数のプロダクトがあります。
安彦は、開発者がそれぞれの現場で迷わず安全に Libero を使えるようにするには、最初に Libero が何を持ち何を持たないかを決める必要があった、と書いています。

Libero は、プロダクトのドメインとブランドを持ちません。
ドメインの知識（特有のデータ構造、業務の流れ、文言など）はプロダクトごとに違い、変わり続けるので、Libero が追い続けるのは難しいからです。
ブランド（テーマカラーやタイポグラフィ）についても、どれか一つのプロダクトの表現を既定値にすると、他のプロダクトは不要なスタイルを打ち消す作業を負うことになります。
そのため Libero の API にはドメインの言葉を持ち込まず、コンポーネントの既定の見た目と振る舞いにも特定のブランドの表現を入れていません。
全社横断のデザインガイドラインを先に作ることもしませんでした。
プロダクトごとにガイドラインの整備状況や目指す表現が違うからです。
そのうえで、デザイントークンを起点に44のコンポーネントを提供しています。

持たないものを決めることは、品質の保証にも関わります。
既定値がどこかのプロダクトのブランドに寄っていれば、他のプロダクトは既定値を上書きしながら使うことになります。
上書きが増えるほど、基盤が保証したはずの振る舞いを利用側が崩す機会も増えます。
持たないものを決めておけば、どのプロダクトも既定値のまま使い始められます。

## 引き受ける五つの層

持たないものを決めたうえで、Libero は自分が引き受ける範囲を層で定めています。
安彦によれば、UI は土台から順に依存しながら積み上がる構造をしていて、最下層にはブラウザや OS、支援技術といった変えられない実行環境があり、最上層にはプロダクト固有の判断が乗ります。
Libero はその間にある五つの層を自分の責務とし、層ごとに何を満たせば品質が守られるかを定義して、すべてのコンポーネントに適用しています。

- **セマンティック HTML**：用途に合った HTML 要素と role で組み立てる
- **アクセシビリティ**：キーボードで操作でき、支援技術に名前と役割と状態を伝える
- **状態表現**：hover、focus、disabled、処理中などの状態を見た目で示す
- **テーマ**：色や形をトークンとして持ち、値をまとめて差し替えられる
- **フレームワーク対応**：UI フレームワークや CSS ライブラリの更新に追従する

最上層にある情報設計、画面の構成、文言、操作後の処理は、引き続き各プロダクトが持ちます。
同氏は、Libero が五つの層を引き受けるのは、プロダクト側がドメイン固有の判断に集中できるようにするためだと書いています。

五つの層を、最初に挙げた画像で表しきれない三つの領域と並べてみます。
状態は状態表現の層に、操作はセマンティック HTML とアクセシビリティの層に、ライブラリ更新後の見た目はフレームワーク対応の層に対応します。
生成された画面から漏れやすいものを、Libero はそのまま自分の責務にしています。

## 値を根拠から導き、CI で確かめる

引き受けた層の品質を、Libero は感覚ではなく根拠と自動化で保っています。
既定の振る舞いは二つの観点を満たすように決められています。
Web 標準については、ブラウザ標準の振る舞いを上書きせず、Baseline の Widely available に含まれる機能だけで作ります。
アクセシビリティについては、WCAG 2.2 の AA の達成基準を満たします。
この二つは CI で検査されていて、Widely available を外れる機能を使っていないかを lint で、アクセシビリティの違反がないかを axe-core で確かめています。

見た目の値も、根拠から導かれます。
色はコントラスト比から候補を絞り、角丸は要素の高さとの比から決めます。
値そのものではなく導き方を決めているので、将来値を変えることになっても、同じ導き方で安全に決め直せる、と安彦は書いています。

前著の第10章では、確率的に揺れる生成に対して、揺れない決定論的な評価をぶつける構造を扱いました。
Libero の CI は、その評価を一つずつの画面ではなく基盤に掛けています。
生成された画面がどれほど揺れても、基盤のコンポーネントは CI を通ったものだけです。

## 接点を三つに絞る

既定値のままでも品質が保たれる基盤であっても、プロダクトに組み込めば、ブランドカラーや固有のスタイルを当てたいという要望が出ます。
Libero は、プロダクトのドメインやブランドを受け入れる経路として、次の三つだけを明示的に開いています。

- **props**：コンポーネントに、variant、状態、表示する文言を値として渡す
- **theme**：primary のような色や形の役割に、ブランドの表現を値として渡す
- **events**：ユーザーの操作が起きたことをプロダクト側に知らせ、その後の処理を委ねる

安彦は、この三つを変えても影響範囲を予測できる経路だと説明しています。
開く範囲を絞る最大の理由は、引き受けた層の品質と振る舞いの一貫性を崩さないためです。
依存の向きをプロダクトから Libero への一方向に限ることで、ライブラリを更新したときの予期しないレイアウト崩れを防ぎ、保守の負担を Libero の中で完結させる狙いもあります。

theme の使い方は、ガイドラインの整備状況に応じて変わります。
ガイドラインがすでにあるプロダクトは、その表現を theme の値として差し替えます。
primary の役割に値を渡せば、ボタンやリンクなど同じ役割の要素がまとめてブランドカラーに置き換わります。
整備中のプロダクトは、まず既定値に乗り、固有の表現が増えてきた段階でガイドラインを育てていけます。

接点の範囲で既定から外れる値を入れたい場合や、接点では表せない要件が出た場合は、Web 標準やアクセシビリティとの整合が崩れるおそれがあります。
そのとき Libero のチームは利用を強制せず、なぜこの制約になっているのかという根拠を共有し、トレードオフを一緒に評価したうえで、判断をプロダクト側に委ねています。

この設計から、安彦は次のように結論しています。
三つの接点だけを通って組まれた画面であれば、人が書いても AI が書いても、その下の五つの層は同じ水準の品質に保たれます。
エンジニアでない人が AI で作ったプロトタイプでも、接点だけで組まれていれば、フロントエンドエンジニアは画面の構成や文言の確認に集中し、安心してそのまま実装に進めます。

## 「接点だけを通る」を確かめる

この結論には条件が付いています。
接点だけを通って組まれていれば、という条件です。
ここからは本書の提案です。

エージェントは、渡された指示を満たすことを完了の条件にします（第1章）。
接点で表せない見た目を頼まれれば、素の HTML 要素で部品を組み直したり、コンポーネントにスタイルを直接当てたりして、指示を満たそうとするかもしれません。
画面は頼まれたとおりに見えるので、頼んだ人は気付きません。
基盤が引き受けたはずの層は、その画面では基盤の外にあります。

そこで、条件そのものを確かめられる形にしておきます。
一つは、エージェントへの指示です。
たとえば、プロダクトのリポジトリの CLAUDE.md に次のように書きます。

```markdown
## 画面を組むとき

- 画面は共通コンポーネントだけで組む。ボタン、リンク、入力欄、ダイアログを HTML 要素から自作しない
- 色、余白、角丸は theme の値で変える。コンポーネントに style や独自の class を当てて上書きしない
- 操作の後の処理は events で受け取って書く。コンポーネントの内部の要素に直接イベントを付けない
- 接点（props、theme、events）で表せない要件が出たら、実装を止め、要件と表せなかった理由を基盤チームへの相談事項として書き出す
```

もう一つは、指示が守られたかを機械で確かめることです。
ESLint の `no-restricted-syntax` のような汎用のルールを使えば、プロダクトのコードに素の `button` 要素やインラインのスタイルが現れたときに CI を落とせます。
指示は確率的に守られ、lint は決定論的に止めます。
前著の第10章と同じ分担です。

最後の項目は、Libero のチームが接点の外の要件を対話で扱っていることに合わせたものです。
エージェントに回避策を書かせるのではなく、表せなかった要件を相談事項として残させれば、基盤の側は接点を広げるべきかどうかを判断する材料を得られます。

条件が守られていれば、画面のレビューは最上層に集中できます。
情報設計、画面の構成、文言、操作後の処理です。
これらはドメインの判断なので、どの基盤にも預けられません。
第8章で見たリリースの QA も、基盤が引き受けた層を毎回確かめ直さずに、品質基準に関わる体験に時間を回しやすくなります。

## UI の外に広げるときの条件

Libero の設計は UI の基盤についてのものです。
ここからは本書の推論ですが、同じ構造は UI の外の共通基盤にも当てはまりそうです。
たとえば、認証やリトライを引き受ける API クライアント、テナントの分離を引き受けるデータアクセスの層、暗号化やログの設定を既定で備えたインフラのモジュールなどです。
エージェントが書くコードがこうした基盤だけを通るなら、その基盤が引き受けた品質は、誰が書いたかに関係なく保たれます。

ただし、Libero の設計から読み取れる条件を満たす場合に限られます。
一つ目は、引き受ける品質をドメインの知識なしに定義できることです。
Libero がドメインとブランドを持たないと決めたのは、この条件を守るためでした。
二つ目は、品質の基準を根拠から導き、機械で検査できることです。
コントラスト比や Baseline のように、外部に根拠のある基準であれば、CI に載せられます。
三つ目は、接点を列挙でき、それぞれの影響範囲を予測できることです。

この三つを満たさない品質は、基盤には置けません。
業務の規則の正しさのように、ドメインの知識がなければ定義できない品質は、プロダクトの側で要件とテストとして確かめることになります。
要件を検査できる形にすることは第3章で、テストの責務と設計は第5章から第7章で扱いました。

前著の第13章では、開発プロセスをスクリプトにして、誰が起動しても同じプロセスが走るようにする事例を見ました。
本章の基盤は、その成果物の側の対応物です。
プロセスを揃えれば作り方の品質が揃い、基盤を揃えれば、作られたものの一部の品質が作り手に依存しなくなります。

## この章のまとめ

- エージェントやエンジニアでない人が画面を組むと、画像に表れない状態や操作の品質を埋めていたフロントエンドエンジニアの判断がなくなる。生成された画面は見た目が整っていても、見えない層が漏れやすい
- 画面ごとに確かめる手間は作り手の数に比例する。品質を基盤に置けば、基盤を一度確かめるだけで、そこを通った画面はその品質を受け継ぐ
- ラクスの Libero は、ドメインとブランドを持たないと決め、セマンティック HTML、アクセシビリティ、状態表現、テーマ、フレームワーク対応の五つの層を引き受けた。値はコントラスト比などの根拠から導き、Baseline の lint と axe-core で CI に検査させている
- Libero は接点を props、theme、events の三つに絞り、接点だけを通った画面であれば、人が書いても AI が書いても五つの層の品質が保たれるとしている
- この保証は「接点だけを通る」という条件付きなので、条件そのものを CLAUDE.md の指示と lint で確かめる。接点で表せない要件は、回避策ではなく相談事項として基盤の側に返す

Libero のチームは、接点の外の要件について、根拠を共有したうえで判断をプロダクト側に委ねていました。
誰が何を決めるのかをあらかじめ定めておくことは、基盤に限らずチーム全体の課題です。
第3部では、決める人を決めることから始めます。
