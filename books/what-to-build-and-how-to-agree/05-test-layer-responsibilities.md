## UI テストが数千件に積み上がるまで

第1部では、何を作るかを決め、エージェントに渡せる形に整えるまでを扱いました。
第2部では、作ったものが決めたとおりになっているかを確かめる側に移ります。
最初の問題は、テストをどの層に書くかです。

サイボウズの kintone 開発チームは、リリース当初から、機能開発のたびに自動化されたリグレッションテストを追加してきました。
そのなかで多く追加されてきたのが、Selenium で実際の画面操作を模擬する UI テストです。
同チームの堀越は、その数が年月とともに増え、現在では数千ケースに及んでいると書いています。
UI を操作するテストなので、不安定さと実行時間も課題になっていました。

改善の試みは過去にも何度か行われ、新しく追加される UI テスト（同チームの分類では E2E-ui）の数は減少に転じていました。
しかし、すでに存在する UI テストの多くは手つかずのまま残っていました。
新規の追加を絞っても、積み上がった分は自然には減りません。

記事は、UI テストが多く選ばれてきた理由を書いていません。
一つの可能性として、仕様の多くが画面の操作として語られるため、画面操作を再現するテストが仕様との対応を最も確かめやすい形だった、ということが考えられます。
一件ずつ見れば妥当な選択でも、どの層に置くかを書き手が一件ずつ決めている限り、テスト全体の構成は誰も決めていない状態になります。

## エージェントはテストをどこに置くか

kintone の UI テストは、長い年月をかけて積み上がりました。
コーディングエージェントがテストを書くようになると、この積み上がる速さが変わります。
エージェントは実装と一緒にテストを数分で書き、頼めば数十件をまとめて書きます。
そのとき、どの層に置くかは、指示とコンテキストから最も素直に導ける形で決まりやすくなります。

たとえば「アカウントを無効化したユーザーはログインできないこと」という受け入れ条件を渡したとしましょう。
条件が画面の言葉で書かれていれば、ログイン画面を操作するテストが最も素直な翻訳になります。
逆に、実装を読みながらテストを書けば、無効化の処理に関わる内部のメソッドを一つずつ呼ぶ単体テストが並びます。
どちらも、そのテストが担うべき責務から層を選んだ結果ではありません。

層の選択を誤ったときの損失も、エージェントを使う場合のほうが大きくなります。
前著の第10章で、速いチェックは Hooks に置いてエージェント自身に結果を見て直させ、遅いチェックは CI に置く、という分担を扱いました。
エージェントが自分で回す修正のループに入れられるのは、短時間で終わるテストだけです。
本来は下の層で確かめられる振る舞いが UI テストに置かれると、その振る舞いはエージェントのループから外れ、CI まで待たないと壊れたことがわかりません。
しかも CI で落ちた UI テストが、仕様の誤りによるものか、画面操作に起因する不安定さによるものかは、ログを読むまで区別がつきません。

したがって、エージェントにテストを書かせる前に、どの層が何を確かめるのかをチームで決めておく必要があります。
「なるべく下の層に書いて」と頼むだけでは足りません。
何を下の層に書き、何を UI テストに残すのかの基準がなければ、エージェントにも、そのテストをレビューする人にも、置き場所の誤りを指摘する根拠がないからです。

## 層ごとの役割を表にする

堀越が所属するサブチームは、UI テストの削減に取り組むにあたり、テストの種類とそれぞれのカバー範囲をガイドラインにまとめる議論から始めました。
議論の土台にしたのは、テストピラミッドの考え方です。
まず、チームで実装、管理しているテストの種類を洗い出し、各テストの役割について共通認識をまとめました。
その結果が次の表です（記事の表の番号付きの項目を、読点でつないで再構成しています）。

| 種類 | テスト範囲 | 役割と想定場面 |
| --- | --- | --- |
| E2E-ui | Backend＋Frontend | ビジネス的な要求度が高い主要機能のハッピーパスの疎通検証、サイボウズ内の他サービスとの連携テストなど |
| E2E-api | Backend | REST API やサービス内部の API の振る舞いの正しさの検証、入力値の網羅やバリデーションなど |
| Integration | Backend | 実装されている Service レイヤーや DB を結合したテスト |
| Integration | Frontend | フロントエンドのコンポーネントを結合した状態のテスト、ユーザー操作によるコンポーネントの振る舞いなど |
| Unit | Backend | クラスやメソッドのロジックが正しく動作しているかの検証 |
| Unit | Frontend | 単一のコンポーネントやロジックなどが正しく表示、操作できるかの確認 |
| VRT | Frontend | レイアウトが崩れていないかの確認 |

この分類をもとに、同チームは自分たちの状況に合わせたテストピラミッドを作りました。
実行コストに応じてテストケースの数を調整し、実行時間の長い E2E テストを最小限に抑え、実行速度の速い Unit テストを最大の割合にする構成です。

この表は、層を範囲だけでなく役割で定義しています。
「Backend＋Frontend を通すテスト」という範囲の定義だけなら、どんな振る舞いも E2E-ui で確かめられてしまいます。
E2E-ui の役割を主要機能のハッピーパスの疎通と他サービスとの連携に限っておくと、入力値の網羅を E2E-ui に書くことは、ガイドラインからの逸脱として指摘できるようになります。
範囲はその層で何を確かめられるかを表し、役割はその層に何を任せるかを表します。
エージェントへの指示に使えるのは、役割のほうです。

## 観点を先に決め、層を後から選ぶ

ガイドラインができた後、同チームは既存の UI テストの分解を進めました。
手順は二段に分かれています。
まず QA が、対象機能の既存のテストケースなどを参考に、自動テストで担保したい観点を整理し直しました。
このとき、UI テストでカバーしていた機能要件を、より下の層のテストで代替できないかを検討しています。
次に開発者が、実装や依存関係を調べて、整理された観点の分類が適切かを確認しました。

この二段は、何を確かめるかと、どこで確かめるかを分けています。
観点は機能の仕様と過去のテストから決まり、層は実装の構造から決まります。
前者を QA が、後者を開発者が担ったのは、それぞれが判断に必要な情報を持っている側だったからだと考えられます。
エージェントにテストを書かせるときも、この順番は変わりません。
観点が決まっていない段階で「テストを書いて」と頼むと、エージェントは観点と層を同時に、しかも実装の都合から決めることになります。

同記事によれば、実装を進める途中で、テストの層が正しいか迷うものも出ました。
それでも、ガイドラインによって共通の認識と言葉を持っていたことで、再分類の判断はスムーズに進んだそうです。
迷いがなくなったわけではありません。
迷ったときに参照できる基準があったということです。

ガイドラインの策定後、いくつかの機能で改善を実施した結果は次のとおりです。

- UI テストを94件から52件に削減（約45%）
- テストの実行時間を約5分短縮
- UI 操作に起因する不安定なテストを数十件削除

変化は数字だけではありませんでした。
普段の機能開発でもガイドラインが参照され、より小さい分類の自動テストが選ばれることが増えています。
新機能の開発では、まず単体テストや統合テストでカバーできる範囲を検討し、UI テストは必ず担保したいハッピーパスなどに対する手段として位置づけるようになった、と報告されています。
副次的な効果として、実装スコープとテスト対象が明確になったことで、QA が自律的にテストの実装や修正を進められるようになりました。
置き場所の基準が明文化されると、テストを書く主体は、その基準を作った開発者に限られなくなります。
エージェントも、その基準を読める主体の一つです。

## ガイドラインをエージェントへの指示にする

層ごとの役割の表ができていれば、それをエージェントが毎回読む場所に置けます。
たとえば、プロジェクトの CLAUDE.md に次のような節を加えます。

```markdown
## テストを書くとき

- 層ごとの役割は docs/testing/layers.md の表に従う。表にない役割を新しい層に持たせない
- テストを書く前に、確かめたい観点を箇条書きにし、観点ごとに層を割り当てる
- 観点は、その振る舞いを確かめられる最も下の層に置く
- E2E-ui に置けるのは、表で E2E-ui の役割とされている主要機能のハッピーパスと他サービス連携だけ。それ以外を E2E-ui に置く場合は、下の層で確かめられない理由を書いて確認を求める
- 層の判断に迷った観点は、候補の層と迷った理由を書いて確認を求める
- プルリクエストの説明に、追加したテストを層ごとに一覧にする
```

この指示には三つの狙いがあります。
一つ目は、観点を先に書かせることです。
観点の一覧があれば、レビューする人はテストコードを読む前に、確かめる内容と置き場所の対応を確かめられます。
二つ目は、E2E-ui を例外として扱い、理由の記述を求めることです。
理由を書けない UI テストは、下の層で書ける候補としてレビューで扱えます。
三つ目は、プルリクエストに層ごとの一覧を出させることです。
層の偏りは、一件ずつのテストを見ても気付きにくく、一覧にすると気付けます。

ただし、この指示がガイドラインそのものを作ってくれるわけではありません。
表の中身は、テストの種類を洗い出し、各層の役割をチームで合意して初めて決まります。
kintone 開発チームの例でも、ガイドラインの策定は開発者と QA の議論から始まっています。
エージェントに「適切な層を選んで」とだけ頼むと、エージェントは一般的なテストピラミッドの知識から層を選ぶでしょう。
その選択は、チームの実行環境で、どの層がどれだけ遅く、どの層が不安定かを反映しません。

## 下の層へ移した後に見えた課題

同記事は、残った課題も報告しています。
移行後のテストケースは、UI の操作で発生する API リクエストを叩けばよいので作りやすく、その結果、バックエンドに関わる多くのテストケースが E2E-api に移りました。
これによって、フロントエンドとバックエンドで確かめるべきテストを分けることができました。
しかし E2E-api は、E2E-ui より軽量で安定しているものの、実行時間は依然として長く、実行環境のリソースも多く必要とします。
同チームは今後、バックエンドのテストをさらに小さい単位に分け、開発者が素早くフィードバックを得られる環境を整えたいとしています。

この課題には、UI テストが積み上がったときと似た力が働いています。
移行先が E2E-api に集まった理由の一つは、作りやすさでした。
作りやすい層にテストが集まる傾向は、ガイドラインを作った後も残ります。
エージェントにテストを移行させる場合は、この傾向がさらに強く出る可能性があります。
UI テストを E2E-api に書き換える作業は、画面操作をそれが発行するリクエストに置き換える変換に近く、エージェントにとって最も素直な移行先になりやすいからです。
そのため、ガイドラインは一度作って終わりにはできません。
層ごとのテスト数と実行時間を定期的に見て、偏りが出ていないかを確かめる対象になります。

もう一点、同チームがこの取り組みに踏み切れた前提も押さえておく必要があります。
記事によれば、フロントエンドの刷新でテスタビリティが上がり、サーバーサイドのテストコードも機能の断面での分割が進んでいたことで、実装面の懸念は大きく減っていました。
下の層で確かめられるかどうかは、コードがその層でテストできる構造になっているかに左右されます。
その構造がないコードベースでは、ガイドラインに「最も下の層に置く」と書いても、エージェントは上の層に置くしかありません。
なお、同記事の時点で、この取り組みはまだ一部の機能への導入にとどまっています。

## この章のまとめ

- サイボウズの kintone 開発チームでは、画面操作を模擬する UI テストが長い年月をかけて数千件に積み上がり、不安定さと実行時間が課題になっていた
- エージェントは、テストの層を指示とコンテキストから最も素直に導ける形で選びやすい。下の層で確かめられる振る舞いが上の層に置かれると、エージェント自身が回す修正のループから外れる
- 層は範囲だけでなく役割で定義する。役割の表があって初めて、置き場所の誤りを指摘できる
- 何を確かめるか（観点）を先に決め、どこで確かめるか（層）を後から選ぶ。この順番は CLAUDE.md の指示として書ける
- 作りやすい層にテストが集まる傾向は、ガイドラインを作った後も残る。層ごとの数と実行時間を見て、ガイドラインを見直し続ける

kintone 開発チームで観点を整理したのは QA で、その材料は既存のテストケースでした。
次章では、こうした QA の知識をエージェントが使える形にする方法を扱います。
