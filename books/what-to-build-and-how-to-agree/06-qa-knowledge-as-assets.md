## 汎用のモデルが書けないテストケース

前章では、テストをどの層に置くかを扱いました。
置き場所が決まっても、何を確かめるかという観点は、別の材料から決まります。
kintone 開発チームの QA が観点を整理するときに参考にしたのは、既存のテストケースでした。
こうした QA の知識は、エージェントが読める場所にあるとは限りません。

食べログの品質管理部は、手動 QA の業務を生成 AI で自動化する取り組みを進めています。
同部の飲食店 QC チームでリーダーを務める助川は、取り組み始めてすぐに課題に直面したと書いています。
汎用の AI は、一般的なテスト観点なら作れても、飲食店のネット予約管理システムに固有の具体的なテストケースを作れなかったのです。
出力には機能テスト、シナリオテスト、パフォーマンステストといったカテゴリが並びましたが、具体的な操作も、何をもって期待結果どおりと判断するかの情報も足りませんでした。

同氏は、その理由を次のように説明しています。
汎用の AI は、一般的なソフトウェアの品質観点や、一般的な飲食店予約システムの機能についての知識を持っています。
しかし、食べログのネット予約管理システムの仕様やデザイン、過去のテストとその結果についての知識は持っていません。
具体的なテストケースを書くのに足りなかったのは、モデルの能力より、モデルに渡せる知識でした。
より高性能なモデルに替えても、食べログの過去のテストを知らないことに変わりはないからです。

## 目標とプロジェクトの分類

取り組みの前提を先に確認しておきます。
品質管理部は、食べログの予約や食べログノート、インバウンドといった案件の QA を担当しています。
同部は、既存案件のテスト作業を中心に生成 AI で効率化し、今のチームで対応できる案件数を2倍にすることを目標にしています。
中期的には、QA 業務のほとんどを AI が行い、人間は AI の作業をモニタリングするだけの状態を目指しています。

目標に向けて、同部は前年度の案件を、新規のテスト観点が多い「新規」、リグレッションテストの観点が多い「既存」、両方を含む「半々」に分類しました。
前年度に実施した4.7万件のテストケースを振り返ると、約半分がリグレッションテストでした。
また、既存案件はリグレッションテストが中心で、バグも少ないことがわかりました。
この結果から、案件を次の二つに分けています。

- **A. 戦略プロジェクト**：新規開発が中心で、過去の知識を再利用しにくく、不具合の検出件数も多い
- **B. 既存機能改修プロジェクト**：既存機能の改修が中心で、過去の知識を再利用しやすく、不具合の検出件数も少ない

短期の戦略は、B のテスト設計からテスト実行までを AI だけで行えるようにし、QA エンジニアを A に集中させることです。
B が増えても、A に入っているエンジニアの手を借りずに対応できるようにする狙いです。

## どの工程から AI に任せるか

食べログの手動 QA は、三つの工程に分かれています。
この章では、工程の呼び方を同部のものに合わせます。

- **テスト設計**：仕様書、設計書、デザインを入力に、箇条書きや表にまとめたテストパターンを出力する
- **テスト実装**：テストパターンを入力に、手順と期待結果からなるテストケースを出力する
- **テスト実施**：テストケースに沿って実行し、テスト結果を出力する

同部は、Phase 1 でテスト実装を AI 化し、Phase 2 でテストケースから自動テストのコード（食べログで使っている Cucumber のコード）を生成し、Phase 3 でテスト設計を AI 化する、という計画を立てました。
工程の並びとは違う順番です。

テスト実装から始めた理由を、同氏は次のように書いています。
テスト実装は、ドメインや過去のテストの知見といった知識を必要とする工程です。
その知識を作るのに時間がかかることが、全体を AI 化するときの最大のボトルネックになると考えたからです。
Phase 2 を後にしたのも、自動テストを実装する入力として、Phase 1 で作る知識が要るからです。
Phase 3 については、良い仕様書の条件の一つは良いテストケースを作るための材料として使えることだと考え、先に知識を作り、その知識を生成できる仕様書を逆算する計画だとしています。

この順番は、自動化しやすい工程からではなく、知識が必要になる場所から決められています。
コーディングエージェントを QA に使うときも、最初に確かめるのは、どの工程がどの知識を必要とし、その知識がいまどこにあるかです。

## 知識が一か所にない

同氏は、具体的なテストケースを作れなかった原因を二つに分けています。
一つ目は、知識が一か所にまとまっておらず、継続的に更新する仕組みもないことです。
開発ではソースコードが Git で一元管理されているのに対し、QA ではテストケースが複数の Excel ファイルに散らばっていました。
これでは、AI が最新の仕様やテストを使い続けることができません。

対策として、同部は知識の CI 化を進めました。
テストケースを JSON 形式で Git にまとめ、開発のソースコードと同じように一元管理します。
さらに、QA プロジェクトの終了時に、そのプロジェクトのテストケースを知識としてマージするフローを作りました。
プルリクエストの承認を通じて、知識が継続的に更新される仕組みです。

ナレッジファイルの1件は、次のような構造をしています。
記事に載っているのは実際の成果物の一部を伏せたり変えたりしたもので、ここではさらに一部を省略しています。

```json
{
  "観点": "予約経路：国内ネット予約登録",
  "観点No": "A1",
  "テスト目的": "店舗TOPカレンダー：予約登録",
  "前提条件": "テスト用店舗が作成できていること\nネット予約受付状態であること\nPCで操作していること",
  "テスト手順": "1. テスト対象店舗のメディアTOP画面を表示する\n2. 食べログアカウントにログインする\n3. ネット予約カレンダーより以下の情報を入力し予約する\n（省略）",
  "確認内容": "予約完了画面が表示されること\n予約登録できること\n（省略）",
  "補足情報": "対象の店舗：食べ台帳、食べログノート\n操作ユーザ：食べログアカウント\n実行環境：PC"
}
```

JSON にした利点として、同氏は Git でバージョン管理できることと、AI に指示してテストを修正させやすいことを挙げています。
手動でテストを実行する場面のために、JSON と Excel を相互に変換する仕組みも用意しました。
実行の記録は Excel に残せますし、Excel で手作業で書いた過去のテストケースを JSON に変換して管理することもできます。

この対策の効き方は、コーディングエージェントを前提にするといっそうはっきりします。
コーディングエージェントが読めるのは、リポジトリと、そこから辿れるものです。
共有ドライブの Excel に残ったテストケースは、エージェントにとって存在しないのと同じです。
知識がリポジトリにあれば、テストケースを書くエージェントも、コードを書くエージェントも、同じ知識を読めます。

更新の仕組みも、置き場所と同じくらい効きます。
古い仕様のテストケースが知識として残っていると、エージェントはそれを根拠に、すでに変わった振る舞いを期待するテストを書くおそれがあります。
プロジェクトの終了をマージの契機にすると、知識の鮮度を保つ作業が QA の仕事の流れに組み込まれます。
前著の第8章では、修正プルリクエストからレビュー観点を育て、人の承認を挟んでスキルを更新する仕組みを扱いました。
食べログの知識のマージも、作業の結果を承認付きで資産に戻すという点で、同じ形をしています。

## QA エンジニアが頭の中で考える順番

二つ目の原因は、汎用の AI がドメインの知識と過去のテストの知見を持たないことです。
一つ目と似ていますが、指しているものが違います。
一つ目は記録の置き場所の問題で、二つ目は記録をどう使うかという判断の問題です。
QA エンジニアは、過去のテストの知見から、重要な機能のリグレッションテストをスコープに入れられます。
汎用の AI は、その判断の材料を持っていません。

対策として、同部は食べログの QA エンジニアが頭の中で考えている手順を、AI で再現することにしました。
整理された手順は、次の三つの Step です。

1. 予約可否はビジネスへの影響に直結するため、過去のテストをそのまま流用してテストを実装する
2. 仕様変更が影響する箇所は、過去のテストを修正してテストを実装する
3. 仕様書、デザイン、設計書から新しい観点のテストを実装する

この順番には、QA エンジニアのリスクの判断が入っています。
最初に確保するのは、壊れたときの影響が最も大きい機能の回帰で、そこは過去のテストを変えずに使います。
次に、変更の影響を受ける箇所だけを修正します。
新しい観点を考えるのは最後です。
知識をリポジトリに集めても、この順番がなければ、エージェントは知識のどこから手を付けるべきかを判断できません。
したがって、QA の知識の資産化には、テストケースの集約と、それを使う順番の明文化の両方が要ります。

実装も Step ごとに進められています。
Step 1 は Dify のワークフローとして組まれました。
QA エンジニアが投げたテストパターンのプロンプト全体を、AI がナレッジ検索用の小さいプロンプトに分解し、小さいプロンプトごとにナレッジから該当するテストケースを検索し、最後に検索結果をマージする構成です。
Step 2 では、過去のテストケースのナレッジファイルと組み合わせのテストパターンを入力に、デシジョンテーブル技法を適用するプロンプトを用意して、テストケースを生成しました。
記事の時点で AI 化できたのは Step 1 で、Step 2 は検証の段階です。
Step 3 と、どのテスト技法を適用するかの判断は、今後の課題とされています。

## 成果と、人が担い続けている部分

6月の1案件で試したところ、リグレッションテストを430件作成でき、手作業と比べて0.3人月程度の工数を削減できました。
初回だったため、プロンプトの試行錯誤と、AI が作った成果物のレビューに時間がかかったそうです。
そのノウハウを得たことで、今後の案件では1か月あたり1.7人月程度の削減を想定しています。
これは記事の時点での見込みです。
同部は7月から、既存機能改修案件のリグレッションテストの実装をすべて AI で作る体制を始め、自動テストの実装の AI 化も小規模に始めたと報告しています。

この事例からは、人が担い続けている部分も読み取れます。
AI が作ったテストケースのレビューは人が行いました。
知識をマージするプルリクエストの承認も人が行います。
Step 3 の新しい観点の洗い出しと、テスト技法の選択は、記事の時点では AI 化されていません。
AI 化が進んだのは、過去の判断を再利用できる部分です。
前例のない判断は、記事の時点ではまだ人に残っています。

## 知識と順番をリポジトリに置く

食べログの仕組みは Dify のワークフローで作られていますが、同じ考え方はコーディングエージェントのスキルとしても書けます。
以下は、既存機能の改修に対してリグレッションテストのケースを作らせるスキルの案です。
ナレッジの JSON がリポジトリの決まったディレクトリにあることを前提にしています。

```markdown
---
name: regression-test-cases
description: 既存機能の改修に対して、ナレッジからリグレッションテストのケースを作る
---

## 入力
- 改修の仕様書と、変更される画面や API の一覧
- qa/knowledge/ 以下のナレッジ（JSON）
- qa/critical.md（ビジネスへの影響が大きく、毎回必ず回帰を確かめる機能の一覧）

## 手順
1. 重要機能の回帰：qa/critical.md に挙げた機能のテストケースを、ナレッジから変更せずに選ぶ
2. 変更の影響範囲：仕様書の変更箇所に関わるテストケースを探し、変更後の仕様に合わせて修正する。修正前後の差分を残す
3. 新しい観点：仕様書から、ナレッジにない観点を挙げる。テストケースにはせず、候補として列挙する

## 出力
- 手順ごとに分けて出力し、各ケースに元にした観点No を付ける
- 手順3の候補には「新規」と明記し、QA の判断を求める
- ナレッジにない仕様を推測で補わない。不明点は質問として列挙する
```

この案は、食べログの3段階の順番を、そのまま手順に写したものです。
どの機能を重要とみなすかは QA エンジニアの判断そのものなので、ナレッジとは別のファイルに分けて明文化しています。
食べログの Step 1 で言えば、予約可否がこの一覧に入ります。

もう一点、手順3の扱いを食べログの Step 3 から変えています。
新しい観点はテストケースにせず、候補として QA に返させます。
前節で見たとおり、新しい観点の洗い出しは食べログでも AI 化の途上にあり、人の判断が残っている部分だからです。
手順ごとに出力を分けておくと、レビューの重みも分けられます。
手順1の出力は、選ばれた観点No が正しいかを確かめれば足ります。
手順2では修正の差分を、手順3では観点そのものを見ます。

## この章のまとめ

- 食べログの品質管理部では、汎用の AI が一般的な観点は作れても、ドメインに固有の具体的なテストケースを作れなかった。足りなかったのは、モデルに渡せる知識だった
- 同部は AI 化の順番を、自動化しやすさではなく、知識が必要になる工程から決めた。テスト実装を先にし、テスト設計を最後にしている
- 散らばっていたテストケースを JSON にして Git に集め、QA プロジェクトの終了時にプルリクエストでマージする。リポジトリにない知識は、コーディングエージェントからは見えない
- 知識の集約だけでは足りない。QA エンジニアが考える順番（重要機能の回帰、変更箇所の修正、新しい観点）を明文化して初めて、エージェントは知識の使いどころを判断できる
- AI 化が進んだのは過去の判断を再利用できる部分で、新しい観点とテスト技法の選択は、記事の時点では人に残っている

知識と順番が揃っても、それを使ってテストを設計するのが、機能を実装するエージェント自身であれば、テストには別の偏りが入ります。
次章では、テストを設計する者と実装する者を分けることを扱います。
