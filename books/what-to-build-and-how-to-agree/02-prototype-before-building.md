## Why が書けても解決策は決まらない

第1章では、要望に Why を書いてもらう方法を扱いました。
Why が書かれていれば、作る側は解決策を選べます。
ただし、選んだ解決策が Why を満たすかどうかは、Why を読んだだけではわかりません。

第1章の例では、「退職者がログインできないようにしたい」という Why に対して、アカウントの無効化という解決策を選びました。
それでも、無効化した退職者を一覧でどう見せるか、その人が所有していたチャンネルを誰が引き継ぐかは、管理者が画面を触ってみるまで決まらないかもしれません。
要望を出した人自身も、具体的に何が欲しいのかを最初から知っているとは限らないからです。

mtx2s は、人間は机上の分析だけで正解を引き当てることが苦手で、それは作る側だけでなく使う側も同じだと書いています。
計画どおりに作り上げるやり方では、計画期間の最終段階でようやく動くソフトウェアに触れられます。
何度も触って改善しながら作るやり方では、初期段階から検証可能な最小限のソフトウェアに触れられます。
同氏は、後者のほうが正解に近いアウトプットを出しやすいとし、この課題の解決策として従来から用いられてきた手法に**プロトタイピング**を挙げています。
本書では、このとき作る動くソフトウェアを**試作**と呼びます。

## 試作はなぜ高くついていたか

試作は新しい手法ではありません。
mtx2s によれば、本番版より簡易な試作でも、実際に動くソフトウェアで作るにはコストがかかっていました。
そのため、ペーパープロトタイプのような静的なもので済ませたり、試作する対象を厳選したりして、コストと検証の充実度に折り合いをつけてきた、と同氏は書いています。

AI は、この折り合いを変えました。
同氏が挙げるのは、本番稼働に必要な内部品質を満たすことを前提としない、使い捨ての試作です。
そのハードルを一気に下げたのが、**バイブコーディング**（人間がコードを書いたり読んだりせず、動作を確かめながらコーディングエージェントに指示を繰り返して作る手法）だとしています。

試作が安くなった理由は、コードを書く速さだけではありません。
mtx2s は、ユーザー価値の断面で本番のコードを少しずつ作り上げるやり方の難しさとして、どの断面で切り取るかの判断と、内部構造をどこまで整えるかの判断を挙げています。
使い捨ての試作では、特に後者の悩みが軽くなります。
捨てるコードの内部構造に悩む必要はないからです。
コーディングエージェントに試作を任せると、書く手間と整える手間が同時になくなります。
残るのは、何を確かめるかを決める手間です。

## 動くものを囲む人が変わる

mtx2s は、バイブコーディングが試作にもたらした恩恵として、コストと時間のほかに二つを挙げています。

一つは、職種を問わず試作に参加しやすくなったことです。
企画担当者やデザイナーも、AI で試作を作れるようになりました。
同氏は、サーバサイドの開発を伴うと難易度が上がるものの、スマホや PC など端末側だけで完結するものならかなりの作り込みができると書いています。

もう一つは、企画から開発へのハンドオフへの依存が減ったことです。
できあがった試作は、仕様を具体的に伝える手段になります。
同氏は、ドキュメントが不要になるわけではないとしたうえで、試作の動作やコードをもとに本番のコードの設計の多くを導き出せると述べています。
そして、職種を越えて一箇所に集まり、動くソフトウェアを囲みながら反復的に検証していく開発の姿を描いています。

この変化は、第1章の Why と組み合わせると効き方がはっきりします。
Why を書いた人が、その Why を満たすはずの画面を自分で触れるようになるからです。
「削除ではなく無効化でよいか」は、文章で問うより、無効化された退職者が一覧にどう見えるかを見せたほうが早く答えが出ます。
要望を出した人が自分で試作を作れるなら、要望が開発に渡る前に、Why と解決策の食い違いの一部を本人が見つけられます。

## 試作か本実装かを先に決める

試作が安くなると、試作と本実装の境界が曖昧になります。
mtx2s は、試作のコードを AI に本番に必要な品質を満たすコードへ書き換えさせて済むこともあるだろう、と書いています。
動いている試作があれば、それをそのまま育てたくなるのは自然です。

nwiizo は、「とりあえず作らせて、見ながら考える」は試作で捨てる前提なら有効だと書いています。
本実装に合意のないまま渡すと、実装と差し戻しの繰り返しでコストが膨らむため、今作るものを捨てる試作にするのか本実装として残すのかを先に決めておく必要がある、というのが同氏の主張です。

先に決めておく理由は、試作と本実装では完了の条件が違うからです。
試作の完了は、確かめたい問いに答えが出ることです。
本実装の完了は、要件を満たし、運用に耐えることです。
どちらか決めないまま作り始めると、動いた時点で完了したように見えます。
そして、試作が答えていない問いを抱えたまま本実装に進むことになります。

## 「API が動く」まで確かめた決済機能

ganesha の個人開発の記録は、この危うさをよく示しています。
同氏は、wiki の記事を販売するサービスを1年かけて開発しました。
決済の要件は、記事ごとのワンタイム決済とプレミアムプランのサブスク決済です。
ワンタイム決済には、一つの記事に紐づく複数の執筆者へ代金を分配する仕組みも必要でした。

同氏は最初、決済サービスに Stripe を選びました。
本人の言葉では、「ろくに Stripe について調べもせずに」技術スタックに積み上げた選択です。
API は使いやすく、分配は Stripe の連結アカウントの機能で実現でき、決済要件を満たすものを難なく作り上げられた、と同氏は書いています。
サンドボックス環境には、テスト時間を進めてサブスクの月額課金をすぐに試せるテストクロックという機能もありました。

導通テストまで終えて本番環境を有効化しようとしたとき、同氏は手続き中にあった「禁止業種および制限付き業種」のリンクを何の気なしに開きます。
制限のある業種の中に、「コンテンツ制作プラットフォーム」に関する記述がありました。
同氏のサービスは、そこに該当しそうでした。
問い合わせに対する Stripe の返答は、コンテンツ制作プラットフォームへのサポートは初期段階にあり、登録されたすべてのビジネスをサポートするのは難しい、というものでした。

代わりを探すとき、同氏は候補のガイドを隅まで読むようになります。
fincode は、決済サービス側の画面へリダイレクトする型の決済ではサブスクが使えないとわかり、諦めました。
KOMOJU は、FAQ の計算例から手数料に消費税がかかることと、振込手数料が別にかかることを見つけ、やめています。
残った Square には、Stripe で分配を担っていた連結アカウントに相当する機能がなく、同氏はこれを諦めました。

Square でも制約は続きました。
サブスク決済では、アプリ側の情報を載せる metadata を含め、webhook によるデータの受け渡しがサポートされていませんでした。
同氏は、決済用のセッション管理を自前で用意してこれを乗り越えます。
さらに、サンドボックスでリダイレクト型のサブスク決済を試すと、サブスク用ではなくワンタイム決済用の画面が表示されました。
API リファレンスを見ても問題は見当たらず、Square に問い合わせると、サンドボックスではリダイレクト型のサブスク決済はできないので本番環境でテストすることを勧める、という答えが返ってきました。
同氏は自分のクレジットカードを本番環境で使い、日ごとの課金と払い戻しを繰り返した後、月額で課金しては1か月結果を待つ周期を3回繰り返しました。
サブスクのテストだけで、3か月を費やしています。

## 試作が答えた問いと答えなかった問い

Stripe での実装は、試作として作られたものではありません。
それでも、本番を有効化する前の時点で何が確かめられていたかを見ると、動くもので答えが出る問いと出ない問いの境目が見えます。

確かめられていたのは、「この API で要件どおりの決済が組めるか」です。
Stripe の API とサンドボックスは、この問いに十分な答えを返していました。
確かめられていなかったのは、「このサービスはこの決済サービスの上で運営できるか」です。
前者は、コードを書けば答えが出ます。
後者の答えは利用規約と決済サービス側の判断にあり、コードをいくら書いても出てきません。

同氏の記録に出てくる制約を、どうすれば事前にわかったかで分けると、次の三つになります。

- **文書を読めばわかる制約**：Stripe の業種制限、fincode のリダイレクト型決済の制限、KOMOJU の消費税と振込手数料。どれも決済サービス側が公開している文書に書かれていた
- **動かせばわかる制約**：Square のサブスク決済で metadata が受け渡されないこと。同氏は実際に試して気付き、問い合わせで確定させた
- **問い合わせなければわからない制約**：Square のサンドボックスでリダイレクト型のサブスク決済ができないこと。API リファレンスには手がかりがなく、問い合わせて初めてわかった

試作が直接答えられるのは、二つ目だけです。
一つ目と三つ目は、試作が動いても動かなくても答えが変わりません。
しかも三つ目は、本番の前にどれだけ検証できるかを決めていました。
Stripe ではテストクロックで時間を進めてすぐに試せた月額課金の確認に、Square では3か月かかっています。
決済サービスを選ぶことは、後で使える検証環境を選ぶことでもありました。

## エージェントは「動く」までを速くする

コーディングエージェントは、二つ目の種類の制約に早く行き当たらせてくれます。
「Stripe で記事ごとの決済と執筆者への分配を試作して」と頼めば、エージェントは API のドキュメントを読み、サンドボックスで動くところまで短時間で進むでしょう。
第1章で書いたとおり、エージェントは渡された指示を完了の条件にします。
指示が「試作して」なら、完了の条件は動くことです。
業種制限のページは、動かすために読む必要がないので、指示しない限り読まれません。

人が数週間かけて決済を組んでいた頃なら、そのあいだに規約や料金のページを目にする機会があったかもしれません。
ganesha も、Stripe の業種制限に気付いたのは、本番有効化の手続き中にたまたまリンクを開いたときでした。
エージェントが試作を数十分で終えると、こうした偶然に出会う時間も短くなります。
動く試作が早くできるほど、動くこと以外の問いは意図して立てる必要があります。

前著の第5章では、再実行性、処理時間、負荷制約といったコード外の現実制約を作業前に洗い出すチェックリストを示しました。
あのリストは、作ることが決まった後で、AI に任せる範囲と粒度を決めるためのものです。
試作の段階で洗い出す制約は、それより手前にあります。
選んだ外部サービスや方式の上で、そもそもこのサービスを運営できるか、という問いです。

## 試作を始める前に書くこと

ここまでを踏まえて、試作を始める前に書いておく項目を提案します。
Issue の先頭に置く短いメモで足ります。

```markdown
## 試作メモ

### 確かめたい問い
- Why のどの部分を、この試作で確かめるか
  （例: 管理者が、無効化された退職者を一覧で見分けられるか）
- 誰が触って答えを出すか

### 扱い
- 捨てる試作か、本実装として残すか
- 捨てる場合、いつ捨てるか（問いに答えが出た時点、など）

### 試作では確かめられないこと
- 外部サービスの利用規約、禁止業種、審査
- 料金体系（手数料、税、振込などの付帯費用）
- テスト環境と本番環境の差（サンドボックスで試せない機能、時間を進められるか）
- 法令や社内規程の制約
- それぞれの確かめ方（読む文書、問い合わせ先）、確かめた結果、確かめた日付
```

最後の項目の下調べは、エージェントに任せられます。
CLAUDE.md に、たとえば次のように書きます。

```markdown
## 試作を依頼されたとき

- 実装を始める前に、試作メモの「確かめたい問い」と「扱い」が埋まっているか確認し、空なら質問を返す
- 外部サービスを使う場合は、利用規約の禁止業種、料金、サンドボックスで提供されない機能を公式の文書から探し、出典の文書名とともに列挙する
- 公式の文書で確定できなかった項目は「問い合わせが必要」として分けて報告する
- 試作のコードは本番のコードと同じディレクトリに置かない
```

エージェントの下調べで、文書を読めばわかる制約の見落としは減らせます。
ただし、問い合わせなければわからない制約は残ります。
ganesha の場合、Square のサンドボックスの制限は、API リファレンスを読んでも見つかりませんでした。
エージェントが「問い合わせが必要」として返した項目は、人が問い合わせて、答えをメモに書き込みます。
試作が動いても、この欄が埋まるまでは本実装に進まない、と決めておけば、「動いた」が「運営できる」と取り違えられにくくなります。

## この章のまとめ

- Why が書かれていても、選んだ解決策が Why を満たすかは触ってみるまでわからないことが多い。作る側も使う側も、机上の分析で正解を引き当てるのは苦手である
- コーディングエージェントとバイブコーディングは、使い捨ての試作のコストを下げ、企画担当者やデザイナーも試作を作れるようにした。動くものを囲んで、職種を越えて確かめられる
- 試作か本実装かは、作り始める前に決める。試作の完了は問いに答えが出ることであって、動いたことではない
- 試作が答えられるのは、動かせばわかる制約だけである。利用規約や料金のように文書を読めばわかる制約と、テスト環境の限界のように問い合わせなければわからない制約は、試作とは別に確かめる
- エージェントは「動く」までを速くするぶん、動くこと以外の問いを意図して立てる必要がある。文書の下調べはエージェントに任せ、問い合わせの答えは人が書く

試作で確かめた解決策は、本実装としてエージェントに渡されます。
次章では、確かめた要件を型やテストや CI で検査できる形にして、本実装が要件から外れていないかを機械で確かめられるようにする方法を扱います。
